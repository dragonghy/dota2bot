## 5. §V.2 前提的一处更正:**高段不是 placebo,它是另一条分支的 active set**

总监 §V.2 的立论是「高段同臂同局同种子,只差 `capmono` 自己的算术 ⇒ 臂内 placebo」。
把 `GetDesireHelper` 的**全部**返回点列出来(`bots/mode_team_roam_generic.lua`,本轮逐行核过):

| 行 | 分支 | 出价 | 在 HP∈[0.42,0.50] 里 capmono 生效当且仅当 |
|---|---|---|---|
| L235 / L258 / L272 | helpCoreTargeted / punish-dive / overchase | **1.96·HP** | HP ≤ **0.4592** |
| L245 | helpAlly | **1.633·HP** | HP > **0.4409** |
| L297 / L312 | l1trade / l5combo | — | **永不**(`bLaneKillCommit` 在 L106 整条豁免,GH #31) |
| L327 | AttackSpecialUnit | Remap(HP,0.1,0.8,NONE,nDesire) | 视 nDesire,边界不在 0.4592 |
| L333 | warlock upheaval | **0.85 常数** | **两段都生效** |
| L356 / L364 | Carry/SupportFindTarget | targetDesire,HP≥0.4 **饱和** | 多数取值 >0.9 或 ≤0.72 ⇒ no-op,**但 L780 那支返回 `BOT_MODE_DESIRE_HIGH = 0.75`** ⇒ **两段都生效** |
| L370 / L382 | towerCreep | **0.90 常数**(HP≥0.4 饱和) | **两段都生效**(见下) |

两条结论:

1. **总监指定的「no-op 高段」(0.4592,0.50] 恰好是 `helpAlly` 的 active 带**
   (1.633·HP > 0.72 ⟺ HP > 0.4409)。两族的生效带在采样窗里**近似互补**,
   所以「高段点估计应贴近 0」并不由代码推出 —— 实测的 −5.8pp 与「capmono 在高段通过 helpAlly 起作用」
   完全相容。§V.2 point 4 说的「helpAlly 预测相反梯度」是对的,但**比总监写的更强:它不是可能互相抵消,
   而是参照带本身就带着效应**。
2. **三条「capmono 生效但对 HP 平坦」的分支**(0.90 / 0.85 / 0.75)在**每一段**都生效,包括 P 带 ——
   它们把任何 HP 切分都往 null 稀释,**与 capmono 是否有效无关**。
   其中 towerCreep 那条尤其值得记一笔:**已发布的 cliff 写的是 `if desire > 0.9`,而这条分支出价恰好 `0.9`
   ⇒ 严格大于号让 cliff 结构上永远碰不到它;capmono 的 `> 0.72` 却碰得到。**
   ⇒ **`capmono` 不是「把同一个集合收窄」,它新捕获了 cliff 够不着的分支**(推塔/塔下小兵出价 0.9→0.72)。
   这一点门的注释("make the ceiling a real ceiling for everything still capped")字面上没错,
   但它的立论只讲了 1.96·HP 那族的「非单调钉死」,**推塔出价被一起压低不在立论里**。

**⇒ 建议进 test_set.md §0b(第二十例,新亚型)**:
> **算术型 gate 的 active set 补集,只有在「域内所有帧共用同一条出价公式」时才是 placebo。
> 出价斜率异质时,补集是另一条分支的 active set;出价为常数的分支则在所有段一起生效。
> 求交之前必须先枚举全部返回点的出价公式,而不是列举「主要的几条」。**
（与 §V.4 第十九例成对:第十九例说「检测域比 active set 宽」,本例说「你以为的补集其实也在 active set 里」。）
