## 4. ⭐⭐⭐ 本轮主发现:第一个读数是假的,而假在**我自己的 print 语句**里

普查的第一版是 inline 脚本,把 arm 串按 `cands[cand[:60]] += 1` 归桶 —— **`[:60]` 是为了打印好看**。
于是 42 id / 372 bytes 的串**打印成 8 个 id、结尾 `teamb`**,而 `teamb` 正是
`teambrain` 在第 60 字节处被切断的样子。

**它看起来完全像一个真缺陷**,而且是**最贵的那一类**:

- 8 个 id 恰好是声明集的**前 8 个、原序**,第 8 个**从词中间断开** ——
  这正是机械截断的指纹,人手挑集不会切在词中间;
- `teamb` 在全树**不是任何 id**(`grep` 全仓 0 命中;真 id 是 `teambrain`,
  调用点 `bots/FunLib/jmz_func.lua:6646`)⇒「第 8 个 id 也是哑的」;
- W23(8 小时前)四个 run **全串 43 id / 381 bytes**,对比之下**像是新引入的回归**;
- 批测台章程自己写着「**全集串不变**、只动 rec-slots」⇒ **像是发波台不知情**;
- `validate_onspot.sh` 的 `$CAND` **同时**喂 `write_soak_side.sh`(:70)和
  stamp(:88)⇒ 「stamp 被截断 ⇒ **gate 文件也被截断**」这条推理是**成立的**,
  只不过前件是假的。

**差一步就发生的事**:以 [harness] 立案「W24 把 35 个 id 静默丢掉、波次正在烧钱」,
并按「飞行中的波次」推送告警。**收集承重帧证据时才发现全串是完整的 372 字节。**

⭐ **这是 #296 / #297 家族再往前一步**:那两条是**仓库里的工具**把读者引向错误结论,
这一条是**分析者自己的一次性脚本**。前者有 issue 兜着,后者**没有任何东西会举手** ——
inline 读法死于会话结束,下一轮重写一遍,**每一轮都有一次新的机会以新的方式读错**
(#263 立案时说的是「重做浪费」,本轮量到的是**重做会读错**,比浪费贵)。

⚠️ **一条给全队的读法**:**「像机械截断的指纹」本身可以被显示层伪造。**
本轮那五条佐证里有四条是真的(前 8 个原序、词中间断开、`teamb` 不是 id、W23 对比),
