## 二、尺子这一格改了什么(以及为什么它之前是**结构性**看不见)

原来的 `measured_levelups` 有一条分支:

```python
if a["name"] not in cur:
    # granted after the horn (scepter/shard: shadow_shaman_urnaconda)
    cur[a["name"]] = a["level"]
    continue
```

**天赋在开门前那一帧根本不在 `abilities[]` 里**(未点的天赋没有可解析的句柄),
它是**被点的那一瞬间才出现**的,于是每一个天赋都恰好走进这条「后发放」分支,
基线被设成「它出现时的等级」⇒ **差值恒为 0 ⇒ 每个天赋都被吞掉**。
`n_talents` 这一列因此**在 80 行里全是 0,而且看起来完全正常**。

修法一行:天赋的基线是 **0**,神杖/魔晶技能保持原样。

```python
cur[name] = 0 if is_talent(name) else a["level"]
```

⭐ **能力那一侧逐位未动**(非天赋走 `cur[name]=a["level"]`,紧接着的 `>` 判定恒假,
与原来的 `continue` 同效)⇒ 上一轮的 `MATCH/PREFIX/DEVIATION` 判决**原样复现**,
这既是兼容性也是**免费的自检**。另外天赋**不并入同帧合并**(同帧齐涨 = 一个技能点,
那条只对连锁技能成立,天赋永远不同帧齐涨)。

新增四列:`last_pt_lvl` / `final_lvl` / `stall_s` / `head_slot`,
以及一个 `--events <hero> <timeline…>` 模式打逐点流水。

`head_slot` 用的是 **`GetSkillList` 自己的槽位规则**(`aba_skill.lua:217` 逐字转写,
不是猜):`i >= 10 and (i % 5 == 0 or 能力表已用尽)` 放天赋。15 能力 + 8 天赋 ⇒

```
[a1..a9, T1, a10, a11, a12, a13, T2, a14, a15, T3..T8]
```

**⇒ 13 个能力点 + 1 个天赋 = 恰好吃掉槽 1..14,队头就是槽 15 = T2。**

⚠️ **`head_slot` 的前提是「一个点吃一个槽」**,而 `generic_hidden` 分支和中间那条
「still try it」**会吃掉一个槽却不产生一个点** ⇒ 一旦发生过,这一列会偏。
本轮承重的 6 行**逐帧核过没有发生**(见第三节),其余行的 `head_slot` **不要单独引**。

## 四、⭐⭐ 把验收 1 的「二选一」砍成一个:幸存者是等级需求,不是 `IsHidden()`

`aba_skill.lua:168-178` 把 #799 验收 1 停在这里(逐字):

> 墙是实测的,因此中间那条分支没被走,因此 **`IsHidden()` 为真 or 等级需求未满足**。
> ⚠️ 这说的是**哪条分支**,不是**两个幸存者里的哪一个**。

本轮买到的是**墙自己塌掉的那一帧**。`ab6c0d_220100_slot6` bristleback(idx=1498,final_lvl=28):

```
      …… 停摆 435 秒 / 10 个英雄等级(14 → 24),手里一直攥着点 ……
#15 t=1085.4  herolvl=24  abil   bristleback_viscous_nasal_goo   ← 墙塌,出来的是**能力**
#16 t=1086.4  herolvl=24  abil   bristleback_warpath             ← 隔 1 秒,队列在逐帧排空

```

`ab6c0d_220052_slot5` shadow_shaman(idx=1426)同形,塌在 **23 级**(#15 t=1301.5)。

**推理(每一步都指得出源码或帧)**:

1. `#15` 出来的是**能力不是天赋**,而 `#17` 之前 `n_talents` 一直是 1
   ⇒ **队头那个天赋离开队列时没有被训练**。
2. 源码里能在 **`botLevel <= 25`** 时把队头挪走的路径**只有三条**
   (`ability_item_usage_generic.lua:386-432`):大 `if`(**升它**)、
   `generic_hidden` 分支(**升下一个**)、中间那条「still try it」(**试着升它,然后移除**)。
   `botLevel > 25` 那条在 23/24 级**够不到**;`skillstall` 门**未 armed**(本语料 W40)。
   第 1 条会让 `n_talents` 涨 ⇒ 被 (1) 排除。
3. 于是走的是中间那条,它的条件逐字是
   **`not IsHidden() and botLevel >= GetHeroLevelRequiredToUpgrade()`**。
4. ⭐ **`IsHidden()` 不随 `botLevel` 变**。这个合取在 23 级为假、24 级为真
   ⇒ **翻号的只能是 `botLevel >= GetHeroLevelRequiredToUpgrade()` 那一项**。

**⇒ #799 验收 1 的答案(天赋队头这一半):幸存者是 `GetHeroLevelRequiredToUpgrade()`,
它对一个卡住的天赋队头报出的是 ~23–24,而不是该天赋的档位等级(15)。**

⭐ **这与上一轮在 OD 上测到的形状是同一个**(「一个已满级技能报出 bot 永远够不到的等级需求」)
—— 两个互不相关的域、两轮独立的语料,**指向同一个幸存者**。

### ⚠️ 这一节的 LIMIT(不要越过)

- **n=2**(两局塌墙),而且塌的等级 **23 与 24 不一致** ⇒ 「~23–24」是读数不是常数,
  **别把它写成一个公式**。

  ⇒ **`sTalentList` 的完整槽位序在本仪器上不可测**。T2 的身份靠的是
  `GetTalentBuild`(`aba_skill.lua:135-150`)的**源码算术** + T1 的**帧确认**,
  **不是对 T2 的直接读数**。
- **残留的另一种解释**(未能排除,如实登记):若 `IsHidden()` 恰好也在 23/24 级由真变假
  (某种与英雄等级相关的天赋可见性),第 4 步就不成立。源码与 API 文档里没有这样的机制,
