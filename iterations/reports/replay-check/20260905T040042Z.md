## 二、`outlatch` 条件 (a):INDETERMINATE,而预登记的读法说中了

### 2.1 能买到什么、买不到什么(先划清楚,后面所有数字都在这条线内)

`outlatch`(`bots/mode_outpost_generic.lua:79`)管的是**闩**:出厂
`DidWeGetOutpost = true` 在扫描之后**无条件**执行,所以**一次空扫描**就把这个
bot 这一局的瞭望塔模式永久关死;armed 时闩改成记录后置条件
(`#Outposts > 0`)并**每游戏秒重扫一次**。

⇒ 可观测的后果**只有一条**:表为空的 bot 永远走不到 `Think()` 里的
`Action_UseAbilityOnEntity(hAbilityCapture, …)`,**发不出 `ability_capture`**。
所以**一次施法证明那个 bot 的表非空**;出厂腿上,它证明**第一次扫描成功**。

⚠️ **逆命题不可观测**:"没施法"与空扫描、与二塔没倒、与
`IsSuitableToCaptureOutpost` 为假、与别的模式出价更高**全部相容**。
`outlatch` 自己的域(**"第一次扫描返回空表"**)**不在 dump 里**,
所以施法普查是**活性的上界**,对门的效应量零信息。
这正是入集时 test_set.md §DN.6 收割前必读第 (i) 条要求的措辞:
**恒零要报"域为空",不许报"测过了无效应"** —— 本轮不是恒零,但同一条线管着它。

### 3.3 代码级根因(读源码,不猜)

`mode_outpost_generic.lua` `Think()` 在 ≤300u 分支里**每个 think tick 无条件
重发** `Action_UseAbilityOnEntity(hAbilityCapture, ClosestOutpost)`,
**全文件没有 `bot:IsChanneling()` 守卫**;重发一次 = channel 重来一次。
它前面唯一的节流是通用的
`J.Utils.IsBotThinkingMeaningfulAction(bot, Customize.ThinkLess, "outpost")`,
而那个 helper 的"正在做正事"判据是
`meaningfulActivities`(`bots/FunLib/utils.lua:2301`)—— 里面是
`ACTIVITY_CHANNEL_ABILITY_1..6`,**是英雄自己的 6 个技能槽**;
`ability_capture` 是**隐藏的通用继承技能**(dumper 自己都把 `_Capture`
从 `abilities[]` 里滤掉),它的动画 activity **不在那张表里**。
⇒ 守卫**结构上盖不住这次 channel**,重发照常发生。

**这是假设不是判决**:`GetAnimActivity()` 在抢塔时返回什么,离线读不到
(dump 不落 anim activity)。**能确证的是可观测的那半**:重发存在、
守卫不存在、中断存在、中断不是伤害造成的。
**双峰分布也支持"要么没被重发打断、要么被打断"**:53 次尝试的时长
0.1…2.9(38 次)/ 4.2 / 4.4 / 5.2 / 5.9×7 / 6.0×5 —— 没有连续谱。

### 3.4 建议的修法与在仓库里的先例

`Think()` 开头加 `if bot:IsChanneling() then return end`。
**先例在仓库里**:`bots/mode_farm_generic.lua:1260` 就是这么写的;
API 见 `docs/BOT_API_REFERENCE.md:1501`。
**这不是本组能落地的改动**(本组不改 bot 代码),已开 issue 交协同组。

## 四、量具:两次被逐帧推翻,一次被真值校准

### 4.1 ⭐ 完成判据不是断言的,是**拿游戏自己的真值校准的**

"channel 满 5.0 秒 = 完成"如果只是抄一个技能时间,它**只在没人改动的那天正确**。
真值是现成的:占下来了,瞭望塔的 `team` 字段就会翻。
`verify_floor()` 每次跑都做这件事,本轮读数:

```
attempts followed by a flip : 0.6 5.2 5.9 5.9 5.9 5.9 5.9 5.9 5.9 6.0 6.0 6.0 6.0 6.0
longest attempt with NO flip: 4.4
flips with no preceding attempt: 0
misfiled by floor 5.0: 0 called complete without a flip, 1 called aborted that flipped
```
**13 次易主,13 次都有对应的 channel**(零孤儿);**翻了塔的最短 5.2s,
没翻塔的最长 4.4s** ⇒ 5.0 落在真空隙里。

⚠️ **空隙是空隙,不是空集**,这句必须写:4.2 / 4.4 / 5.2 三次落在带里,
判据挪进那条带会**重新标注个别尝试**。它**不动结论**
(界 4.0–5.5 全程:armed 中断率 68–76%、base 75–79%,四段零收益围观逐字不变),
所以可引用的说法是**"在那条带上稳健"**,**不许写成"分布在那里是空的"**。

`misfiled` 的那 1 次是 `20260905_003438_slot7` 的 lina:0.6 秒的尝试
**恰好落在 bristleback 那次 5.2 秒成功之后 5 秒的建筑采样窗里**,
是 **5 秒采样率的合并假阳**,不是判据出错 —— 据实登记,不消掉。

### 4.2 逐帧推翻量具之一:**channel 必须按施法者配对,不许用一个全局槽**

首版用一个全局"未闭合槽"配 `MODIFIER_ADD/REMOVE`。两个英雄同时抢塔时,
它把 `ADD(a) ADD(b) REMOVE(a) REMOVE(b)` 读成**一次**尝试并**丢掉另一次**。
改成按 actor 配对后,尝试数 52 → **53**、完成数 12 → **13**。
**方向要记住:这个缺陷不制造发现,它压制发现**(它丢的是真尝试)。

### 4.3 逐帧推翻量具之二:**帧轨迹按英雄名过滤是错的,而且错得无声**

首版 `hero_track` 直接在 `snapshots` 上按 `hero == 'npc_dota_hero_luna'` 过滤。
`20260905_010205_slot7` **t=1348.5 一个时刻就有 21 行 luna** ——
1 行活人(hp_pct 1.00)+ 20 行尸体/重复实体流(0.00),
**打印出来每秒二十行幽灵,而读者会挑排在前面的那一行**。
仓库里**早就有正确的东西**:`entities.frames_by_hero`(它的 docstring 钉的
就是 2026-08-25 那个 lina 三实体流的案例)。
⇒ 改走它。**顺带第二个坑**:它按 **canon 名**(`luna`)建键,
用 `npc_dota_hero_luna` 去查**返回空表**,而**空轨迹长得跟"这个英雄不在场"
一模一样**。两条都钉成了 liveness pin(4g / 4h)与变异体(M7)。
