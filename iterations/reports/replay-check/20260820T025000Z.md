## 4. 逐帧:偏斜的真实机制(结论在这一节)

### 4.1 更强、更原始的观测量:大招根本没放

不是「攥着大招死」,而是**候选侧的 OD 整局几乎不放大招**:

| 局 | 种子 | OD 角色 | 真实 Sanity's Eclipse 施法次数 | OD 死亡数 |
|---|---|---|---|---|
| `_222030_slot1` | 867 | **ARMED** | **0** | 2 |
| `_222559_slot1` | 867 | **ARMED** | **0** | 2 |
| `_223055_slot1` | 868 | **ARMED** | **0** | 3 |
| `_223607_slot1` | 868 | **ARMED** | **1** | 3 |
| `_223128_slot1` | 867 | BASE | 2 | 3 |
| `_223642_slot1` | 867 | BASE | 2 | 2 |
| `_222014_slot1` | 868 | BASE | 1 | 1 |
| `_222526_slot1` | 868 | BASE | 2 | 1 |

**armed 1 次 / 4 局 vs baseline 7 次 / 4 局**(binom p=0.070),**2/2 种子同号**。
机会帧(大招已学 + cd=0 + 蓝 ≥400 + 敌方英雄在 600u 内,6s 去重):
**armed 33 vs baseline 18** —— **候选侧机会反而是基线的近两倍**,
每机会施法率 **3.0% vs 27.8%(Fisher p=0.017)**。
(「机会更多、转化更低」与 #41 同形,**n 本身是症状**。)

### 4.2 把门拆开:差异全在一条子句上

`X.ConsiderSanitysEclipse`(`hero_obsidian_destroyer.lua:442`)有两条可离线判定的子句。
逐帧重放(工具已提交,见 §7):

| 子句 | ARMED | BASE | 显著性 |
|---|---|---|---|
| 队友人数 parity(`#allies(bot,1200) >= #allies(target,1200)`) | **27/33 (82%)** | **15/18 (83%)** | Fisher **p=1.00** |
| 致命性 `J.CanKillTarget(base+|Δmana|*mult)` | **8/33 (24%)** | **12/18 (67%)** | Fisher **p=0.006** |
| 两条都开 → 真的放了 | 1/6 | 5/11 | Fisher p=0.33(**不显著**) |

(致命性一列取三组参数中最宽松的 base=450/mult=0.8;
`base_damage`/`damage_multiplier` 的真值不在录像里,三组参数
(250,0.6)/(350,0.7)/(450,0.8) 的 `lethal_ok` 分别是 armed 6/12/24% vs base 44/56/67%
—— **方向和量级在整个参数区间内稳定**,故不依赖参数猜测。)

**这是本轮最重要的一行:parity 子句 p=1.00,完全没有差异。**
「守卫子句把人数数错」那一族(#21 的低血追击案、`lanefix` 的教训)在这里**被排除**。

### 4.3 那条有差异的子句,差异从哪来

致命性子句 = `估计伤害 >= 目标当前 HP`。逐机会帧取分量中位数:

| 分量 | OD-armed 的机会帧 | OD-baseline 的机会帧 |
|---|---|---|
| **目标当前 HP** | **868** | **500** |
| OD 自己的净值 | **4071** | **5515** |
| OD 蓝量 | 1012 | 1016 |
| 蓝量差 \|Δmana\| | 492 | 635 |
| 机会发生时刻 | 497s | 442s |

OD 的蓝量两侧一样(1012 vs 1016)。差的是**它面前那个敌人的血条**:
中位 868 vs 500。**OD-armed 面对的是 baseline 阵营(更肥),OD-baseline 面对的是
armed 阵营(更穷)** —— 这正是已知的候选侧 −27/−33 gpm 经济赤字本身。
换句话说:**执行门在候选侧更少打开,是因为它要处决的那个人更厚,不是因为 OD 更犹豫。**

**运动学撤退代理(本轮首次实现,答上一轮 22:36Z 留的欠账)**:
机会帧后 3s 内向自家泉水净位移 >150u 的比例 **armed 27.3% vs baseline 27.8%** ——
**完全持平**。「armed id 把 OD 顶进 RETREAT ⇒ `J.IsGoingOnSomeone` 为假 ⇒ 大招整条关掉」
这个假说**得不到支持**,不采信。

## 6. 诚实边界(照抄进 #54,别让下游过度解读)

1. **`J.IsGoingOnSomeone` 不在 `.dem` 里**(与 `J.IsRetreating` 同类,22:36Z 已记录的结构性
   边界)⇒ §4/§5 的所有机会计数都是真实可触发集的**超集**。§4.3 的运动学代理是我能做到的
   最好替代,它给出的答案是「两侧持平」,但它**不等于**读到了 mode。
2. **`J.CanKillTarget` 走引擎的 `GetActualIncomingDamage`**,我用
   `0.75 × (base + |Δmana| × mult)` 近似(25% 基础魔抗),且两个 special value 不在录像里。
   §4.2 用了三组参数做敏感性,**任何单一参数下的「门开了却没放」都不能当作已证的漏放**。
   §5 的立论**不依赖**这个近似 —— 它靠的是代码形状 + 施法次数 + 死亡数。
3. **多敌 AoE 浪费只有 n=4**(≥2 个敌人在 500u 内且大招就绪的 episode:armed 4、baseline 0、
   合计 0 次施法)。方向对得上 §5,但**样本太小,本轮不作判据**,只作为 §5 的旁证登记。
4. §4.3 的「敌人更厚 ⇒ 门更少开」链条本身是**相关**证据(镜像同阵容 + 分量中位数),
   不是因果实验;但它与 parity 子句 p=1.00 合起来,足以**排除**「守卫数错人」这一族解释。
