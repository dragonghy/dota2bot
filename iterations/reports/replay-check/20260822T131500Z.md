## 2. 核验结论

### 2.0 判据:域怎么定的(先说清楚,再报数)

`J.ShouldCreepPullLane`(`jmz_func.lua:6698`)+ `J.IsCreepPullSafe`(`:6212`)+
调用点 `mode_roam_generic.lua:94`(动作在 `:185`)。逐条搬到离线:

| 源码子句 | 离线判据 | 可观测? |
|---|---|---|
| `DotaTime() > 6*60 -> nil` | `0 < t <= 360` | ✅ |
| `J.GetHP(bot) < 0.5 -> nil` | `hp_pct >= 0.50` | ✅ |
| `IsCreepPullSafe`:`1<=nNear(1000)<=2`、`nWide(1800)==nNear` | 同(idx 锁后的存活敌方英雄) | ✅ |
| `GetNearbyLaneCreeps(900, true)` 非空 | creeps 流(3s 采样)+ **1.6s 陈旧上限** | ✅ |
| 目标环:敌方英雄 ≤1000 且 ≤500 邻接敌方兵 | 同 | ✅ |
| `not WasRecentlyDamagedByAnyHero(2.0)` | 战斗日志里 2s 内无 hero→bot 的 DAMAGE | ✅(见下) |
| `J.IsCore(bot)` | `analysis.json:team_slot % 5 + 1 <= 3` | ✅(见下) |
| `bWavePushedToUs`(`GetLaneFrontAmount` 之差) | 900 内敌方兵质心**离我方远古更近** | ⚠️ 保守代理 |
| `bZoned`(`not J.WeAreStronger`) | 不可观测 | ❌ |

两条纪律性更正,登记备查:

1. **`WasRecentlyDamagedByAnyHero` 不再是「捕获缺口」。** 章程末节把它列在
   「已知捕获缺口」里,但那说的是**引擎读数**;战斗日志逐条带 hero→hero 的 `DAMAGE`,
   **谓词本身可以逐字重建**(唯一欠修正:英雄召唤物的伤害也会置引擎的标志位而这里不算
   ⇒ 我的域仍是**超集**,只会少判 SILENT,不会多判)。本轮它是 STRICT 域的承重子句之一。
2. **`team_slot % 5 + 1` 这次是从源码推出来的,不再只是「与 `player_id` 对拍过」。**
   `J.IsCore` → `J.GetPosition` → `aba_role.GetPosition` → `RoleAssignment[team][i+1]`,
   而 `aba_role.lua:13-28` 的 `RoleAssignment` 两队**都是 `{1,2,3,4,5,1,2,…}` 的恒等映射**,
   索引就是 `GetTeamPlayers` 里的队内次序 ⇒ **代理与源码同构**(前置:`HeroPositions[playerId]`
   未被 hero_selection 覆盖)。副产品:本波里 `crystal_maiden` 读作 pos2 **不是 bug**,
   是这套随机镜像抽签下真实的位置分配。

**三档域**(从松到紧,一律**超集**,只会少判不会多判):
`DOMAIN` = 上表全部可观测的安全/几何子句;
`STRICT` = `DOMAIN` + core + **恰好 1 个** 1000 内敌人 + 2s 内没被英雄打过;
`FORCED` = `STRICT` + 敌方兵在**我方半场**(⇒ `bWavePushedToUs` 为真,
`bZoned` 那条析取项因此不再承重)。

**执行签名**(1Hz 下动作长什么样):`DRAG`(3s 内朝自家泉水方向的位移投影 ≥200u,
且末帧仍有敌人 ≤1400)+ `POKE`(同期对目标英雄造成伤害)= `PULL`。

### 2.1 `creeppull`: **WORKING(倾向)** —— 二分装置说话,不是单帧说话

**先说为什么单看 19-id 那一波不够。** 19-id 波单波读数如下(131 局):

| 域 | 候选侧(armed) | 基线侧 | delta | 局级置换 SD / p |
|---|---|---|---|---|
| STRICT | 461 / 4989 = **9.24%** | 348 / 6019 = 5.78% | **+3.46pp** | 0.72pp / p<0.0001 |
| FORCED | 209 / 2898 = **7.21%** | 182 / 3357 = 5.42% | **+1.79pp** | 0.78pp / p=0.0204 |

**这个读数本身不可归因**:批测台 §2.2 必查项 ⑤ 已事先登记「19-id 全集波是合成效应」,
而且同波 armed 的 `capmono`(登记在案的效应就是「域内 retreat 率」)、`ownhalf`、`overchase`
都能造出「敌人在近处时往回走」的形状。**形状不是指纹**(章程 08-21T22:05Z 丙)。

**免费的二分装置。** 08:10Z 那波的 armed 串是**同样 18 个 id、恰好少 `creeppull`**,
四个种子相同(888/895/896/906),侧别 8/8 平衡。于是:

| 域 | | 候选侧 | 基线侧 | 该臂 leg-delta |
|---|---|---|---|---|
| STRICT | 臂 A(19id,creeppull **armed**) | 461/4989 = **9.24%** | 348/6019 = 5.78% | **+3.46pp**(SD 0.72) |
| | 臂 B(18id,**无** creeppull) | 35/637 = **5.49%** | 58/970 = 5.98% | **−0.48pp**(SD 1.49) |
| | **ARMED A−B = +3.75pp** | **NULL A−B = −0.20pp** | **DiD = +3.94pp** | **合成 SD 1.65pp,\|t\| = 2.38** |
| FORCED | 臂 A | 209/2898 = 7.21% | 182/3357 = 5.42% | +1.79pp(SD 0.78) |
| | 臂 B | 19/321 = 5.92% | 17/551 = 3.09% | +2.83pp(SD 1.52) |
| | **ARMED A−B = +1.29pp** | **NULL A−B = +2.34pp** | **DiD = −1.04pp** | 合成 SD 1.71pp,\|t\| = 0.61 |

恒等式守卫通过(`(Aa−Ab)−(Ba−Bb)` 与 `(Aa−Ba)−(Ab−Bb)` 浮点逐位相等)。

**按章程 §AG.1 的口径逐项读**:

- **STRICT 是承重通道**:NULL(两条**出厂代码**基线腿,跨 `12ef3de`→`19b90b9` 两棵树)
  读 **−0.20pp**,几乎是认证零 ⇒ DiD 的 +3.94pp **全部来自 ARMED 那一项**,
  没有一段「没有代码解释的基线腿落差」。顺带回答批测台 12:10Z 传下来的第 1 条
  (「基线腿跨树不是常量」):**在这个行为指标上,跨这两棵树的漂移 ≤0.2pp**。
- **NULL 通道同时控住的不只是「树」。** 两臂还差着 **`--rec-slots` 8 vs 1**,而批测台
  12:10Z 自己测过录制的时标代价(`timescale ≈ 0.01044*slot + 1.7955`)⇒ 时标不同、
  引擎每帧预算不同,原则上能改变 bot 行为;两臂的**语料负载、机型、树**也都不同。
  **这些全是波次级差异,而两条基线腿各自来自本波** ⇒ 它们**整体**落在 NULL 里。
  NULL 读 −0.20pp,因此这一整族混淆在本指标上**合计 ≤0.2pp**。
  (这也正是这里必须用 DiD 而不是直接比两条候选腿的原因。)
- **FORCED 这一列本轮不可判**:NULL 读 **+2.34pp,比效应还大**,臂 B 的 FORCED 候选侧
  只有 **321 帧 / 19 次事件**。按 08-22T08:50Z 那条(「同一扫描里不同阈值的列统计性质不同,
  要写明哪一列承重」):**承重的是 STRICT,FORCED 只作方向参考,两列不可一起引用。**
- ⭐ **归因问题被臂 B 自己解决了**:臂 B 的候选侧(18 个 id 全 armed,含 `capmono`/
  `ownhalf`/`overchase`)在 STRICT 域上读 **5.49%,反而低于它自己的基线腿 5.98%**
  ⇒ **那 18 个 id 合起来不制造这个签名**;把 `creeppull` 加进去才跳到 9.24%。
  这正是我在单波读数时担心的 `capmono` 混淆,**实测排除**。

## 3. 工具坑(本轮新踩,建议进章程)

- **⭐ 位移分类器的 TP 排除必须带一个采样间隔的「落地尾巴」。**
  章程 08-21 那条「`modifier_teleporting` 读条帧不是决策帧」我照做了(用
  `capmono_refusal.tp_channel_spans` 的同形实现),**照样漏**:
  `20260822_103347_slot4` 的 crystal_maiden 在 **135.1 就 `MODIFIER_REMOVE modifier_teleporting`**,
  而快照 **135.4 仍是 TP 前的坐标,136.4 才出现落点** ⇒ 区间 `[ADD, REMOVE]` 与
  `[135.4, 138.4]` 这个窗口**不相交**,一条 **10,060u 的「拖拽」**就这么进了结论。
  **落地比频道结束晚一拍**(dumper 只在下一次采样才网络化新位置)。
  修法:`clean_window` 里给 span 末端加 `TP_TAIL = 1.5s`。
  抓住它的是**物理上界守卫**(3s × 550 u/s = 1650u),不是眼睛 ——
  **凡按位移分类的检测器都该带一条这样的守卫,它比事后看排行榜便宜得多。**
- **`--selfcheck` 的先验写错了会伪装成数据错。** 第一版写「两泉水相距 8000–12000u」,
  真值 **18,877u**(16k 地图的两个对角出生点),于是健康数据被判 FAIL。
  **几何先验要现算一遍再写死**;现在这条改成 17k–21k **并配正控**
  (每队质心必须落在**自己的**远古 2500u 内且比对方远古近,实测 r=1469 / d=2000)。
- **每队进入快照流的第一帧不是同一个 t。** 本波 radiant 从 `t=−67`、dire 从 `t=−63` 起,
  拿全局 `t0+3` 当窗口算泉水质心,会**只算出一队**(另一队直接缺项,`len(fs)!=2`)。
  **逐队各算各的起始帧。**
- **免费的二分装置就躺在归档里。** 「上一波 armed 串是这一波少一个 id」在多-id 全集
  节奏下**经常成立**(本轮 18→19),而它把「合成效应不可归因」直接变成可归因,
  代价只是 16 局的 dumper 时间。**每次拿到全集波读数,先 `diff` 一下前一波的 cand 串。**
- **本容器可以装 `lua5.1`**(`apt-get install -y lua5.1`,本轮实测可用)。
  过去几轮报告里「本容器未装 lua5.1 ⇒ 铁律 6 无适用对象」的写法,**从今天起不成立**;
  该跑就跑。(`luacheck` 未试,本轮无 Lua 改动。)
