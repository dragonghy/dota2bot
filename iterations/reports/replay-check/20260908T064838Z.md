## 四、⭐ GH #609 验收 (2) 在 W55 变红,而根因两条都在**阈值那个量**上

```
misfiled by threshold 5.8: 0 called complete without a flip, 3 called aborted that flipped
of those, multi-caster groups: 3  (GH #609 acceptance (2): must be 0)
  MULTI-CASTER MISFILE North t=1189.3 cs=5.8 n=2 jakiro,ogre_magi
  MULTI-CASTER MISFILE North t=1162.6 cs=5.8 n=2 ogre_magi,obsidian_destroyer
  MULTI-CASTER MISFILE North t=1449.6 cs=5.8 n=2 luna,zuus
```

上一轮 W52 上这个数是 0,本轮 W55 是 3。**逐帧查下去,两条根因都不是配对规则:**

**(甲) 二进制浮点。** 三组的 `caster_s` 打印成 `5.8`,真值是

```
caster_s = 5.7999999999999545     >= 5.8  ->  False
```

`caster_s` 是把 0.1 秒的片段累加出来的,**真值恰好等于阈值的那一组,必然落在阈值下方**
(差 4.5e-14)。⇒ **阈值判据在它自己的调参点上是坏的**,而四轮阈值狩猎的夹逼区间
`[5.8, 5.9]` 的左端点**正是这个点**。W52 上之所以是 0,只是那 98 组里没有一组恰好落在 5.8。

**(乙) 0.0 秒的「施法者」。** 三组的第二名成员分别只有 0.1s / 0.0s / 0.0s:

```
att jakiro    North 1183.6-1189.3  5.7s rmv=0
att ogre_magi North 1189.2-1189.3  0.1s rmv=0     ← 帧轨:ogre_magi 到 1189.5 才进 140u

att ogre_magi North 1156.8-1162.6  5.8s rmv=0
att obsidian_destroyer North 1162.6-1162.6 0.0s rmv=0  ← 帧轨:OD 最近只到 255u,从未进 140u

att luna North 1443.8-1449.6  5.8s rmv=0
att zuus North 1449.6-1449.6  0.0s rmv=0          ← 帧轨:zuus 1449.5 到 145u,正好那一帧
```

条填满的那一帧,引擎给半径内**刚起手**的英雄补一对 `MODIFIER_ADD` + `MODIFIER_REMOVE(value=0)`,
时间戳同帧。⇒ 这三组**不是"两人合力填条"**,是**一个人填完条 + 一个蹭到判决的搭车者**。
把它们叫 `n=2` 的多施法者组,是**分组规则忠实地记录了引擎发生的事**;
真正错的是**拿 caster-seconds 当完成判据**——它把一个 5.7 秒的单人占领
加上 0.1 秒的搭车者,凑成一个刚好落在阈值下方的和。

**⇒ 给 #609 的建议不变,而且现在有了机制层面的理由(不只是"尺子刻度 0.1s"):**
**把 caster-second 阈值降级为纯叙述量,验收 (2) 改挂在判据上。**
判据在这 3 组上读作 `rmv=0,0` → 完成 → 与三次易主(t=1194.5 / 1165.4 / 1454.5)一致,**3/3 正确**。
