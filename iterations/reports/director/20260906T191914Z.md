## ⭐ GH #548 第五个读数(欠五轮,本轮结清)—— 是集合长了,不是容器慢

240s 上限下 `rc=124`(我的 timeout);**拿掉上限**后进程跑到**自然结束**
(19:19:14 → 19:23:09,~235s),仍然 **`GH548_RC=2`**,
`49 checks, 0 failures, 9 uncertified`。
⇒ 那 9 条不是被外层 timeout 砍的,是**这条腿自己的 `budget 120s`** 砍的。
**外层上限多大都一样。**

```
NOTE 5a0 cost: 84 file(s) [discovered] in 120.1s (budget 120s)
     -- two numbers on purpose: set size and container speed move independently
49 checks, 0 failures, 9 uncertified   /   UNCERTIFIABLE -- this is NOT a pass.
```

⭐ **那条 NOTE 的两个数字正是为这一刻写的,而它们现在分开了。**
issue 里带的历史读数是 **50 个文件**(本容器 99.5s / 批测台 133.3s,GH #358)。
**今天是 84 个。** ⇒ 五轮悬案有答案:**集合长了,50 → 84(+68%)**。
容器速度解释不了它 —— 133.3s/50 是**同一集合在更慢机器**上,同一量级;
**84 个文件在 120s 预算下没有任何容器能跑完。**

**独立佐证(不靠腿自己报的数)**:按 `routine_selfcheck.sh:527-531` 的发现式手数,
`grep -l '\[detector\]\|\[ratchet\]' tests/test_*.lua | wc -l` = **80**,
加四个点名文件(`sort -u`)= **84**,与腿报的 `84 file(s)` **逐位相同**。

**边界(诚实范围)**:本次跑与 `test_smoke_load.lua` **有过短暂并发** ⇒
**墙钟那一侧我不当作干净读数**;但**文件数是结构量,与并发无关**且已被独立 grep 佐证,
⇒ **结论只压在文件数上,不压在 120.1s 上**。`0 failures` = 这条腿本身没发现缺陷,只是没跑完。

修法三条路(**不在本轮拍板**,已写进 #548):抬预算(常数对单调增长的量,只是推迟)/
