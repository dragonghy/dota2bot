## 1. `[bug] #29` 已修复并关闭 — retreat guard 链优先级倒挂

### 缺陷

`bots/mode_retreat_generic.lua` 的 `GetDesireHelper()` 是「先命中先 return」,
但两条**故意设成更高优先级**的 guard 被排在一堆 `HIGH`(0.75)分支**下面**:

| guard | gate | 返回 | 旧位置 |
|---|---|---|---|
| `J.ShouldAbortDeepSoloPush` | `pushguard` | **0.92** | 8 条 HIGH 之下 |
| `J.ShouldAbandonTpChannel` | `tpwatch` | **VERYHIGH (0.9)** | 3 条 HIGH 之下 |

只要上面任何一条 HIGH 先为真,函数就带着 0.75 返回,这两条**永远不被求值**。

issue 只报了 `tpwatch` 一条。修的时候发现 **`pushguard` 这一处更严重**:
0.92 这个值在 20260723 的 C 组诊断里是**专门挑出来压过追杀 desire 的**
(注释原文「HIGH (0.75) LOST the desire auction to the chase that was killing
the bot」)——为解决「HIGH 压不住追杀」而选的值,自己被 HIGH 遮蔽了。只按
issue 的最小提议改会留下这一条。

### 改法

整条链**按 desire 降序重排**,并用 `=== RETREAT GUARD CHAIN: BEGIN/END ===`
标记围起来 + 写明不变量:

```
pushguard  0.92
tpwatch    VERYHIGH (0.90)
nodive / lf_chase / l1xpsoak / lanesurv / l1kite / midguard /
lf_revive / lf_threat / deathzone / teamfight-idle    全 HIGH (0.75)
```

纯重排,没动任何 helper 逻辑。**没有选「收集所有为真分支取 math.max」那个
方案**:那会让每帧多求值一批 helper,而其中至少 `ShouldCounterTradeKite` 带
副作用(`bot.laneKiteUntil = DotaTime() + 2.0`),`ShouldXpSoakLane` 带滞回
状态——为修一个顺序问题引入一堆新的求值时机变化,不划算。重排拿到同样的
正确性,风险面小得多。

**已发布默认行为不变**:链里除 `lanesurv` 外全部 soak-candidate gated、真实
对局 inert;被上提的两条都是 gated,全 gate 关闭时链的行为逐字不变;
`lanesurv` 与所有可能同帧触发的 guard 的相对位置也未变。

### 验收:源码级不变量测试 + 变异测试

issue 建议钉「`l1xpsoak`+`tpwatch` 同时 armed」的真实帧 fixture。**没这么做,
理由写在 issue 和 state.json 里**:(a) 录像组自己确认当前语料没有这种帧;
(b) 更本质——一个 fixture 只能证明它恰好触发的**那一对** guard 的顺序,而
需要的不变量对**每一对**成立,包括未来新增的 guard。

`tests/test_retreat_priority_order.lua`(3 个测试):解析标记之间的 guard 返回
值,断言**按源码顺序 desire 非递增**(NONE 是硬否决不是 floor,豁免),外加
一条针对本 issue 的回归钉(任何 HIGH 必须排在 tpwatch/pushguard 之后)。

**做了变异测试**(不是「写完就绿」):把 tpwatch 块挪回原位 → 3 挂 2,报错
直指缺陷本身;挪回来 → 全绿。

验证:`luacheck bots game` **0 警告**;`lua5.1 tests/run_tests.lua`
**389 tests, 0 failures**(本轮 +3)。容器初始无 Lua 工具链,已 apt 装
`lua5.1` + luarocks 装 `luacheck` 后再跑。

### 对历史数据判读的影响(重要,已写进 test_set.md + state.json)

14-id 全集那一波 `tpwatch` 与 `l1xpsoak`/`lf_chase` **同时 armed**,在旧链上
彼此改变对方的生效行为 —— **那一波违反了「一次只变一个量」的隐含前提**。
这是 `-34.59` 的一个**结构性候选解释**(不是断言祸首;`lf_rescue` 的嫌疑仍
在)。今后同一条 guard 链上多个 id 同时 armed 时都要意识到这层耦合。

## 2. `l1xpsoak` 处置裁定:移出 armed 集(退回协同组,非 reject)

依据录像组 06:45Z 报告(solo 波次 855-858,12/12 镜像局宽扫,6 局深查)与
issue #28。核验结论是 **SILENT / 不可区分**,且——这是关键——**不是样本量
问题**:

- 唯一消费点把 `ShouldXpSoakLane` 返回的**锚点 Vector 直接丢弃**,只判
  `~= nil`,然后返回和 `lanesurv` 同一个 `HIGH`。20260819 重设计的核心卖点
  (绝对锚,防死亡行军漂移)在消费端根本没接上,只剩滞回状态位的作用;
- 入场条件是**已 promote、默认开**的 `lanesurv` 的真子集(1200/≥2 敌 vs
  1100/≥1 敌,同 3.0s 窗口、同 `HP*0.75` 阈值),335 个 episode 里 **97.3%
  两者逐位同判**,9 个独占帧(2.7%)逐帧还原**无一**有可归因的行为差异。

条件 (a) 在当前设计下**结构上无法证明**,继续加局也没用 → 按章程「核验不
成立 → 退回对应组」。`test_set.md` armed 集 **13 → 12 id**,历史行已留。
重新入集路径写进 #28(要么让锚点真的驱动行为、可观测地区别于 `lanesurv`,
要么取消独立 id 把滞回收进 `lanesurv` 参数;我倾向后者并说明了理由,但把
设计决定留给协同组)。

## 3. 本轮的一条主动发明:把 855-858 这一波变成**噪声底校准**

批测台已经启动的这一波,按上面的结论对 `l1xpsoak` 是「读数即噪声」——但正
因为如此,它是一份**免费的经验零点**:候选侧和基线侧在 97.3% 的入场帧上跑的
是同一条规则,所以它的 per-seed gpm delta 的离散度,估的就是**镜像 draft
harness 在真实效应为零时的噪声分布**。

我们从来没有测过这个零点。它直接决定 `-34.59` 该给多大的证据权重:零点本身
能漂 ±30,和零点稳在 ±5 以内,是完全不同的两个结论——而 CLAUDE.md 里
「econ A/B 是噪声受限」这条硬教训,至今用的还是 random-draft 时代的 SD≈600
估计,不是当前 mirrored-draft harness 的数。

已在 `test_set.md` 给批测台留了具体请求:收割时除照常出 verdict 外,单独记
一行 4 个种子 per-seed gpm delta 的**均值 + 离散度**,标注
`null-calibration, l1xpsoak solo, 候选≈基线`。**不额外花钱,数据已经在跑。**
