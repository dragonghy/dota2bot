## 2. 缺陷:验收世界不是"拒绝回答",是**答错**

`mock/bot_api.lua` 把未指定的 `GetPlayerID` 默认成 **0**,loader 的
`GetTeamPlayers` 又只返回**裸下标 `1..N`**。`aba_role.GetPosition` 的匹配是
`heroID[i] == bot:GetPlayerID()` ⇒ **永不成立**,五个人一起掉进同一条兜底,
于是 **`J.IsCore(任意友军) == true`,在全部 61 个 fixture 里**。
`J.IsCore(bot) = J.GetPosition(bot) <= 3` —— 凡是分叉在 core/support 上的断言,
**判它的是 harness 不是那一帧**。

第二层(英雄组没量的):`GetTeamPlayers`/`GetTeamMember` 以前都建在**只算活人**
的列表上,而引擎的这两个读法是**花名册**(阵亡成员照报)。所以**每死一个队友,
全队的角色就整体错位一格** —— 即便 id 修对了,这一层不修仍会给出错答案。

## 3. 修复(三段,全部端到端验过)

### 3.1 dumper 出 `player_id` —— 并踩到一个真实的编码坑

`m_iPlayerID` 在实体上确实存在,但 **`GetInt32` 取不到**:它以**无符号**字段
到达,而且**仍带着 protobuf 的 zigzag 编码** —— 10 人局的原始值是
**0,2,4,…,18**。第一版按 `GetInt32` 写,跑真录像出来 **8025 个快照全是 -1**
(没有静默填 0,是因为我把"没网络到"显式定成 -1),这才发现。
改成 `GetUint32` + 解 zigzag。

**地面真值 10/10**:`raw/2` == 该局 `analysis.json` 的 `team_slot`(Dire +5),
局 `20260819_221200_slot1`(lina 0 / crystal_maiden 1 / dragon_knight 2 /
juggernaut 3 / obsidian_destroyer 4;dire 5-9)。**不是推断,是逐个对表**。

### 3.2 `make_fixture.py` 透传 + loader 建真花名册

- 生成器写 `units[].player_id`;**dump 里没有这个字段时整段省略**,老 fixture
  拿到的仍是 loader 的旧世界,而不是一个**捏造的槽位**。
- loader:`GetTeamPlayers`/`GetTeamMember` 走**按槽位排序、含阵亡成员**的花名册;
  `GetUnitList(ALLIED_HEROES)` **仍是活着的单位** —— 这正是引擎自己的分法。
  没有 `player_id` 的 fixture **逐字节走旧路径**。

### 3.3 护栏 `tests/test_fixture_roles.lua`(5 例)

锚点是**真实帧** `f_221200_od_roles.lua`(本轮从真录像新生成,该局 t=300,
**两名友军已阵亡** —— 正好证明花名册必须报满 5 人):

1. 花名册报满 5 人、id 是引擎的、`GetTeamPlayers` 与 `GetTeamMember` 逐项对齐,
   且这一帧确实有 2 个阵亡友军(**锚点防退化自检**);
2. `J.GetPosition` / `J.IsCore` 逐人对地面真值,并断言**五个位置互不相同**
   (`#53` 的症状本身);
3. **两侧都可达**(pos 1 必须是核心、pos 5 必须不是)—— 防止断言烂成恒真;
4. **棘轮**:62 个老 fixture 显式列名,重新 dump 过的必须删名,新 fixture 不带
   id 立刻红;
5. **特征化**:老 fixture 仍答"全员 pos 1",并写明这是**已知错答案**、不是背书 ——
   兜底一变,老语料上的结论就要重读。
