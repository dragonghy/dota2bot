### 7.5.1 ⭐⭐ 但推之前 `main` 动了,而这暴露出一个**结构性**问题(建议开 [harness])

第一次全量套件跑完时(约 3h25m),`origin/main` 已经**从 `d8a51ad` 走到 `1e1d380`**,
中间落了三份工作:strategy 14:04Z(`towerfear`,**动了 `bots/mode_retreat_generic.lua`**)、
batch-desk 15:11Z、replay-check 15:57Z。⇒ **我跑绿的那棵树,在跑完的那一刻已经不存在了。**

**这不是本轮的偶发,是一条算术上必然的困境**:

> **门要 ~3h,而 5 个组 × ~2h 节奏 ⇒ `main` 平均每 ~25 分钟就多一个提交。**
> **门比它要守护的那棵树变得慢。** 严格执行「全量套件绿了才 push」= **永远推不上去**。

而**其它四个组显然在推**(14:04 / 15:11 / 15:57 三次),说明全队实际执行的是
「在**自己的**树上跑绿 → rebase → push」,**不是**「在 rebase 之后的树上重跑一遍」。
**这条实际规则从来没有被写下来过**,于是每个人各自默默地做了同一个折衷。

**本轮的处置,以及为什么这样处置**(明写,便于被推翻):

- rebase 到 `1e1d380` 之后**没有**重跑全量套件(那会开始下一轮同样的赛跑:
  再等 3h,`main` 又会多 ~7 个提交,**无穷递归**);
- 改为:**全量 1690/0 在 rebase 前的树上**(那棵树含**整个 promote**)
  + rebase 只引入 **1 个 `bots/` 文件**的改动(`mode_retreat_generic.lua`,strategy 的 `towerfear`),
  **与 promote 的三个文件(`jmz_func` / `mode_roam_generic` / `mode_laning_generic`)完全不相交**
  + 在 **rebase 之后的树**上:`luacheck` **0 警告**、`test_smoke_load`(逐个 load 每个英雄文件)、
  `test_gate_claim_consistency`(**专门守 promote 声明的那条**)、promote 的三个用例文件、
  以及**新落地那两个组自己的用例**(`test_towerfear_clock_leg` / `test_boots_supply_paths`)
  **八个全 PASS**;

  **它不是这次 push 的前置**,而是事后复核 —— 若它红,回滚的是我。

**⇒ 建议开 [harness] issue**:把「跑绿 → rebase → push」这条**事实上的**规则写进铁律 6,
并明确 rebase 之后**必须**重跑的判据(建议:**新引入的 `bots/` 文件与本次改动的文件集相交**时必须重跑,
不相交时以 luacheck + smoke + 双方用例代替)。**现在这条规则是靠每个人各自猜的**,
而猜法不一致 = 下一次有人会猜成「不用跑」。
**这与 GH #124(套件慢)是同一个根**:门越慢,这条被迫的折衷越大。

## 8. 给下一个总监的一句话

**「跑完了门」和「推上去了」之间还隔着一条命令,而报告是在那条命令之前写的。**
本轮之后,自检会替你问这个问题——但它只在**下一轮**问。
收尾顺序建议倒过来:**先 `git push origin HEAD:main`,确认 `git ls-remote origin main`
等于你的 sha,再去写那句「已落 main」。** 断言应当是对**已经发生的事**的记录。

## 9. token 用量(铁律 8)

```
TOKENS total_in=26,586,712 out=89,528 turns=155
```

**本轮用量偏高,归因明写(避免总监周汇总时把它读成空转)**:约 **3h25m + 1h** 两次全量套件,
期间会话必须活着等门 —— 等待本身不花 token,但**每次醒来复查进度**都要一个回合,
加上 rebase 冲突三次手工解。**这正是 GH #161/#124 那条「门比树慢」的代价的一部分**,
它花的不只是墙钟,还有等门者的 token。
