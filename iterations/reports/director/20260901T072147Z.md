## 1. GH #380 [harness] —— 开工自检的 python 腿**把诊断信息扔掉了**

### 1.1 现场

开轮的自检打出的**全部**内容:

```
FAIL  tests/test_rc_wrapper.py
71 passed, 1 failed, 1 uncertifiable
failed: tests/test_rc_wrapper.py
TRUNK RED -- a python test is failing ON THE WORKING TREE.
```

工作树是干净的(`git status` 只有本轮自己的改动之前的空),所以这读作 main 红。
去查:

- `python3 tests/test_rc_wrapper.py` **单独跑 exit 0,33/33 全 ok**;
- 紧接着第二次 `bash tests/run_py_tests.sh` ⇒ **`72 passed, 0 failed`**;
- 循环**单独跑 30 次:0 失败**。

⇒ **这是一次间歇性红**,而**唯一一份证据已经没了**。
**重跑不是补救** —— 一个复现不了的 flake,证据只有那一份。

### 1.2 根因

`tests/run_py_tests.sh` 特意捕获每个失败测试自己的输出、**缩进六个空格**打出来
(`sed 's/^/      /'`)。而这条腿是这样把它交给读者的:

```sh
printf '%s\n' "$suite" | grep -E '^(FAIL|failed:|[0-9]+ passed)' || true
```

`^` 锚定 ⇒ **每一条缩进行都被丢掉**。runner 费劲存下来并打出的东西,这条腿扔了。

**为什么这不是装修。** 这条腿已经因为**说错话**修过两次 —— #243(could-not-run 被报成
TRUNK RED)、#267(手工归因)。两次之后**横幅是对的**。两次都没碰
「读者能不能知道**为什么**」。而这条腿**自己的注释**写着:
*a false TRUNK RED is what teaches people to ignore the line*。
**一个没法诊断的红,对读者就是一个假红** —— 信任代价一样,只是机制不同。

### 1.3 同一份输出里的第二个缺陷

那次运行**既红又有 uncertifiable**(`71 passed, 1 failed, 1 uncertifiable`),
而 exit-1 分支的 grep **没有 `uncertifiable:` 这一项**(exit-2 分支有)。
⇒ **报告更坏那棵树的分支,反而少说了一件出问题的事**:没跑成的文件无人点名。

### 1.4 处方

1. 两条非绿分支都打印 runner 的缩进详情(上限 40 行,超出显式标注截断);
2. exit-1 分支的过滤器加入 `UNCERTIFIABLE|uncertifiable:`;
3. 完整输出写到 **`$TMPDIR` 下**的日志、路径打在 stdout(`PY_LOG:`),
   沿用 `rc.sh` 的 RC_LOG 惯例:**打出来的是视图,日志才是数据**。
   **写在树外是有意的** —— 这条腿上面那段「刻意不 auto-stash」的注释,
   保的就是「自检永不改动工作树」,新代码不能把它破掉(用例 7a 钉这一条);
4. 绿路径**完全不变**:不打详情、不写日志、不打横幅、仍 exit 0。

### 1.5 验收

新增 `tests/test_selfcheck_py_leg.py`,**26 检查全绿**。按
`test_selfcheck_lua_leg.py` 的办法把腿**原样从脚本里切出来**、喂一个桩 runner ⇒
**秒级**,不像 Lua 腿端到端要两分钟(GH #358,见 1.6)。

**变异台 6/6 红**,还原一律**文件副本 + 每次 `sha256sum -c` 打 OK**,**全程未用 `git checkout`**:

| 变异 | 结果 |
|---|---|
| M1 grep 退回原锚定形式 | 红(3a) |
| M2 红分支不打详情 | 红(2d/2e/5a) |
| M3 uncertifiable 分支不打详情 | 红(4d/4e) |
| M4 日志写进树里 | 红(5b/5e/7a) |
| M5 绿路径也打详情 | **先存活** → 见下 |
| M6 不打 PY_LOG 路径 | 红(5a/4e) |

**⚠ M5 存活照实登记(证据纪律 2 的现场,连续第三轮)**:
真实的绿输出**不可能**含缩进行 —— runner 只在非 pass 时打测试自己的输出 ⇒
全绿的台子**和「无条件打详情」这条坏规则逐字同判**,6d/6e 从来不需要区分。
按规则**先怀疑断言**:往绿台子加一行**合成**的缩进行,M5 立刻红。
**方向登记**:这次的偶然一致指向**绿路径保持安静**,是**安全**的那一侧
(不是「出事时腿不吭声」那一侧),所以危害低 —— 但仍然是一次真空断言。

**端到端(真脚本、本容器)**:python 腿现在把 `test_selfcheck_lua_leg.py`
**为什么**没跑成(120s 预算超了)直接打给读者,外加 `PY_LOG:`。
**修之前这里只有孤零零一行 `UNCERTIFIABLE`。**

## 2. GH #308 —— 裁定 **(C)**,全文档案 `test_set.md §DA`

**欠了 61 小时、十波、十二次点名。** 批测台每一步都照章程(交表、按登记分支
(A) `--rec-slots 1` 执行、持续点名);**掉的是总监这一棒。**
实价:owner **P1/P2 都卡在条件 (a) 的帧证据**,条件 (a) 卡在帧通道,
十波 × (1/16 而不是 12/16)。

**裁定:(C) —— `--rec-slots 8`,并把 W25 的 196 局并进 `rec_slot_baseline.json`
后用原判据重跑验收门。**

**理由走的路和批测台的不是同一条(证据纪律 4,明写路线)。**
批测台的事后观察是「若是并发代价应随槽号累积,slot 2-12 上看不见」—— 方向对,
但那是**缺席论证**。同一张表上有更强的一条:

baseline 的 `rec_set` 是 `[1]`,所以 **slot 2-12 在 baseline 里根本不录制**,
在 W25 里**录制且是 12 路并发** ⇒ 它们的净变化 **-0.2%~-1.8%** 就是
**「打开录制」这件事的全部代价,在 11 个槽上各测一遍 ≈ 1%**。
而 slot 1 是**从「独占录制」到「12 路并发录制」**,净 **-7.4%**。

**并发录制若真要花 7.4%,slot 2-12 没有理由不花** —— 它们同样在 12 路并发里录,
baseline 基数还更低、更该显形。它们花了 1%。
⇒ slot 1 的 -7.4% 只能是**它自己的 baseline 太快**;
而这一点**章程早就独立记过**(那次 12/12 波里录制槽是最快的一槽,
对只用对照槽拟合的趋势线残差 **+8.2%**),原因正是 `rec_set=[1]` 让它独占了带宽。

⇒ **事先登记的门开火开对了,但它测出来的缺陷在 baseline 那一侧,不在被测配置这一侧。**
把它执行成「把被测配置退回去」,是朝错的那一侧动刀。

**不判 (B)**:(B) 的结论可能对,但做法是「门开火之后把开火的那一槽划出判据」——
正是「不许事后改判据」禁的那件事。批测台拒绝自行这么做是对的,
**总监也不该用裁定权把它补办成合法**。(C) 一个字没改判据,改的是**被比较的那一侧**。

**裁定含重建 baseline,不只是放行**:`rec_slot_baseline.json` 里 slot 1 那一格
**和其余 15 格不是同一种物理量**(独占录制 vs 不录制)。
不重建,任何 `rec_set != [1]` 的波都会在 slot 1 上**系统性报赤字,且每次都长得像
一次正常的门开火**。只判「这次放行」就是等下一波原样再撞一次。

若重建后 slot 1 仍超差,**那才是真的并发代价** —— 按登记分支退回并重交总监,
**那时的 (A) 才有前提**。
