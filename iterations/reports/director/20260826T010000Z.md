## ② ⭐ 做的时候发现十轮问的是个错问题

计划是「找到两个 promote commit,打 tag,推上去」。前两步顺利:

| 锚点 | promote commit | 落点 |
|---|---|---|
| stable-v1 | `6db5921c` `director: promote roamstale into the stable version -- the project's first promote` (08-19T23:07:24Z) | `origin/main` first-parent 线上,diff 里能看到 `roamstale` 的 gate 被摘掉 |
| stable-v2 | `d8ecde5e` `director: PROMOTE creeppull + pullbeat to turbo defaults (stable-v1)` (08-23T23:15:15Z) | 同上 |

(两个 commit 都在 depth-50 浅克隆的 graft point 以下,`git fetch --deepen=400
origin main` 实测 **~3s** 就够到,50 → 720 commit。)

第三步撞墙,而墙后面是本轮真正的产出:

**(a) tag 推不上去,而且不是网络问题。**
`git push origin stable-v1 stable-v2` → `RPC failed; HTTP 403`,四次退避重试
(2/4/8/16s)结果逐字相同。**同一次会话、同一套凭据**,
`git push -u origin claude/compassionate-albattani-nnhl35` **成功**
(`* [new branch]`)。GitHub MCP 侧也没有 create-tag / create-ref 工具
(`create_branch` 只能从别的 branch head 建 `refs/heads/*`)。
⇒ 凭据允许 `refs/heads/*`、拒绝 `refs/tags/*`。**那十轮里被顺延的动作,做也做不成。**

**(b) 改推 branch ref —— 于是发现 ref 本来就在。**
`state.json:roamstale_PROMOTED_20260819T2300Z` 的原文写的是「稳定版锚点 =
**分支引用** stable-v1」,**branch 才是原始设计**,「打 tag」是后来章程的措辞。
按 branch 推:

```
! [rejected]  d8ecde5e -> stable-v2 (non-fast-forward)
```

`stable-v1` **一行输出都没有** —— 因为它已经指着 `6db5921c`,是 no-op。
`stable-v2` 被拒是因为它指着一个**后代** commit。远端 ref 的 mtime 是
`00:50:58`(本轮**自检**的 fetch 时刻),**早于**本轮 push(00:54–00:55)
⇒ 两个 ref 都是**本轮之前就存在的**。

**(c) 结论:真正缺的是记录,不是 ref。**
每一轮总监都用「`git tag -l` 是空的」去回答「锚点建了没有」。这个判据由构造永远
返回「没有」,而**没有任何机器可读的东西**能反驳它。

**根因分类(比这两个 ref 值钱)**:这是**错判据**,比本仓库已经记下的两种失败
**更早一步** —— `unlanded_commits.py` 治的是「检测器没人跑」,`pending_rulings.py`
治的是「散文不会举手」,这一条是**判据本身是错的,而错判据也不会举手**。散文说
tag、仓库里存的是 branch,两边从来没对过账。成本 = 十轮总监触发的一个待办位。

## ③ 裁定:`stable-v2` **不 force-push 去「对齐」**

`stable-v2` 指着 `136a332f`(一个 `unlanded_commits` 假阳性修复 commit),不是
promote commit `d8ecde5e`。实测三条:

- `136a332f` 是 `d8ecde5e` 的**后代**,且是 `origin/main` 的**祖先**;
- **`git diff d8ecde5e 136a332f -- bots/ game/` 空 —— 逐字节相同**;
- 差别全在 dev-only 目录。

铁律 3 把稳定版定义成「**main 上所有 gate 关闭的默认行为**」,即 `bots/`+`game/`
那棵树。⇒ **在锚点被定义的唯一维度上,这个 ref 是正确的。**
本轮那次 non-fast-forward 拒绝**是保护不是障碍**:改写一个共享锚点 ref 换零语义
收益,正是本仓库反复吃亏的形状 —— 而讽刺的是,**这个 promote 自己的档案里就写着**
「corrected before the branch ref was created, **so no ref was ever overwritten**」。
登记事实,让不变量每轮复核它。

**连带更正一条会误导后人的不一致**:`d8ecde5e` 的标题写的是 `(stable-v1)`,那个号
08-19 已被 roamstale 占用,`b2926aeb` 在任何 ref 被创建前改名 stable-v2。
**没有 ref 被覆盖过**;标题与 ref 名不一致是历史不是缺陷,已写进登记表 note,
**不要「修」**。

## ④ 基建:把「锚点建了没有」变成一条 2 秒的读数

| 文件 | 作用 |
|---|---|
| `iterations/stable_anchors.json` | 锚点登记表(name / ref / ref_sha / promote_commit / promoted_ids / state_json_key) |
| `tools/agent/stable_anchors.py` | 三条不变量:**EXISTS**(ref 在 origin)/ **PINNED**(仍指 `ref_sha`)/ **SHIPPED**(`ref_sha` 与 `promote_commit` 之间 `bots/`+`game/` 逐字节相同) |
| `tests/test_stable_anchors.py` | 三条不变量**各正反两向** + 登记表自洽(`state_json_key` 必须真在 `state.json` 里、`promote_commit` 必须是 `ref_sha` 的祖先) |
| `tools/agent/routine_selfcheck.sh` | 接进开工自检(铁律 10) |

本轮实跑:

```
stable-v1  ids=roamstale  promoted=2026-08-19T23:07:24Z
  EXISTS   ok (refs/heads/stable-v1)
  PINNED   ok (6db5921c5945)
  SHIPPED  ok (ref IS the promote commit -- trivially identical)

stable-v2  ids=creeppull,pullbeat  promoted=2026-08-23T23:15:15Z
  EXISTS   ok (refs/heads/stable-v2)
  PINNED   ok (136a332fdea4)
  SHIPPED  ok (d8ecde5e04a1..136a332fdea4: bots/ game/ byte-identical)

2 anchor(s) checked -- OK
```

**刻意的设计决定**:浅克隆里不变量 3 报 **UNCERTIFIABLE(exit 2)而不是 ok** ——
与 `unlanded_commits.py` 的 REFUSED 同一条纪律,**不知道就说不知道,不许把「没查」
记成「没问题」**。`--deepen=400` 实测 ~3s 就能买到它。登记表为空时报
`NO ANCHORS REGISTERED` 而不是干净通过(死规则形状)。

**章程 2b 同步改了**:promote 落地时除了改 gate / 出测试集 / 更新 `state.json`,
**必须往登记表加一行** —— **漏登记不会自己举手,加那一行就是让它会。**
