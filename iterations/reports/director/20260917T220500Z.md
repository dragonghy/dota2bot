## 六-bis、⚠️ 收尾时我自己造出并修掉的一个真事故,照登:**一次 rebase 冲突我把带冲突标记的 `state.json` 提交了进去**

推 `main` 被拒(`fetch first`)⇒ `git pull --rebase` ⇒ `iterations/state.json` 冲突(英雄组 + 协同组
同一轮各落了一个新键)。**第一次冲突我按行做了合并并当场 `json.load` 校验通过**;
**第二次冲突的形状不同**(HEAD 侧这次有**两个**新键,且两侧都不以文档的 `}` 结尾),
我那段按行合并的脚本**断言失败、没有写文件** —— ⛔ **而我把 `git add` + `git rebase --continue`
和它写在同一条 `&&` 链的后面,于是「没解决」被当成「解决了」提交了进去。**

**读数(自查,不是别人发现的)**:`json.load` 逐字
`JSON BROKEN: Expecting property name enclosed in double quotes: line 9880`,
`grep -c '^<<<<<<<'` = **2**。

⭐ **失效方向与本报告 §三 那四笔逐字同族,而这次是反的**:那四笔是**闸替我举手**;
这一次**没有任何一条闸会举手** —— `state.json` 不在 luacheck 的范围里、不是 Lua 测试、
py 闸也没有一条测试 `json.load` 它。**它会一路推到 `main`,然后在下一个读 `state.json` 的组那里炸。**

**修法(不是打补丁,是重建)**:取 `git show origin/main:iterations/state.json`(**已含另两组的键,valid**),
用 `json` 模块加我那一个键、`json.dump` 写回 ⇒ **657 键,三个键全在**,零冲突标记。
然后 `git reset --soft origin/main` 把两个 commit 收成一个,
⛔ **让那个带冲突标记的中间 commit 根本不进 `main` 的历史**。

⇒ **两条习惯(已写进章程「下次触发」)**:
(甲) ⛔ **解冲突脚本不许和 `git add`/`rebase --continue` 串在同一条 `&&` 链上** ——
`&&` 只看退出码,而我那段脚本**断言失败也是非零**…… 正是因为非零,`&&` 本该拦住它。
**真正的成因是我把 `python3 - <<'PY'` 的退出码交给了 heredoc 之后那条独立的命令行**,
⇒ **下次:解冲突与提交分两条命令,中间必须有一次 `json.load` / `grep -c '<<<<<<<'` 的显式校验。**
(乙) **结构化数据文件的冲突不要按行合并** —— 用解析器从 `origin/main` 的那份**重建**,
