## 2. ⭐⭐ 本轮真正新增的判定:**编号是错的,而且错法有牙**

交付通篇(commit message / 报告标题 / `state.json` / `test_set.md` §BA.4 / `CLAUDE.md` /
章程状态节,共 6 处)把本次 promote 记作 **`stable-v1`**。

**但 `stable-v1` 已经存在**:`git ls-remote origin 'refs/heads/stable-*'` ⇒
`6db5921 refs/heads/stable-v1`,建于 **2026-08-19T23:00Z 的 `roamstale` promote**
(章程状态节第十二次触发 ① / `test_set.md` §K.7 / 该文件 718 行「稳定版锚点」)。
**本次是第二次 promote ⇒ `stable-v2`。**

**为什么这不是一个笔误而是一个有牙的缺陷**:`stable-vN` 按 §D 是**分支引用不是 tag**
(容器推不了 tag),而**分支引用可以被覆盖**。抢救说明 §8.5 里写死的收尾指令逐字是
`git push origin HEAD:stable-v1` ——

- 两棵树是**祖裔关系**(本次 promote 的 main 是 2026-08-19 那棵的后代)⇒ **推送是快进,不会被拒**;
- 于是「稳定版第一个正式锚点」会**静默地**指到 2026-08-23 的树上;
- 之后任何「跟 stable-v1 比一比」的读数都会**拿本次 promote 当基线**,
  而 `roamstale` 的那次 promote **从此没有任何 ref 指着它**。

**没有任何引用被覆盖过** —— 错误是在建引用**之前**发现的,`stable-v1` 仍逐字节指向 `6db5921`。
六处全部改为 `stable-v2`,并在 `test_set.md` §BA.4 留了更正框
(含给下一个 promote 的人的一句:**建引用前先 `git ls-remote origin 'refs/heads/stable-*'` 数一下**)。

**为什么改文不改史**:23:xxZ 那两条 commit 的 message 里也写着 `stable-v1`,
**没有改写历史**——commit message 是那一刻的记录,更正以本轮的新提交承载。
`state.json` 的 ruling 字段里把「原文写的是什么、为什么改、有没有覆盖过」三件事一起记进去了,
这样**读 state.json 的人不需要读两份报告才能对上帐**。
