## 2. `[bug] #64`:`J.IsValidTarget` 是一颗没有引信记录的雷管

### 2.1 事实(自己重数,不是转述)

```lua
function J.IsValidTarget(nTarget)
    -- NOTE: ... ideally it should be IsValidUnit, but a lot of legacy usage causing some problems.
    return J.Utils.IsValidHero(nTarget)      -- 与 J.IsValidHero 同一 delegate
end
```

**376 个调用点 / 100 个文件**(issue 报的 377 含定义那一行);`botTarget` **287 个**,
来自 `J.GetProperTarget` → `bot:GetTarget()` / `GetAttackTarget()` —— 对线补刀、推塔、
打肉山的时候**它就是小兵 / 建筑 / 中立**。于是**凡是为非英雄目标写的分支,恰好在它自己
适用的场景下被这道闸门挡掉**。**没有一个调用点在 TS 生成文件里**(查过),不需要双向棘轮。

### 2.2 我自己查证的两条(一条支持 issue,一条**修正**候选清单)

- **支持**:`IsValidHero == IsValidUnit and IsHero`,纯函数,同帧同参必同答 ⇒ 等价性成立。
- **修正**:我做了全树上下文扫描找**第 4 个受害者**(241 个候选,滤掉 `illusion` 噪声 —— 幻象
  **是**英雄,`IsValidTarget(x) and not x:IsIllusion()` 是自洽的)。两个看着像的**都不是**:
  - `hero_centaur.lua:385` / `rubick_hero/centaur.lua:325`:`nInRangeEnemy[1]` 紧挨着
    `creepList`,像是把小兵喂进来了 —— **但 `J.GetEnemiesNearLoc` 只遍历
    `UNIT_LIST_ENEMY_HEROES` 且自己过 `IsValidHero`**,是英雄专用列表,那两处只是冗余;
  - `mode_outpost_generic.lua:170`:「我在跟英雄打就别去抢前哨」,是**有意收窄**。
  ⇒ **issue 报的三处仍是目前唯一确认反转的三处,清单没有变长。** 这一步值得做:
  批准/排期一份跨 100 文件的清理,先把"受害者到底有几个"钉住,比事后一个个撞上便宜。

### 2.3 本轮**不做**什么,以及为什么

**不改那 376 个点,也不动 delegate。** 一次性放宽 = 几百条已发布行为同时变 —— 正是
`lanefix` 的形状(局部各自可辩护,聚合是负的),而且会**当场点燃** invoker 那条本来死着的
分支。issue §4 自己也是这个判断,我同意。

**第 1 类(~90 个参数按构造就是英雄的点,改名成 `J.IsValidHero`,零行为变化)本轮也有意不做**:
它跨 60+ 文件,而四个组每 2 小时都在改这些英雄文件;一次大范围改名换来的是 rebase 冲突,
**买不到任何行为**。棘轮已经保证这个数只减不增,谁顺手谁做即可。

### 2.4 本轮落地的东西:让这颗雷不再无声

1. **FUSE RECORD**(`bots/FunLib/jmz_func.lua`,定义正上方):改 delegate 会点燃什么 ——
   ~90 个英雄参数点行为中性、287 个 `botTarget` 点行为改变、三处已确认反转逐个点名。
   原始 NOTE 保留(它是历史),但不再是唯一的说明。issue §5 结尾要的正是这个。
2. **`tests/test_isvalidtarget_fuse.lua`(5 例)**:
   - 等价性在合成世界(英雄 / 小兵 / 塔 / 肉山 / 死英雄 / nil)上逐个断言 ——
     **可执行事实,不是注释里的断言**;
   - **正向**断言收窄本体:小兵、塔、肉山**是** valid unit 而**被这个谓词拒绝**;
   - delegate 源码守卫(body 变了就失败,文案把人送去 fuse record);
   - 记录守卫(record 消失、或不再点名那三个文件,失败);
   - **调用点数量棘轮 376,只减不增**,失败时点名最重的文件。
3. **给各组的硬规矩**(`test_set.md` §Q.2):**不要再新增 `J.IsValidTarget` 调用点**;
   要英雄写 `J.IsValidHero`,要任意单位写 `J.Utils.IsValidUnit`;**退役调用点时同一个
   commit 里把 `CALL_SITE_CEILING` 调低**。

### 2.5 变异测试(三次,每次都恰好点名缺陷)

| 变异 | 结果 |
|---|---|
| delegate 改成 `J.Utils.IsValidUnit` | **恰好 3 挂**(等价性「小兵上 true vs false 不一致」/ 收窄「小兵是 valid unit 却被接受」/ 源码守卫「body 变了」) |
| 只删 fuse record(delegate 不动) | **恰好 1 挂**,文案说明为什么记录不能删 |
| 在 `mode_roam_generic.lua` 加一个新调用点 | **恰好 1 挂**:「377 > 376」,点名该文件 |

**踩坑记一条给各组**:第一次做变异时我用 `sed` 替换 `return J.Utils.IsValidHero(nTarget)`,
**`J.IsValidTarget` 和 `J.IsValidHero` 的函数体逐字节相同**,sed 把两个都改了 ⇒ 两者仍然一致
⇒ 等价性那条没挂,我差点误判测试无效。更糟的是接着的 `git checkout` **把我尚未 commit 的
fuse record 一起还原了**,导致第二次变异跑在一棵没有记录的树上。**教训:变异前先备份文件
(或先 commit),不要用 `git checkout` 当撤销键;当两个函数体逐字相同的时候,任何按内容
定位的编辑都是二义的。**

## 3. `[strategy] #52` 裁定:`tpwatch` **reject 出集**(第一个 reject)

### 3.1 自己复核的两条承重断言

   → `BOT_MODE_DESIRE_VERYHIGH`)。

### 3.2 但我**不采纳** issue 的主论据

issue 说「0.9 抬的是**已经在赢**的那个 mode ⇒ 那 +0.15 没有落点」。这在它重建的那一帧上成立
(次高是 laning 0.446),**但不是结构性成立**:`mode_team_roam_generic` 的 L1-TRADE / L5-COMBO
修完 `[bug] #31` 之后**真能出到 0.92**,roam 也有 `VERYHIGH * 1.2` 的分支 ⇒ 存在「退却 0.75
输、0.9 赢」的帧,那种帧上 armed **确实换掉当选者、确实产生新的移动令**。

**所以它不属于「结构上不可证」那一类**(≠ `creeppull` / `pullcamp` / `l1xpsoak` 的退回)。
**它是可发生的 —— 只是发生的时候做的是错事。**

### 3.3 reject 站得住的是条件 (c)

判据(「读条开始后已掉 ≥30% 最大血」)在 3.0s 的 Turbo 读条上是**滞后指标**:11 局 8 次里
最早只在**落地前 1.2s** 成立,3 次只在死/落地那一瞬成立,1 次从未成立。而 issue 自己给的
ground truth 指向**相反**的决定 —— juggernaut 27% 血扛完读条落地,**又活了 103.5 秒**。
在剩 0.5–1.2s 放弃读条 = 把残血英雄**留在敌方半场**,放弃唯一能救他的那件事。
候选侧 3 次有窗口的读条 3 次都跑完了,与机制分析互相印证。**价值论证是反的,不是没测出来。**

### 3.4 立了一条归档口径(比这次裁定更值钱)

**退回 = 条件 (a) 测不出来**(语料 / 可测性问题,改工具就能重来,id 留在各组 backlog);
**reject = 条件 (c) 被帧证据推翻**(规则本身想错了,换多少语料都不会变对,只留 gate)。
前四次(`creeppull` / `pullcamp` / `l1xpsoak` / `cmrguard` 第一次 / `axebuyblink`)全是前者,
这是第一次后者。

### 3.5 对在跑波次的影响:**无,不重跑、读数不作废**

10:11Z 那波的 cand 串里**有** `tpwatch`。它买的是 `zusult` / `cmrguard` 的条件 (b)
**行为检测器**读数,两者都不路由经过退却出价链;`tpwatch` 是**两臂常量**且近似惰性
⇒ 不构成混杂。**下一波 cand 串 = 本波去掉 `tpwatch`(16 id)**,其余逐字不变。
写进 `test_set.md` §Q.0,免得下轮再问。

### 3.6 认账
