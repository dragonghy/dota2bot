## ② ⭐⭐⭐ GH #384 [harness]:`test_rc_wrapper.py` 的 TRUNK RED 不是并发假红

### 现场
开工自检的 python 腿读到 `TRUNK RED`,详情(**这是 GH #380 修复后第一次真正兑现的红利** ——
以前这一行会被 `grep -E '^(FAIL|...)'` 的 `^` 锚定删掉)是:

```
1 FAILURE(S):
  - self-running .lua: NOT refused, real code passed through: got 127
    -- a refusal that fires on everything is not a check
```

### 根因(**127 是诊断,不是噪声**)
`tests/test_rc_wrapper.py:156` 的 `run(['lua5.1', script])` 走
`bash tools/agent/rc.sh lua5.1 <script>`。rc.sh 对 module `.lua` 的**拒绝发生在 `:82`,
比 `"$@"`(`:103`)早二十行** ⇒ 前一条 `rc == 2` 的检查**与 `lua5.1` 在不在无关**、照常绿;
而这一条是**故意构造的放行用例**,要真的 exec `lua5.1` ⇒ **`lua5.1` 不在 PATH 上就是 127**。

**而 `routine_selfcheck.sh` 在 `:321` 跑这套 python 套件,在 `:451-452` 才
`ensure_lua_tool lua5.1`** —— **晚了约 130 行**。⇒ 新容器上 `:321` 那一刻解释器**真的不在**,
这不是并发、不是脆,**是确定的顺序缺陷**。

### 为什么四轮都判错
前四轮的判据是「**裸串行复跑是绿的 ⇒ 假红**」。
**那次复跑是被污染的测量**:自检**自己后面那条腿**在两次测量之间把缺的二进制装上了。
本轮同样复现:`python3 tests/test_rc_wrapper.py` 裸读 **exit 0 全绿** —— 但这一次我去看了**是哪一条**红、
**红成了什么值**,而那个值把因果指了出来。
**#380 的价值就在这里**:那四轮**根本拿不到这一行**。

### 同一个缺失依赖,在同一个文件里给出两个方向相反的错答案
文件末尾 `run_tests.lua is never refused` 写成 `rc != 2 or ...`。
`lua5.1` 缺失 ⇒ rc = 127 ⇒ `127 != 2` 为真 ⇒ **这一条 vacuously 绿**。
**上面那条为缺失的二进制变红,下面这条为同一个缺失的二进制变绿**,相隔四行。

### 处方(本轮只动 `tests/test_rc_wrapper.py`,**不动自检**)
`HAS_LUA = shutil.which('lua5.1') is not None`;两条**真的需要解释器**的检查在缺失时改打
`UNCERTIFIABLE` 并把退出码抬到 **2**(该文件 docstring 自己写的「did NOT run」那个词),
`fails` 仍然优先于 `uncs`(**真失败压过缺依赖**);**其余检查一字未动**。
⇒ 新容器上这条腿由**假红(3)**变为**诚实的未核验(2)**。

**故意没做的那半(留给 #384,不夹带)**:把 `ensure_lua_tool lua5.1` 挪到 python 腿之前,
让这两条检查**真的能跑**而不只是诚实地没跑。
不夹带的理由是**验证成本**:改自检要过 `tests/test_selfcheck_lua_leg.py`,
而它在本容器上**撞 GH #358 的 120s 预算、9 条 UNCERTIFIABLE**,
本轮**买不到**对那次改动的核验 —— **买不到核验的改动不该和一个已核验的改动同轮出门。**

### 变异台(**证据纪律 2**)
本轮的变异必须在**两种世界**里各跑一遍(`lua5.1` 在 / 不在),否则一个只在缺失时才犯的错**测不出来**。
「不在」用 `mv /usr/bin/lua5.1 /usr/bin/lua5.1.hidden` 现场制造,**同一条 bash 调用里还原**并
`lua5.1 -v` 验证复原。

| 变异 | present/absent 退出码 | 判决 |
|---|---|---|
| CONTROL(未变异) | (0, 2) | **CONTROL GREEN** |
| M1 去掉 self-running 那条的守卫(= 修前源码) | (0, 1) | CAUGHT |
| M2 `HAS_LUA = True` | (0, 1) | CAUGHT |
| M3 `unc()` 什么都不记(一个会通过的 SKIP) | (0, 0) | CAUGHT |
| M4 uncertifiable 退 0 而不是 2 | (0, 0) | CAUGHT |
| M5′ `unc()` 记进 `fails`(未核验又变回红) | (0, 1) | CAUGHT |
| M6 探错二进制名(`lua5` 而非 `lua5.1`) | (2, 2) | CAUGHT |

**6 条全红 + CONTROL 绿**;还原走**文件副本**,`sha256sum -c` **OK**,**全程未用 `git checkout`**。

**⚠️ 方法自伤照实登记(第二发)**:第一版的 M5 是「只守第二条不守第一条」,
读数 (0,1) 与 M1 **逐位相同** —— 因为 M1 把 `if HAS_LUA:` 改成 `if True:` 时**同样让 `else` 变成死代码**,
两条**是同一个变异**。**「六条」当时是五条。** 换成 M5′(改的是**词汇**不是**守卫**)后才真是六条独立的。
**与前三轮的 M3/M5 同族,连续第四轮:变异台最容易骗人的不是「没红」,是「红得不独立」。**

**⚠️ 方法自伤照实登记(第三发,这次伤到了别人的档案)**:统一时间戳时我对
`test_set.md` / `queue.json` 做了一次**无锚点的整文件 `str.replace('09:5xZ', ...)`**,
一次改坏 **7 行历史档案 + 2 处 `queue.json` 正文**(§BL / §CT / §AM 的裁定时刻、`_protocol` 里的条款日期)。
**没有任何测试会红** —— 那些是散文里的时刻。是**读 `git diff --stat` 时行数对不上**才发现的,已逐行还原,
最终 `queue.json` 回到 **18 insertions / 2 deletions** = 恰好我那两行。
