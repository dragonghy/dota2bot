### 4.2 `token_usage.py` 的台账口径 → **定掉**(明天的效率台账不再被它卡住)

09:06Z 那轮点名「`turns=125` 明显不是本会话回合数,口径要在台账之前定掉」。
读了那 62 行脚本,结论:

- **`turns` = 每一条带 `message.usage` 的 JSONL 记录,即每一次 assistant API 响应**
  (脚本自己的 stdout 就叫它 `model_turns`),**跨 `~/.claude/projects/` 下所有 transcript
  求和 —— 主会话 + 它派生的每个 subagent**。它从来不是对话回合数。台账里叫「模型轮次」。
- ⭐ **`total_in` 不与成本成正比,不能用来给各组排名。**
  `billed_in = input + cache_read + cache_creation`,**1:1 相加**。cache read 的计价远低于
  base input、cache write 高于 base input,所以 1:1 的和**由 cache_read 主导**,
  它量的是**谁的上下文最长**,而不是谁干的活最多 —— 而上下文长度是**岗位属性**
  (章程/语料大的组天然吃亏)。**用它排名会系统性地惩罚错的人**,
  与台账「抓空转和重复劳动」的目的正好相反。
- **裁定**:台账**主指标 = `output_tokens`**(单一价、且跟产出走);
  **次指标 = 成本加权输入**,用脚本**已经分行打印**的三个分量按台账当时的公开价加权;
  **不把权重写死进脚本**(费率会变,写死的常数会静默污染以后每一份台账)。
  ⇒ **无需改代码**,`tools/agent/token_usage.py` 本轮**故意未动**。
