## 一、⛔ 交过来的那条红:`mutstand_fixture_debt.sh` 的 EXIT trap 陷的是 `rm`

批测台 21:15Z 报告原话:「**本台不修别组的工具,交总监**」。归属判得对,本轮修掉。

### 缺陷本身比测试说的更重

测试(`test_mutstand_restore_trap.py`,GH #418)只说「trap 了一个不存在的函数 ⇒ trap 触发但什么都不做」。
**裸读源码,真实形状更坏**:

```bash
TMP=$(mktemp -d)
trap 'rm -rf "$TMP"' EXIT      # ← 旧行
```

`$TMP` 里装的是**每个 mutant 唯一的原件副本**(`save()` 写进去的 `.orig` + `.sha`)。
于是一次中断同时做两件事:**把 mutant 留在工作树里**,**并把唯一能还原它的副本删掉**。
⇒ 这条 trap **比没有 trap 更坏**:GH #418 立案时说「其余五个台子的 restore 只活在直线路径上,
中断就把 mutant 留下」,而这一个**连中断后手工恢复的路都一起铲了**。

### 修法

`restore` 在本台**带参数**(兄弟台子还原的是固定 FILES 列表,不带参),所以
`trap restore EXIT` 在 `set -u` 下会因 `$1` 未绑定而炸 —— 这大概率就是当初写成 `rm -rf` 的原因。
落地:加一个 `INFLIGHT` 变量记住「此刻被改的是哪个文件」(`save()` 置位、`restore()` 清位),
trap 一个 `on_exit()`:**先还原、再删副本**(顺序是内容不是风格)。

### ⭐ 两个裸读的证据,不是静态断言

**(甲)修后中断实测**:后台起真台子,**轮询到 mutant 真的出现在工作树里**(第 8 次轮询),
当场 `kill -TERM`,然后对**跑之前存的 sha 清单**核账:

```
MUTANT PRESENT after 8 polls
stand wait rc=143                      # 143 = 128+15,确实是被 TERM 杀的
tests/fixtures/f_260903_101254_cm_farm_stealcamp.lua: OK
tests/test_focus_innate_index_anchor.lua: OK
SHA_CHECK_EXIT=0
git status --short                     # 只有本轮两个有意改的文件
```

**(乙)反事实**:把修好的版本**存到树外**、`git checkout --` 拿回旧版、**同一个实验**:

```
MUTANT PRESENT after 7 polls
tests/fixtures/f_260903_101254_cm_farm_stealcamp.lua: FAILED
SHA_CHECK_EXIT=1
git diff --stat  =>  1 file changed, 1 insertion(+), 1 deletion(-)
```

**旧 trap 下,SIGTERM 把 M1 的 mutant(给一行野怪加一个 `name =`)留在了 fixture 里** ——
一个「本轮本来就在动的文件里的、看起来完全合理的单 token 编辑」,正是 GH #418 立案句描述的东西。
两个实验之间只差那一处 trap;之后修好的版本从树外拷回,`sha256sum -c` 逐字核过。

**(丙)先量了机制再依赖它**:`trap ... EXIT` 到底会不会在 SIGTERM/SIGINT 下跑,
是个**可以量的问题**,本轮量了(独立 probe 脚本,TERM 与 INT 各一次,两次都打出 `TRAP RAN`)
⇒ **不需要**给六个台子加 `INT TERM`,`EXIT` 够。⚠️ `SIGKILL` 与容器被回收**任何 trap 都救不了**,
这条不声称。

**(丁)台子本身还能干活**:`bash tools/agent/mutstand_fixture_debt.sh` ⇒
**`mutants: 6/6 CAUGHT`,`RC_EXIT=0`**,跑完树干净。

### ⭐ 顺带修掉测试自己的一个盲点(而它当场咬了我一口)

`test_mutstand_restore_trap.py` 的**顺序检查**(trap 必须装在第一次施加 mutant **之前**)
是靠字面量 `apply_mutant ` 找施加点的。而 `mutstand_fixture_debt.sh` 的施加函数**叫 `mutant`** ⇒
它**有窗口可排序**,却被打成 `--  ordering not applicable` **跳过**。
这就是本仓反复买的那个形状:**检测器只认得这件事的一种拼法,把另一种拼法读成"不存在"**。

⛔ **而我的第一版加宽当场把四个台子从绿打成跳过**:我把调用点锚到了行首,
可真实调用点是 `if ! apply_mutant "$m"; then`。**输出里它们不是变红,是变成 `--`** ——
如果只看退出码(仍是 0),**这次回归会静悄悄落地**。
⇒ 第二版按**定义**找施加函数(`mutant` 或 `apply_mutant` 的函数定义),按**行内**找调用点,
并**新增一条断言**:一个**定义了**施加函数却**找不到调用点**的台子,是**检测器丢了形状**,
**不是"没有窗口"** ⇒ 直接判失败,不许再打 `--`。

**这条新断言有牙,裸读**:把调用点正则**改回我第一版那个行首锚定**(即精确复现我差点交出去的回归),
文件 **`M_A_EXIT=1`**,并逐台点名 `FAIL ... [the ordering check below cannot run; widen the call-site pattern]`
(11 个台子)。改回后 `sha256sum -c` 核过原状。

**修后**:`91 ok / 0 FAIL`,`TRUE_EXIT=0`,20 个台子;
**净变化是 `mutstand_fixture_debt.sh` 从 `--` 变成两条 ok**,
另外 5 个仍打 `--` 的台子**逐一核过它们在旧检测器下也是 `--`**(`grep -c 'apply_mutant '` 全 0)⇒
**没有任何台子在这次加宽里丢了检查**。
