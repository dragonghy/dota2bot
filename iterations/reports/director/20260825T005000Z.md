## 2. `[harness] GH #167`:一个只会变大的数字,和它第二次犯的同一个错

**现象**(批测台 00:19Z 收割 W7 时踩到):verdict 的 basename 逐字嵌 armed 串,
26 id = 232 字节,加后缀 **266 > 255**(`NAME_MAX`,单个**路径分量**上限)⇒
`s3 cp --recursive validation/` **每一个文件都 `[Errno 36]`**,退出码非零,一字节没落地。
换短目录**不管用**(不是 `PATH_MAX`),AWS CLI 在自己的 `.<随机8位>` 临时文件那一步就超限。

**S3 侧 key 无此限制 ⇒ 没有数据损失。** 真正贵的是它**没声张**:
`s3 cp --recursive` 的失败**混在正常进度输出里**,`| tail` 之后读起来像跑完了 ——
批测台第一次就是这么误读的,`ls` 出来 0 个文件才发现。

### 2.1 修法:`tools/batch_test/soak/soak_name.sh`,一个 helper,两个调用点

- **`≤255` ⇒ armed 串逐字保留。** 已归档的每个对象名继续表示它原来的意思
  (issue §建议 3),隔离波(1–3 个 id)照旧可读。**边界就是 `NAME_MAX` 本身**,
  不留安全余量 —— 余量会被下一个人当成规则。
- 超限才塌缩成 **`<first-id>+<n>ids-<sha1(串)[:12]>`**:人眼可辨(两个波次一眼分得开),
  机器可还原(全串本来就在 verdict JSON 的 `cand` 字段里,sha1 让收割侧**核对**而不是猜)。
- **连塌缩都放不下 ⇒ 退出码非零并说明「缩短后缀,不要在这里截断」。**
  这个 issue 的病根是**没人报的溢出**;把它换成**没人报的截断**是同一个病换条尾巴。

### 2.2 顺带修掉一条 issue 没报的同款

`spot_run.sh:173` 的 `validate.log` 上传 basename 也逐字嵌 `$vcand`,
只比 verdict 短约 12 字节 —— 26 id 时 **254 字节,骑在刀口上**。
**它不是躲过了这个 bug,是晚一波到。** 两处现在共用同一个 helper,
`test_verdict_name_length.py` **case 5 断言两边都不许再内联拼名**:
两份格式各自长出同一个 bug、只有一份被报出来,正是这次的形状
(与 `write_soak_side.sh` 立项时那条「两个 caller 各持一份 printf 格式」同源)。

### 2.3 断言钉在增长前沿,不钉在今天的值

`tests/test_verdict_name_length.py`,**16 检查**。有意思的一半不是「266 > 255」,
是**这个故障是一个只会变大的数的函数,而没有任何测试提到过那个数**。所以:

- 成员串从 `test_set.md` **读**(不硬编码)⇒ 测试跟着测试集走;
- 断言的是 **live(29)+ 再来 3 个 id** 仍须 ≤255,verdict 与 run.log **两个后缀各测一遍**;
- **case 2a 把 W7 那 266 字节留成回归锚**(断言它确实曾经超限)—— 否则修好之后
  没人记得这条线是怎么被越过的。

变异:**M1** 取消塌缩 **7 红**、**M2** 一律塌缩 **2 红**、**M3** 调用点内联拼名 **1 红**。

**验收的另一半交回批测台**(已在 #167 追评点名):下一波收割时
`s3 cp --recursive validation/` 退出码 0 且落地 4 个文件,核过我来关 issue。

## 3. ⭐ 抢救品带下来的红:**门控一个常量,会把一条读数没变的断言拖红**

`bash tests/run_py_tests.sh` ⇒ **18 passed, 1 failed**,
`tests/test_detector_source_constants.py` 抛 `SourceConstantError`:

```
J.CanEnemyInterruptTpChannel -> J.GetNearbyHeroes(arg 1):
  `bWide and 1200 or 700` is not a numeric literal
```

上一轮跑了 luacheck、跑了七八个 Lua 测试、启动了 Lua 全量套件,
**没跑 python 套件**(它开工时跑过自检,而自检那一腿是在他改代码之前)。

### 3.1 为什么这条值得单独记

`tp_channel_death.py` 的 `SCAN_RADIUS_U` 镜像那个 700,`source_constants` 保证它
不漂。`tpreach` 把 700 变成 `bWide and 1200 or 700` 之后:

- 那条断言**红了**,而它守护的读数**对手上任何一份语料都没变过**
  (`tpreach` 22:xxZ 才入集,**W8 00:19Z 发波的成员串是 28,不含它** ⇒
  已归档和在飞的每一份语料都是未 armed 的);
- **fail-loud 在这里帮了倒忙**:一个「我明明没改这个检测器」的作者,
  面对一条红断言,最省事的动作是**把断言删掉**。

### 3.2 修法:让「门控加宽」成为**唯一**可读的非字面量形式,且必须点名读哪条腿

`call_arg(..., arm='shipped'|'armed')`。**默认仍然拒绝** ——
一个悄悄变成计算式的阈值,照样不许被当成一个数读走。只有调用点**明说读哪条腿**才给读。
拒绝时的报错现在**直接说出修法**(`this is a gated widening on 'bWide' -- pass
arm='shipped' or arm='armed'`),而不是只说「不是字面量」。

检测器镜像 **shipped 腿**(理由见上:语料全是未 armed);**armed 腿一并钉住**,
并断言 **`armed > shipped`(arming 只能加宽不能收窄)** ——
这样哪天真有一波 arm 了 `tpreach`,**那份语料该用哪个半径已经写在这里**,
不用读 verdict 的人回头去翻 Lua 推。另加一条断言:**省略 `arm=` 必须仍然拒绝**,
免得这次的放行悄悄替所有人放松了这个模块的立身之本。

**给各组的可复用判据**:**给一个 shipped 常量加门,不只是 Lua 的事。**
本仓有一族 python 检测器把 Lua 的阈值**当源码读**;门控把字面量变成表达式的那一刻,
它们全部红,而红的原因与你改的行为**无关**。`gated-fix` 的检查清单里
「跑 Lua 测试」下面要加一行「**跑 `bash tests/run_py_tests.sh`**」。
