### 4.3 是什么:**最后一局的 `.dem` 上传被 run 结束截断**

两条证据同向,且互相独立:

1. **它是这个 run 的最后一局** —— 按 game tag 排序的末位是 `123837_slot3`;按**上传时间**
   排序,该 run 全部 `soak/` 对象的末三件就是它的 `.log.gz`(12:44:12)/
   `.analysis.json`(12:44:13)/ `.demclaim.json`(12:44:14);`dem21/` 的最后一次上传
   停在 12:44:09(上一局 `123828_slot14`)。**该 run 之后再无任何对象。**
2. **上传顺序本身把 `.dem` 排在最后** —— `soak_loop.sh:154` 先传 438 字节的
   `$TAG.demclaim.json`,`:160` 才传 ~10MB 的 `$TAG.dem`。轻的先落地、重的在最后,
   run 一结束被切掉的必然是后者。

**范围**:308 局丢 1 局(0.32%),且只在**一个 run 的最后一局**上;另外三个 run 的
最后一局 `.dem` 都完整。**这是竞态不是结构性缺陷**,但顺序让这个竞态每个 run 都有
一次机会(= 每波最多丢 4 局,上限 ~1.3%)。**不影响 14:12Z 的任何读数**(经济读数走
`analysis.json`,308 全在)。

### 4.4 免费捡到的一条纪律:**`.demclaim.json` 才是 `.dem` 的正确分母**

以前拿 `analysis.json` 数当分母去看 `.dem` 缺多少,**分不出「归属失败」和「上传截断」**
——两者都表现为「少一个 `.dem`」,而处置完全不同(前者是 `#75` 的证据质量问题、要查;
后者是运维尾巴、不影响读数)。现在有了三元组:

```
analysis.json  = 打了多少局
demclaim.json  = 其中多少局把 .dem 认领成功   ← 新分母
.dem           = 其中多少局真的传上来了
```

- `demclaim < analysis` ⇒ **归属侧问题**(`#75` 域),要查、要影响帧证据可信度;
- `.dem < demclaim` ⇒ **上传侧截断**,只是少了那几局的帧,读数不受影响。

本波实测 **308 / 308 / 307** ⇒ **归属侧 100% 干净**,损失全在上传侧。
**今后每轮收割的固定栏位按这个三元组写**,不再只写 `.dem` 对 `analysis` 的差额。
