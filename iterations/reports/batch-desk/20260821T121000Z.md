## 3. 本轮交付:**shallow clone 让章程步骤 5 的树漂移核对往危险方向静默失效**

**怎么撞上的**:按章程步骤 5 核对「上一波测的树 `11a8de33` 到现在 `bots/` 有没有变」,
`git log 11a8de33..HEAD -- bots/ game/` 直接 `fatal: Invalid revision range`。

**根因不是历史被改写**(第一反应是这个,查错了会浪费一整轮):

```
git rev-parse --is-shallow-repository  ->  true
git rev-list --count HEAD              ->  50          # 深度 ~50
根 commit 日期                          ->  2026-08-20 19:05:12 +0000
```

**本会话的仓库是 depth≈50 的浅克隆**,而 `11a8de33` 是 08-20T18:0xZ 的树 —— **就差在边界外一点点**。
同一现象还伴随一条会误导人的输出:`git fetch origin main` 打印
`+ 46d381d...2cb0768 main -> origin/main (forced update)`,**浅仓库里这是正常的,不是别人 force-push**。

**为什么这条比 20:11Z 那条「本地 `origin/main` 是陈的」更危险 —— 它往安全的反方向失效**:

| 写法 | SHA 在边界内 | SHA 在边界外(本轮的情形) |
|---|---|---|
| `OUT=$(git log A..HEAD -- bots/ 2>/dev/null)`;`[ -z "$OUT" ]` | 正确 | **stdout 0 字节 ⇒ 读成「无漂移」⇒ 会用 `--ref main` 上机,而正确动作是钉 SHA** |
| `git log A..HEAD -- bots/ \| wc -l` | 正确 | 丢弃 stderr 时 = **0**;不丢弃时 = **1**(那行 fatal 被数成一个 commit) |
| 看 **exit code** | 0 | **128** ⇒ 这是唯一没被骗的那个 |

三种写法全部实跑验证过(见下「验证」节)。**20:11Z 那条坑算出的是一个虚假的巨大 diff(645 行删除),
人一眼就会去查;本轮这条给出的是一个虚假的「干净」,没人会去查。**

**修法(已写进章程步骤 5)**:核树前**先把那个 SHA 取回来**,再比,并且**认 exit code 不认空输出**:

```bash
git fetch --depth 1 origin <40位SHA>          # 浅仓库里这一步是必需的,不是可选的
git log --oneline <SHA>..HEAD -- bots/ game/  # exit 128 = 不可比,不是「无漂移」
```

**`git fetch --depth 1 origin <SHA>` 对浅边界之外的 SHA 依然有效**(实测:在一个空 `git init` 里
`--depth 1` 取 `11a8de33` 成功 ⇒ `SHA_FETCH_OK`),这与 20:09Z 立的「裸 SHA 能不能 fetch 先本地实测」
是同一条工具链,**只是这次它救的不是上机、是核对本身**。

**取回后的真实读数(即条件 (ii) 的证据)**:`11a8de33..2cb0768` 在 `bots/`/`game/` 上
**8 个 commit、5 个文件、+277/−5**:

```
bots/BotLib/hero_crystal_maiden.lua      +40
bots/BotLib/hero_lion.lua                +57 −1
bots/BotLib/hero_obsidian_destroyer.lua  +34
bots/FunLib/jmz_func.lua                +150 −4
bots/ability_item_usage_generic.lua       +1
```

⇒ **条件 (ii)「有新东西可测」满足**(但见第 5 节:满足 ≠ 该启动)。
