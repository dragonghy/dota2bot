### 9.1 ⭐⭐ 发评论前那道门自己出了问题,而它的失效方向是「让人删掉正确的引用」

按 #290 先跑 `claim_precheck.sh`,**它拦下了这条评论**:

```
PRECHECK_EXIT=3
CITATIONS ... trunk origin/main  (shallow clone)
OFF-TRUNK commit  48ff29fe / c48dc11b / 75a88fa3
      resolves on origin/claude/admiring-hawking-0k75ms
DO NOT PUBLISH YET -- the citations above do not resolve on origin/main.
Push, then re-run this, then close the issue / post the comment.
```

这三个 hash 是**从 #352 正文里引出来的**,而 #352 正文写着「五个被引 commit 均已核实为 `origin/main` 的祖先」。**表面读法是「#352 正文写错了」,而且这正是本轮差一步就要写进评论的论断。**

**没有据此下结论,去查了原因**:

```
git rev-parse --is-shallow-repository  => true
git rev-list --count origin/main       => 51      # 底板停在 2026-09-02
```

被引 commit 是 **08-25 / 08-27** 的,**在 shallow 底板以下** ⇒ `merge-base --is-ancestor` / `branch -r --contains` **按构造答 NO**,而它们在别的会话分支上恰好可达(那些 ref 的 fetch 深度不同),于是被归成 "resolves on `origin/claude/...`"。

`git fetch --deepen=600 origin main`(758 commit)后重查:**`48ff29fe` / `c48dc11b` / `75a88fa3` / `aadd9938` / `79f32c92` 五个全部 `ancestor-of-main: YES`**,同一份草稿重跑门 ⇒ **`PRECHECK_EXIT=0` / `clean` / `OK to publish`**。

⇒ **#352 正文是对的,是门错了。** 三点值得记:

1. **这不是偶发**:Routine 容器每次都是全新 shallow clone,本轮底板 **51 commit ≈ 一天** ⇒ **任何引用一天前以上 commit 的草稿都会踩**,而跨周归因讨论(#352 这种)几乎必然如此。
2. **失效方向朝着「删掉正确的东西」**:`DO NOT PUBLISH` + `Push, then re-run` 把人往「我有东西没推」推,但**推什么都没用**(同一份输出里 `local commits not on origin/main: 0` 与 `OFF-TRUNK` **两个读数在打架**,与 GH #420 同形);推了没用之后最省事的「修法」就是把 hash 删掉 —— **一条正确引用被门吃掉**。
3. **工具自己知道自己 shallow**(`(shallow clone)` 那句就是它打的),**但没把这个事实接到判据上** —— 与 GH #171/#205 同族,方向相反:那两次是**门没开过**,这次是**门开了却指错方向**。

**已开 GH #446 交总监**(三条独立建议:甲 shallow 时自行 deepen 后复判、拿不到就降 `UNCERTIFIABLE`/exit 2;乙 只改行文但 `Push, then re-run` 在该分支下必须不出现;丙 两读数打架时自己举手)。**本台不自己改 harness。**
