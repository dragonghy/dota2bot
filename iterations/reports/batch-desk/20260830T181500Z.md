## 2. ⭐⭐ 本轮实质发现:自检的 `TRUNK RED` 可以是假的,而且不走 #243 那条豁免路

**读数**:自检打


`60 passed, 0 failed, 0 uncertifiable`,`PY_SUITE_EXIT=0`。**

**归因(本台自纠,不推给工具)**:自检是我后台起的,起来之后我在同一棵树上跑了
`git reset --hard FETCH_HEAD`(把工作树从 `0440598` 挪到 `7e4210c8`)。
失败的**恰好**是三个**普查型**测试 —— 它们要遍历整个 `bots/` 树 ——
**它们正在读的文件在读的过程中被换掉了。**

**为什么这条值得登记,而不是只怪我自己手快**:

- `tests/run_py_tests.sh` **没有 per-file timeout**(`:30` 直接 `out=$(python3 "$f" 2>&1); rc=$?`),
  所以这不是超时,是测试真的以非零码退出了 —— **一个真实的失败退出码,来自一个不真实的原因**。
- `routine_selfcheck.sh:256-265` 里 GH #243 立的那道守卫,判据是**退出码 2**
  (「some test could not read its input」),它打 `UNCERTIFIABLE`、`note 2`,并明写
  「**it is NOT evidence that trunk is red: re-run on a quiet tree (nothing writing under bots/)**」。
  **那句话完全正确,只是挂在了错误的退出码上。** 树被改写这一个原因,可以产出 exit 2
  (读不到输入),**也可以产出 exit 3**(读到了半棵树、普查算出一个真的不一致);
  #243 只买下了前一形,后一形照样打 `TRUNK RED` 并把 worst exit 抬到 3。
- **后果不是「多看一眼」那么轻**:`TRUNK RED` 是会改变下游行为的读数。本轮它出现在
  **W29 已经发出去之后**,如果照字面读,该轮的正确反应是**考虑把四台杀掉**
  ——为一个不存在的红杀一波真钱。
- **同族**:与本台上一轮登记的「`describe-instances` 对已消失的实例答空列表 + exit 0」、
  与「没跑的门不打印任何东西」是一族的反面 —— 那三条是**坏消息长得像好消息**,
  这一条是**好消息长得像坏消息**,而**两边的共同点是:退出码的形状与原因的形状不是一一对应的。**

**建议(总监地界,本台不改工具)**:自检在跑 python 套件的**前后各取一次
`git rev-parse HEAD` + `git status --porcelain` 的指纹**,不一致就把该腿判 `UNCERTIFIABLE`(exit 2)
而不是 `TRUNK RED`(exit 3),并打一行点名「树在读的过程中变了」。零额外成本,
且**正好落在 #243 已经写对了的那句话上,只是把它从退出码判据换成状态判据**。
已开 issue(见 §8)。

**本台自己的纪律也一并写进章程**:**自检跑着的时候不许动工作树** —— 它「不碰工作树」
是它对我的承诺,不是我对它的。
