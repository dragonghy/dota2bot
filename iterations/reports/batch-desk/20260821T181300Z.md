### 3.3 ⭐ 新发现:扁平的 `replays/` 前缀正在静默丢局和错配,而这一波的语料里就有一个

`dem_inventory.py` 的文档写着 `replays/<TAG>.dem` 是「flat slot-1 mirror,
never expires,deliberately kept(owner 再看 + 行为普查)」。它确实是同一批文件
(逐字节同名同大小),**但它把 run 前缀丢掉了,而文件名只有 `<游戏起始时间戳>_slot1.dem`。**
同一波里多台实例是**相隔几秒**启动的,slot 1 的开局时间因此会**撞进同一秒**。

全桶实测(两次 `s3 ls --recursive`):

| 口径 | 值 |
|---|---|
| `soak/**/*.dem` 对象数 | **1,015** |
| 其中不同 basename 数 | **990** |
| 出现在 >1 个 run 里的 basename | **21** |
| 因此被压掉的对象 | **25**(占录像语料 **2.5%**) |
| `replays/*.dem` 对象数 | **991**(= 990 + 1 个 `soak/` 里没有的名字) |
| `soak/` 的 basename 有几个在 `replays/` 里找不到 | **0** |

⇒ **两条事实**:(甲) 25 个 `.dem` **只存在于 `soak/<run>/` 下,经 `replays/` 拿不到**;
(乙) 更麻烦的是那 21 个名字**在 `replays/` 里是无法归属的** —— 你拿到
`20260819_061017_slot1.dem`,它可能来自**三个不同 run 的三个不同种子**,
文件名里没有任何东西能告诉你是哪一个。这不是「少了几局」,是「拿到的那局属于谁不知道」。

**碰撞集中在我自己现行的拓扑上**:21 个里有 13 个来自 08-19 / 08-20 的波次,
正是「4 台 × 1 种子、相隔 2-4 秒启动」这个我从 06:09Z 起固定使用的配置 ——
同秒开局是它的结构性副产品,不是偶发。

**对 §AF.3 那件任务的直接影响(已逐个查过,不是泛泛提醒)**:bisect 的 40 个 slot1
`.dem` 里有 **3 个 basename 撞车**:

- `20260819_180855_slot1.dem` ×3 —— 臂 A 的 863/864/865,**三个都是暖场局**;
- `20260819_201016_slot1.dem` ×2 —— 臂 B 的 863/864,**两个都是暖场局**;
- `20260819_201920_slot1.dem` ×2 —— **臂 B 863 radiant 与臂 B 866 radiant,两个都是镜像局**。

⇒ 若从 `replays/` 取语料,**32 个镜像局会变成 31 个,且那一个的种子归属是错的**
(两个候选都是臂 B radiant,所以臂归属侥幸不受影响,种子归属受影响)。
**规避方法零成本:一律从 `soak/<run>/` 按 run 分目录取,40 个文件一个不少、归属明确**

`soak/` 侧对象数与 basename 数之差(25)是上界也是最可能值;(2) `replays/` 里那 1 个
