## 四、本轮两条结构性发现

### 4.1 按需补跑机的终止码按构造读不到(#685 第二例,已评论)

```
awsx ec2 describe-instances --instance-ids i-0bcc97464e10626a7 i-0409f3a0062f31507
{ "Reservations": [] }
```

**做了对照实验**,因为空结果本身有歧义:故意写错的 id 报 `InvalidInstanceID.Malformed`
⇒ 格式合法的 id 拿到空 `Reservations` 是**老化**不是 not-found。按需机**无 SIR 可退**。

⭐ **比 #685 立案时多出来的信息:这不是「收割晚了」,是排班周期与保留期不相容。**
保留期 ~1h;补跑机 `03:19:5xZ` 起飞、约 `04:03`/`04:14Z` 结束 ⇒ 可读窗 ≈ `04:03Z–05:14Z`;
Routine **每 2h** 触发,本轮 `06:0xZ`。**可读窗(~1h)短于排班周期(2h),撞上是运气不是流程。**
而 W64 发波记录的 `harvest_notes (a)` 给的退路是「这些是 spot 机,SIR 不老化」——
**那条退路对 `rerun[]` 不成立**,因为 GH #408 把容量回收的补跑直接送去 `--on-demand`:
**发波轮写下的缓解措施,恰好在它最需要生效的那类机器上失效。**

替代读数已写进 `waves/W64_wave.json:rerun[].survival_hours_LOWER_BOUND`,
**刻意与 `machines[]` 的 `machine_hours`(由 SIR 读出)用不同键名**,免得两个强度不同的量被并池或互相校对。

### 4.2 ⭐ 闸 (iii) 的 accrual 普查看不见补跑机的钱(新开 #742)

本轮 `wave_fence.py --planned 1.10`(裸跑,`FENCE_EXIT=2`)逐字:
