## 7. 章程 4c 缺口立案:**GH #33**(`[harness]`)

章程步骤 4c 要求"若还没有对应 [harness] issue 就开一个"。检索开放/全量 issue
均无对应条目 → 本轮开 **#33**。查清的确切缺口(不是笼统"缺支持"):

- **链路 A(gate 式,现役)**:`spot_run.sh --validate` → `validate_onspot.sh` →
  `soak_side.lua`。有镜像 draft / 定种子 / 换边 / verdict / 自毁,收割脚本
  `recover_verdict.py` 只认它的 stamp `mirror:<cand>:s<seed>:<side>`
  (`recover_verdict.py:41-48`)。**但两侧跑同一棵树**,差别只有 armed 的 gate 集
  —— upstream 基线是另一棵树,**语义上表达不了**。
- **链路 B(ref 式,旧)**:`aws_run.sh --old/--new` → `make_ab_build.py` →
  `ab_deploy.sh`,**真能把两个 git ref 装到两侧**且做 fwd/rev 两方向
  (`aws_run.sh:55,61`)。但:无 seed(退回随机 draft,SD≈600 GPM/局的噪声地狱)、
  stamp 写成 `ab:<old>..<new>:R=NEW,D=OLD`(`ab_deploy.sh:33`)**收割脚本对它失明**、
  不往 `validation/` 传 verdict、且 `git fetch origin <裸 SHA>` 默认不可行
  (基线得先打 tag)。

issue 里给了三级修法建议(先给 `74727e4a` 打 tag → 让链路 B 借用链路 A 的
stamp+seed → 或给 `validate_onspot.sh` 加 `--ref-arm` 模式)和验收方式。
