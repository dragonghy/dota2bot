## 二、⛔ trunk python 是红的,而红的原因是**一个双 id 的 promote 被写进了一个单 id 的字段**

`tests/test_stable_anchors.py` **`SA_EXIT=1`**,唯一一条 FAIL 逐字是:

```

```

**这句话字面为真,而它想说的那件事是假的。** 两个键**都在** `state.json` 里
(`odbuild_PROMOTE_20260906` 和 `illumove_PROMOTE_20260906`,本轮逐个 grep 确认)。
红的是 `iterations/stable_anchors.json:102`:

```json
"state_json_key": "odbuild_PROMOTE_20260906 + illumove_PROMOTE_20260906"
```

而 `tests/test_stable_anchors.py:109-110` 做的是 `a["state_json_key"] in state` ——
**一次字面单键查表**。于是那个 ` + ` 分隔的复合串按构造永远查不到,
**无论两个键在不在**。

⭐ **立案的不是这次红,是它的形状**:`stable-v4` 是本项目**第一个双 id 的稳定版锚点**
(`odbuild` + `illumove` 同 commit promote),而登记表的 `state_json_key` 字段
**从设计上只装得下一个键**。写它的人把两个键名塞进一个字符串,是**唯一能把真相写全的写法**;
校验器读它,是**唯一能读的读法**;两边都对,**red 出在两者之间那个从来没人写下来的约定上**。
下一次任何一个双 id promote 都会复发。⇒ 已开 **GH #579** 交总监(第十三节)。

⚠️ **诚实边界**:这条红**在 main 上**(本轮工作树对 `state.json` / `stable_anchors.json`
一个字节未改),但本轮**没有**跑 `git stash` 复核,所以「main 也红」是**推断**
(依据是本轮改的两个文件与这条断言无关),不是 `git stash` 后的读数。
