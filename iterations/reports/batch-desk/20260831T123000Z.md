### 1.1 ⭐⭐ 本轮 exit 3 的头条 `trunk-red(python)` 是**假红**,证据是 7 次裸跑

开工自检打的是:

```
FAIL  tests/test_rc_wrapper.py
67 passed, 1 failed, 1 uncertifiable
failed: tests/test_rc_wrapper.py
TRUNK RED -- a python test is failing ON THE WORKING TREE.
```

随后在**同一棵未改动的工作树**上,该测试:

- `python3 tests/test_rc_wrapper.py` 裸跑 **BARE_EXIT=0**,34 条 check 全 `ok`(1 次);
- `bash tests/run_py_tests.sh` 重跑读作 **`PASS tests/test_rc_wrapper.py`**、
  **`68 passed, 0 failed, 1 uncertifiable`**(1 次);
- 再连续裸跑 **5 次,全部 BARE_EXIT=0**。

⇒ **7:1**。工作树一行未改,`git status` 在两次读数之间无差异。

**为什么这条值得单独写**:`tests/run_py_tests.sh` 的 header 里已经有一条同族教训
(GH #243:exit 2「没跑成」被升级成 `TRUNK RED`,一轮把整棵树报成红的),
处置是**把 2 从 1 里分出来**。本轮这条**不是 #243** —— 它走的是 `else` 分支
(rc 既非 0 也非 2,即**真的跑了、答案错了**),而重跑 7 次都对。
所以 #243 修好的那个轴上没问题,**红在另一个轴上:这个测试本身是 flaky 的**。

**失效方向**:**朝吵闹那一侧**(cry wolf),不是朝「静默放过」那一侧 ——
它不会漏掉真红。**但代价不为零**:铁律 10 逼每个 stream 每轮读这个退出码,
一个会随机报红的头条会**训练读者把 exit 3 当噪声**,而 exit 3 正是本轮
`cadence` 那条真发现所在的同一个数。

**机制假设(是假设,不是结论)**:该测试大量使用子进程、`SIGTERM`(check 20/21 断言
退出码 143)、临时文件与 500 行长输出;假红那次,容器正**并发读一个 831KB 的章程文件**。
计时/信号类断言在负载下偶发是已知形状。**本台不改 harness**(章程明令),
只把读数和复现次数交出去 —— 见 §5 交棒 ①。

> **诚实边界**:上面那 7 次全在**同一台容器、同一段负载条件**下跑;它证明的是
> 「这个红不可复现」,**不是**「这个测试在任何机器上都稳」。真正的修法要看
> 到底哪一条 check 当时挂了,而**假红那次的逐条输出已随 `head`/`tail` 丢掉**
> —— 这本身就是给 #新 issue 的第一条建议:**runner 把 FAIL 的逐条输出留档**。
