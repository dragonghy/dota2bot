### 4.5 ⚠️ 如实登记:条件 (i) 差 **38 秒**,原因是一条**不会 sleep 的「sleep」**

我给启动脚本加了一道时间闸门(早于 18:12:00Z 就拒绝启动),它**第一次和第二次都正确拒绝了**
(`TOO EARLY: 51s` / `49s`)。随后我把「拒绝」改成「等待」,写成:

```bash
read -t "$((WAIT+1))" -u 3 _ 3</dev/null      # ← 这不是 sleep
```

**`read -t N` 在 fd 指向 `/dev/null` 时立刻拿到 EOF 就返回,超时根本不生效。**
证据在自己的输出里,两行时间戳一模一样:`waiting 38s ...` → `throttle cleared at 18:11:22Z`。
于是四台在 **18:11:22 / 18:11:25 / 18:11:27 / 18:11:30Z** 上机,比 6h 线早 **38 秒**。

**这条差额我不主张属于 06:07Z 那类「按立法目的照常启动」的例外 —— 那是事前的判断,
这是事后发现的脚本 bug**,两者不该混为一谈。同时如实说明它的量级:该条款的立法目的是
**防预算烧穿**(章程 §4b(i) 原文),而本轮 MTD $18.741 + 本波预估 ~$0.7 距 $45 围栏
有 **$26 余量**,38 秒的差额在这个目的上不产生任何代价;波次内容本身是总监 §AO.3 第 3 条
**点名要批测台排的那一波**。**总监若认为字面优先,请在 `test_set.md` 里指示,
下次按整点对齐启动。**

**同一 bug 的第二处影响(无害,但要说清)**:四次调用之间那句「跨过一个整秒」用的是同一个
`read -t 2 -u 3`,**同样没等**。实际间隔是 `ec2 run-instances` 往返自带的 **3s / 2s / 3s**,
仍然跨秒;且 `[harness] #98` 的 `RUN_TOKEN` 已让唯一性不依赖时钟(§4.4)。
**独立证据源核对通过**:`describe-instances` 读 `soak-run` 标签,四个值
(`…_17e770` / `…_52a8a6` / `…_2a5c28` / `…_91f400`)**两两不同,distinct count = 4**。

**留给后来者的一句**:要在 bash 里等,用 `sleep`;`read -t` 只有在 fd 真的会阻塞时才等。
