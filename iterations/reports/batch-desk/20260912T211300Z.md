## 三、⭐⭐ 头号:围栏的 `11.3h` 被实测顶穿,失效方向是「可以多花」

### 三.1 常数自己声称的是什么(第一手读源码,非转载)

`tools/batch_test/soak/wave_fence.py:306-310` 逐字:

```
# Ruling 6.  The upper end of the documented ActualSpend lag.  A wave launched
# more recently than this before the budget snapshot cannot be assumed to be in

ACCRUAL_LAG_MAX_HOURS = 11.3
```

⇒ 这个常数**明确以「上缘」的身份承重**:比它更早的波被**静默**当作已落账。

**只**把 `last >= cutoff` 的波列进 `un-accrued?`(`:739`);列不进去的波**不进 `must cover`,也不触发 Ruling 6 的 `exit 2`**(`:889` 的 `if wave_rows:`)。

### 三.3 ⭐ 为什么这条的失效方向是危险那一侧(量化,用本轮真实数字)

**本轮没出事,是因为快照恰好很旧** —— cutoff 被推到 `00:50:45Z`,两波都落在其后,围栏因此
**保守地**点名了它们。**⚠️ 那是快照失效救了围栏,不是围栏做对了。**

设想快照**正常刷新**到 `21:00Z`(这正是它该有的样子):cutoff = `21:00Z − 11.3h` = **`09:42Z`**。

- W68 末台 `03:26:12Z` **< cutoff** ⇒ **不列入** `un-accrued?`;
- W69 末台 `09:26:31Z` **< cutoff** ⇒ **也不列入**。

⇒ `wave_rows` 空 ⇒ `:889` 的 `if wave_rows:` **不成立** ⇒ 不打 Ruling 6 的 `UNCERTIFIABLE`,
而是走 `accrual check : CERTIFIED ZERO` ⇒ **`pending=$0.000` 成为「可认证」的**,
操作员读到的 `must cover` 是 **0 波**。于是:

```
projected = MTD 86.758 + pending 0 + planned 1.10 = $87.858   < $90 刹车  ⇒ 围栏放行
真实值    = 86.758 + 2.20(W68+W69 真的没落账)+ 1.10 = $90.058 > $90 刹车  ⇒ 本该拒绝
```

⇒ **围栏会放行一发把 MTD 推过 `$90` 刹车的波**,而三道闸(围栏、刹车、每 $50 找 owner)
**都不会有人举手**。这与 GH #603 立案时点名的那一族**同形同向**,只是发生在它的**修复**
(Ruling 6)**之内**:修复把洞从「无限宽」收成「`11.3h` 宽」,而本轮实测说**真实滞后比它宽**。
