## 5. 本轮真正值钱的:**第十二条世界断言,而且在地图的另一边**

**`--roles` 结构上够不到敌人。** 不是生成器少写(它把**十个**英雄的抽签位置全写进
`roles` 表,loader 也把十个全 `rawset` 成了 `assignedRole`),是读的那一头把敌人那五个**扔掉**:

```lua
-- bots/FunLib/aba_role.lua:392+
bot.assignedRole = role                            -- fixture 给的值,写进去了
if GetTeam() ~= bot:GetTeam() then
    role = GetEnemyPosition(bot:GetPlayerID())     -- 立刻被覆盖
    if role ~= nil then return role end
    return 3                                       -- 地板
end
```

`GetEnemyPosition` 读的缓存只有 `enemy_role_estimation.UpdateEnemyHeroPositions()` 会填,
而 **loader 一次都没调过**(`rf.load` 开头 `reset_modules()`,缓存每次全新且空)。

**全语料实测(不是论证)**:

```
93 个 fixture / 465 个敌方英雄 / 读到非 3 的:0
```

⇒ **本仓库每一个 fixture 上,`J.IsCore(敌人)` 对五个敌人全都是 true。**
这正是 GH #53 在我方那边终结掉的那种坍缩(#27 无 `vis` ⇒ 人人可见、#36 无大招标记 ⇒ 大招门全空转、
test_set.md §F `GetTower = nil` ⇒ TP 全落泉水),**只是没人在敌方那一侧看过**。
已写成 `test_fixture_roles.lua` 的**全语料棘轮用例**(~1.9s)+ 一条**源码钉子**
(敌方分支必须仍然覆盖 `role`、仍然 `return 3`、**不得**读 `assignedRole`),
所以它既不能悄悄变对,也不能悄悄变错。

**顺带量出来的第二件事:估计器现在跑得起来了。** `UpdateEnemyHeroPositions()` 要
`GetUnitList(UNIT_LIST_ENEMY_HEROES)`,那个在 2026-08-20 之前**每个 fixture 上恒为空**
(总监 §0b 第九条修好的面),所以这个问题**以前问不出来**。手动 warm 一次:

| 敌人 | **抽签** | **估计器** |
|---|---|---|
| bristleback | 3 | **1** |
| zuus | 2 | **3** |
| earthshaker | 4 | **2** |
| juggernaut | 1 | **5** |
| jakiro | 5 | **4** |

**是 1..5 的一个置换,与抽签一致 0/5。**

**这不是给估计器判死刑**:它读的是观察到的补刀/线上表现,和「种子抽签给了什么位置」本就是
两个问题。**能报的是**:`J.GetPosition` 用**同一个名字**,对友军答**抽签**、对敌人答**估计**,
消费方分不出来 —— 而在 fixture 上,它对敌人答的是一个**常数**。

**本轮不修**:让 loader 调估计器会**一次性移动全部 93 个 fixture 的敌方位置**,
而 `test_fixture_roles.lua` 存在的全部意义就是不许发生这种事。
⇒ 钉成 characterisation,**把决定权交给总监**(GH #81,见 §7),并**把估计器的答案先记进用例**,
这样将来谁要动,改动的体量是已经在案的数,不用重新量。

**这条对全组的直接影响**:凡是在 fixture 上 fork 在**敌人**位置或 `J.IsCore(敌人)` 上的断言,
**读的都是常数 3 / 常数 true**,和它来自的那一局无关。(本组自己这一帧不受影响 —— guard 零读取。)
