## 1. 我要找的泄漏(先把假说写清楚,免得事后改口)

`J.TryTakeTpResponseSlot()` 是一个**模块级台账**,全队 6 秒只发一张票:

```lua
local tTpQuota = { t = -999, n = 0 }
function J.TryTakeTpResponseSlot()
    local nNow = DotaTime()
    if nNow - tTpQuota.t > 6.0 then tTpQuota.t, tTpQuota.n = nNow, 0 end
    if tTpQuota.n >= 1 then return false end
    tTpQuota.n = tTpQuota.n + 1
    tTpQuota.t = nNow
    return true
end
```

两个消费方(`J.GetRescueTpTarget` = `lf_rescue`,`J.ShouldTpSupportTowerFight` = `midtp`)
**在 helper 内部就把票取走**,而**要不要真的放 TP 是调用方之后才决定的**:

```lua
local hRescueAlly = J.GetRescueTpTarget( bot )          -- 票在这里就没了
if hRescueAlly ~= nil then
    local vRescueLoc = J.GetNearbyLocationToTp( hRescueAlly:GetLocation() )
    if vRescueLoc ~= nil then                            -- ← 如果这里能是 nil…
        return BOT_ACTION_DESIRE_HIGH, vRescueLoc, 'ground', '救援TP'
    end
    -- …就会掉出来:票花了、TP 没放
end
local hTowerFight = J.ShouldTpSupportTowerFight( bot )   -- 而且下一行的 midtp 也被自己人堵死
```

**假说**:落点解析失败 ⇒ 票被吃掉、TP 没发,**全队 6 秒内没人能再响应**,
并且**同一帧同一个 bot 的 `midtp` 被自己的 `lf_rescue` 顺手堵掉**。
这正好是 #37「lf_rescue 真的会触发但 11 次里 7 次从未抵达」那笔经济账想找的那类浪费。

## 2. 头条结论:**泄漏不存在**,而且是结构性的不存在

`J.GetNearbyLocationToTp` 是一个**全函数(total)**:

```lua
function J.GetNearbyLocationToTp( nLoc )
    ...
    if J.GetLocationToLocationDistance( nLoc, nFountain ) <= 2500 then return nLoc end
    ...
    if targetTower ~= nil then return J.GetLocationTowardDistanceLocation( targetTower, nLoc, 575 ) end
    return nFountain          -- ← 无条件兜底
end
```

**函数体里没有任何 `return nil`,也没有裸 `return`,末尾是无条件 `return nFountain`。**
(`nFountain` 来自 `J.GetTeamFountain()`,它是 `DireFountain`/`RadiantFountain` 二选一,
也不返回 nil;真为 nil 的话第一行就 error 了,那是**抛错**不是**返回 nil**。)

⇒ 两个调用方的 `if vRescueLoc ~= nil then` / `if vTpLoc ~= nil then` **是死代码**,
`lf_rescue` 取到票之后**结构上不可能掉出来**,`midtp` 也就**不可能被自己人堵**。
**假说 (ii) 作废。**

两条独立取证,都写成了断言(单独一条都不够:读源码排除不了运行期抛错,四帧排除不了没走到的分支):

1. **源码穷举**(test 1):`J.GetNearbyLocationToTp` 函数体内 `return nil` 计数 = 0、裸 `return` 计数 = 0、
   `\treturn nFountain\n` 存在。
2. **四个真实帧实测**(test 2):GH #37 验收三帧 + `lf_rescue` keystone 帧上,
   `J.GetNearbyLocationToTp(ally:GetLocation())` **均返回真实坐标**(非 nil、带 x/y、距离可用)。

顺带把另外两条也钉掉了:

- **两个 helper 各自只有一个调用点**(test 4 的前置 + grep 复核)⇒ 不存在「出价评估顺手把票吃掉」那类泄漏;
- **取票在两处都是 `and` 链的最后一个合取**(test 8)⇒ 不存在「取完票后面还有条件会否决」。
  这一条的验收**第一版是空的**(见 §4 M7),已改成断言「该行在调用之后只允许跟一个 `then`」。

**顺带澄清一条本组自己写在章程里、但已经不成立的担心**:`hRegen`(`J.LaneRegenItemToUse`)
确实排在**整个物品循环之前**并且会 early-return,但它**挂在 `J.IsLaneFixOn('salve')` 上**,
而 `lanefix` **不在 armed 集里** ⇒ 当前波次它是惰性的。已写成断言(test 10),
免得哪天 arm 它的时候没人意识到那同时是一次 TP 响应链的改动。

## 3. 第二条结论(**变异跑出来的,不是读出来的**):台账的时间戳是双写,单删任何一个都是无声的

变异 M6 本来是想证伪 test 7「窗口从最后一次成功取票起算」。结果 **M6 删掉取票路径的
`tTpQuota.t = nNow` 之后,10 条断言全绿** —— 即我第一版的 test 7 **是空的**。

追下去发现的是一条真东西:**`tTpQuota.t` 在两个地方被写**,而**每一个单独看都是 dead store**:

| 变异 | 结果 |
|---|---|
| 只删**重置分支**的 `tTpQuota.t, tTpQuota.n = nNow, 0` 里的 `t` | **行为逐位不变** |
| 只删**取票路径**的 `tTpQuota.t = nNow` | **行为逐位不变** |
| **两个都删** | `nNow - tTpQuota.t` 永远 > 6 ⇒ 每次调用都重置 ⇒ **`TryTakeTpResponseSlot` 永远返回 true** |

机制:能走到取票路径的前提是 `n == 0`,而 `n` 只被重置分支和初始化器置 0;初始化是 `t = -999`,
Dota 开局 `DotaTime()` 约 −90 ⇒ **第一次调用必然触发重置分支**。所以取票路径那次 stamp
**在任何可达状态下都是冗余的** —— 反过来也一样。

**为什么这值得钉住**:两个都删之后,**全队配额静默变成无限** ——
fix B 要治的「COLLECTIVE TP(≥3 个英雄同一瞬间 TP,3 张卷轴 + ~200s 步行换零干预)」原样复发,
**没有报错、没有日志、没有任何别的测试会红**。而这恰恰是最容易发生的删法:
一个 reviewer 删「那句冗余赋值」**第一次是对的,第二次是灾难性的**,
而第一次的安全正好是第二次的理由。

⇒ test 7 改写成断言**两处 stamp 都必须在**,并在失败信息里写明「另一处若也没了配额就废了,
先回来读这个测试」。改写后 M6b / M6d 两个单删变异**各自都红**。

**未验证的边界(如实登记)**:`tTpQuota` 是不是**全队一份**,本 harness 判不了 ——
mock 每个测试都新载一次 `jmz_func`,每 bot 一份 VM 在这里看起来完全一样。
shipped 设计的注释断言它是共享的(`jmz_func.lua:5700`),只有游戏内观察能定这件事。
所以 test 5-7 钉的是**台账的算术**,那才是这段代码真正控制得住的东西。

## 4. 仍然成立的那一半:TP 卷轴在物品循环里排第七

假说 **(i) 没有被推翻**,已钉成 test 9:`nItemSlot` 字面量 `{ 5, 4, 3, 2, 1, 0, 15, 16 }`,
**第 7 位才是 15(TP 卷轴槽)**,前六位全是主物品栏。循环是**首个 desire>0 即 return**,
⇒ **任何当帧想用主物品栏里某件东西的 bot,当帧根本不会评估 `ConsiderItemDesire["item_tpscroll"]`**,
`lf_rescue` / `midtp` / `suptp` 三条响应一并被跳过。

**本轮不动它,理由**:抢跑的物品多数是**一帧性**的(用掉即进 cd),下一帧 TP 就轮得上,
所以「排第七」到底是**一帧延迟**还是**持续饿死**,取决于**earlier slot 连续赢多少帧** ——
这是个**要数语料**的问题,不是读源码能答的,照一个静态形状去改共享消费路径正是 `lanefix` 的入口。
**已交出去的零支出问题(见 §6)**:在已付过钱的语料上数这个数。
