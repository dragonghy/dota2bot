## 2. ⭐ 缺陷:`GetRespawnTime()` 已经是剩余时间,而算「剩余时间」的那行又减了一次 elapsed

`bots/ability_item_usage_generic.lua:368`(出厂):

```lua
function X.GetRemainingRespawnTime()
    if fDeathTime == 0 then return 0
    else return bot:GetRespawnTime() - ( DotaTime() - fDeathTime ) end
end
```

`docs/BOT_API_REFERENCE.md:992` 逐字:**`GetRespawnTime()` → "Seconds until this hero
respawns"** —— **已经是剩余时间,自己在倒数**。

设 R = 复活时长,e = 死后经过秒数。引擎给回 **R − e**,这个表达式返回 **R − 2e**:

- 读数**以两倍钟速衰减**;
- 在 **e = R/2**(死亡过程**正中间**)穿过 **0**,此后为负,而英雄还要再躺 R/2 秒。

**产生这段函数体的读法,名字自己招了**:同一个 getter 在 15 行外被存进一个叫
**`nFullRespawnTime`** 的 local(`:565`)。只有把 getter 读成**恒定的完整时长**,
再减一次 elapsed 才是算术而不是缺陷。**一个 getter,两处,同一个误读。**

### 2.1 方向是单向的:只会关掉本该允许的买活

三个消费方**全是这个数的下界**:

| 行 | 门 | armed 的真实窗口 | 出厂(R−2e)的窗口 |
|---|---|---|---|
| `:574` | `nRemainingRespawnTime > 20`(守遗迹) | e < R−20 | **e < (R−20)/2** |
| `:584` | `nRemainingRespawnTime > 80`(24 级归队) | e < R−80 | e < (R−80)/2 |
| `:596` | `nRemainingRespawnTime < 40` → return | e > R−40 | **e > (R−40)/2** |

**而且后半程恒 ≤ 0** ⇒ 每一次死亡的**后半段**,三个门全关。
