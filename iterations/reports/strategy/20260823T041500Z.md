## 3. 缺陷:claim 是被「问」烧掉的,不是被「去」烧掉的

`J.ShouldAllowDefendTp` 的戳记写在 query 的**末尾**:任何一个 query 返回 true 的 bot
都拿走了 12s / 1600u 的 claim。但它的调用方**问完之后下一行还能拒**:

```lua
if botAmount.distance > nMinTPDistance            -- 离那条路多远
    or botAmount.amount < laneFront / 5           -- 落后兵线前沿多少
then tpLoc = X.GetDefendTPLocation( nDefendLane ) end

if tpLoc ~= nil and not J.ShouldAllowDefendTp( bot, tpLoc ) then tpLoc = nil end   -- 问(并戳记)

if tpLoc ~= nil
    and GetUnitToLocationDistance( bot, tpLoc ) > nMinTPDistance - 500             -- 直线距离
then ... return BOT_ACTION_DESIRE_ABSOLUTE end                                     -- 才真的去
```

**赋值那两条腿和拒绝那一行读的是两个不同的量**:前者是「离那条路多远 / 落后前沿多少」,
后者是**到目的地的直线距离**(`nMinTPDistance = 5500`,阈值 5000;12 级且离泉水 <600 时 5600/5100)。
两者**例行不一致**:

- 一个**待在自家基地、而中路正被围**的 bot:`botAmount.amount < laneFront/5` 成立
  (它离前沿很远),而中路二/三塔离它常常**不到 5000** ⇒ 过第一行、挂第二行。
  **这正是 Turbo 后期最常见的守家场面。**
- 一个**站在另一条路上**的 bot:`botAmount.distance > 5500`(离目标路很远)成立,
  但到那条路 tower 的**直线距离**可以只有四千 ⇒ 同样过第一行、挂第二行。

⇒ 它**根本不会 TP**,而它刚拿走的 claim **把四个真能应答的队友挡了 12 秒**。
**仲裁翻转:唯一的应答名额发给了那个不会去的 bot。**

### 修法(一个变量)

- `bots/FunLib/jmz_func.lua`:query 末尾的戳记改成
  `if not J.IsSoakCandidate('tpclaim') then J.NoteDefendTpClaim( bot, vLoc ) end`,
  新增 `J.NoteDefendTpClaim`;
- `bots/ability_item_usage_generic.lua`:在**已经过完全部拒绝、正走向
  `BOT_ACTION_DESIRE_ABSOLUTE` 的那一行**(现有 `tpRespondLoc` 戳记旁)加一次
  `J.NoteDefendTpClaim( bot, tpLoc )`。

**问不等于答。**

### 未 armed 时逐字节等价(两个方向都断言了)

- `tpclaim` 关:query 照旧在原处戳记;调用方新增的那一次是**同一帧、同一个 bot、
  同一个点**的重写 ⇒ claim 状态一模一样(`[off-candidate equivalence]` 直接对读两条路径的裁决)。
- `teambrain` 关:整个仲裁在读 claim **之前**就 `return true` 了 ⇒ 单独 arm `tpclaim`
  什么也打不开(`[transparency]` 对 `{}` 和 `{tpclaim}` 两种组合都断言)。
- 非 Turbo:同上,`[non-turbo]` 断言。
