## 1. 主判据(闭式,可由源码顺序证明)

`bots/mode_team_roam_generic.lua` 里有**两对**「GetDesire 写、Think 读」的句柄:

| 句柄 | 复位 | Think 消费位次 |
|---|---|---|
| `hTargetCreep` | **每个 turbo 帧**由已 promote 的 `roamstale` 在 `GetDesireHelper` 顶部清 | `:587`,**第一条** |
| `towerCreepMode` / `towerCreep` | 只有 (i) `DistanceFromFountain() > 4600` 块里的 `else`,(ii) `OnEnd()` | `:612` |

而 `Think()` 的投递顺序是

```
:587 hTargetCreep    -> Action_AttackUnit(h, true),           return
:612 towerCreepMode  -> Action_AttackUnit(towerCreep, false), return   <-- 这一条
:621 ShouldHelpAlly  -> Action_AttackUnit(targetUnit, false), return
:628 core / support  -> Action_AttackUnit(targetUnit, false), return
```

**⭐ `:612` 排在 `:621` / `:628` 之上,而 `:621` / `:628` 正是 `GetDesireHelper` 每一条早返回分支
(`ConsiderHelpWhenCoreIsTargeted` 0.98 / `ConsiderHelpAlly` 0.98 / punish-dive 0.98 /
punish-over-chase 0.98 / `l1trade` 0.92 / `l5combo` 0.92 / `CarryFindTarget` / `SupportFindTarget`)
唯一的落点。** 所以一个陈旧的 `towerCreepMode` **不是打错目标,是把赢下竞价的那条分支整个取消掉**:
出价说「去救被集火的核心」,这一帧执行的是「继续打上一帧那只塔下小兵」。

**为什么复位覆盖不到那些帧**:`GetDesireHelper` 内唯一的复位躺在 **16 条 `return` 之下**
(数字从树里数,钉在测试里),取其中任意一条的帧都原样保留上一帧的值;而另一个复位 `OnEnd()`
只在**该 mode 不再赢**时触发 —— 那恰恰是 `Think()` 根本不会被调用的那一种情形。

## 2. ⭐⭐ 这条合同**就写在同一个函数的头上**,并且只被兑现了一次

`GetDesireHelper` 开头那段 `[roamstale]` 注释把这套机制**逐字讲清楚了** —— 句柄写在下面、从不复位、
`Think()` **第一个**读它并 `return`、于是出价算出来的那个集火目标一次都没被碰过 ——
**还把发生这件事的分支一条条点了名**(与上表同一批)。然后它修了这套推理覆盖的**两个句柄里的一个**。
两个句柄相距不到两屏,在同一个函数体内。这是 `0S`/`0S2` 那一族(「同一条合同两份」)的新形状:
**不是两个文件各一份,是同一个函数里的同一条推理,只被应用到它自己列举的对象之一。**

**⭐⭐⭐ 而且「照抄那条已 promote 的行」是错的修法**,理由是一条本轮钉住的不变式:
`towerTime ~= 0` 与 `towerCreepMode` 在出货代码里是同一个比特(三处写入两两成对,已断言),
但**「仍在窗口内」那条分支 `return` 之前不重新确认这个 flag**。所以把
`towerCreepMode = false` 放在 `roamstale` 那一行旁边,会把一次**正在进行中**的塔下小兵攻击关掉 ——
`roamstale` 自己的安全性论证(「只会移除陈旧攻击、绝不新增」)**不覆盖这一步**。
正确的修法要多一句「仍在窗口内时重新确认」,这一句在出货世界里可证是 no-op(由上述不变式)。
这条差异已写成断言:它一旦不成立(有人给那条分支加了重新确认),测试会自己红。
