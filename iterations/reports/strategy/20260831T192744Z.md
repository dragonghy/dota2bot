## 2. 缺陷

`bots/mode_team_roam_generic.lua` 的 `Think`(出厂形状):

```lua
if isInIdleState then
    isInIdleState = J.CheckBotIdleState()
end
```

**这个块对控制流零影响** —— 块以下没有任何地方再读 `isInIdleState`。
**但被调方不是查询**:`J.CheckBotIdleState` 在恢复分支里**下命令**,
`bot:Action_ClearActions(true)`(`jmz_func.lua:11994`)+
`bot:ActionQueue_AttackMove(laneFront)`(`:11998`)。
**往下十一行**,只要 `targetUnit` 有效,同一个 `Think` 就发
`bot:Action_AttackUnit(targetUnit, false)`;而一条 `Action_*`
**「CLEARS the entire action queue and sets this as the new (and only) action」**
(`docs/BOT_API_REFERENCE.md:1715`)。

⇒ **恢复命令在发出它的同一帧被销毁**,而且**恰好在这个 mode 自己制造的那个情形里**被销毁
(有漫游目标)⇒ **反卡死恢复在最需要它的场景里是个 no-op。**

### ⭐ 主判据(可复用,超出本主题)

**一个调用方不可能为一件它不知道发生过的副作用排序。**
写成裸语句的「状态刷新」——返回值被赋值、然后从不被分支读——**读起来像查询,也就被当查询审计**;
若它其实**下了命令**,同一函数里下一条无条件的 `Action_*` 就把它抹掉,而调用点手里没有任何东西能拦。

**与两个同族区分清楚**(都是「守卫/推理对不上消费点」,**因**不同):
GH #368 是**作用域**(同名不同变量);GH #348 是**顺序**(判 `nil` 前一行就索引);
**本条调用方对任何一个值都没判断错 —— 它缺的是被调方从来没汇报过的一件事实。**

### ⭐⭐ 第二条互相独立的后果(**登记,本轮不修**)

它**每帧重复一次,不是每 3 秒一次**:`return true` 排在刷新采样锚点的两行
(`botState.botLocation` / `botState.lastCheckTime`,`:12010-12011`)**之上** ⇒
**idle 一旦闩上,`>= 3s` 的门再也关不上**;两个出厂调用点于是各自走每帧路径
(`:259` 的 `... or isInIdleState`,以及 `Think` 那个块)。
被抹掉的 `Action_ClearActions(true)` 因此**每帧落在其它所有系统排进队列的动作上一次**。
**一次只动一个小杠杆** ⇒ 这一条是下一格。
