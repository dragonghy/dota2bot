## 1. 为什么验收形状此前无法表达(两处 mock 保真度缺口)

总监在 §0b 立的规矩:**动作类缺陷,验收要断言动作在世界里的真实后果**
—— 这一例该断言的是「**落点到友军的距离**」,不是「门返回了一个目标」。

但落点由 `J.GetNearbyLocationToTp` 决定,而它在**每一个 fixture 里**都走了
退化路径:

1. **`tests/mock/bot_api.lua:264` 把 `GetTower` 桩成 `nil`。**
   `J.GetNearbyLocationToTp` 的塔循环因此永远空转,函数直接落到
   「一座塔都不剩」的兜底分支 —— **返回泉水**。也就是说:**在此之前,
   本仓库任何一个关于 TP 落点的 fixture 断言,测的都是一条真实对局里
   (塔还立着时)不会发生的退化路径。** 同一个缺口还让
   `J.GetRescueTpTarget` 的「友军站在自家塔下就别救」否决恒为 false
   (它扫 `UNIT_LIST_ALLIED_BUILDINGS`,而 mock 返回 `{}`)。
2. **mock 的 `Vector` 没有 `__div`。** 落点是
   `J.GetLocationTowardDistanceLocation` 用 `(b - a) / dist` 归一化算出来的,
   所以**即使**把塔接上,一碰到真塔就会 `attempt to perform arithmetic on a
   table value` 直接崩。两处缺口互相掩盖,所以此前谁也没撞见。

这是本组连续第二轮补 mock 保真度缺口(上轮 4 处,见
`20260819T113516Z.md`),同属 §0b 那一族:**验收只测了 helper 的返回值。**

### 改动(全部在 dev-only 目录)

- `tools/batch_test/replayscope/make_fixture.py`:输出 `buildings`
  (塔/兵营/遗迹/前哨的 name/team/x/y/alive,取 ≤ t 的最新采样)。dumper 早就
  在落这份数据(`buildings` 数组),只是 fixture 生成器一直把它丢掉。

  dump 不记录塔的 `TOWER_*` 枚举槽位,只有类别/坐标/队伍;而所有 shipped 读者都是
  `i=0..10` 扫一遍再做归约(最近/计数/还在不在),**集合才承载语义,顺序不承载** ——

## 3. 两条结论(本轮的实质产出)

### (i) 候选改法 1「落点距离门」被这三帧**证伪**

录像组给的分布提示阈值在 **1200-1600**,总监把阈值留给本组钉帧后定。钉完的答案是:
**这个家族做不到。**

> **必须拒绝的 B 落点 1579,比必须放行的 C 落点 1746 还要近。**

任何砍掉 B 的天花板都会连 C 一起砍掉 —— 而 C 是本波**唯一一次按设计工作的救援**。
这正是 `lanefix` 教训要防的「连好的一起改掉」。录像组自己也标注了 n=11 不足以由
它们定阈值,这条自律是对的:真按 1200-1600 落一刀,就会把唯一有效的那次删掉。

(录像组报的 B/C 距离是 1857/1585,与我重建的 1579/1746 **顺序相反**。差异来自
只取 `tower` 类 + 结构 5s 采样;两个数都在 1.5-1.9k 这一档,**无论取哪一版,
B 与 C 都相距不到 300 码,距离维度上根本不可分**。结论不依赖哪一版更准。)

### (ii) 候选改法 2「把落点距离喂回生存窗口」**能分开全部三帧**,余量充足

用录像 ground truth(友军血量轨迹)按「到达时刻 = 3s 读条 + 落点步行」结算:

| 帧 | 窗口 | 友军在窗口内掉的血 | 判定 |
|---|---|---|---|
| A | 21.7s | **430 / 430**(打空) | 拒绝 ✅ |
| B | 8.3s | **225 / 225**(打空) | 拒绝 ✅ |
| C | 8.8s | 159 / 246 | 放行 ✅ |

**两个方向都有余量**(A 超预算 4.6 倍、B 超 2.9 倍、C 富余 17 倍),所以对移动速度
取值不敏感(本仓库 mock 用名义 300,真实 285-330 翻不动任何一条)。

### 顺带证实的第三点:**shipped 的生存门本身分不开任何东西**

`J.WillAllySurviveTpWindow` 在**三帧上全部返回 true** —— 包括两个必须拒绝的。
原因是机制性的:它那 **4.0s** 预算**全花在读条上**,一点没留给落地后要走的路
(注释自己写的是「3s 读条 + 一步」,而实测「一步」是 5.3-18.7 秒)。
所以这不是「阈值调松了」,是**被测量的量本身就不含那段路**。

## 4. 验收(新测试 `tests/test_lf_rescue_landing_reach.lua`,6 例)

- 三帧全部**驱动真的 `J.GetNearbyLocationToTp`**,断言的是**落点到友军的距离**
  (§0b 要求的「动作的真实后果」),不是 helper 返回值;
- 前提是**断言出来的**:>3500 跨图、友军 <35%、鏖战侧仍有 9-11 座塔立着、
  落点**不是**泉水(否则说明塔没接进去);
- 一条**证伪断言**(B 落点 < C 落点)+ 一条**候选 2 可分性断言**;
- 一条**回归护栏**:没有 `buildings` 的老 fixture 世界逐字节不变
  (`GetTower` 仍为 nil、落点仍退化成泉水)——它同时也是这个缺口本身的存档;
- **两次变异测试**:拆掉塔接线 → 恰好 3 条断言 FAIL;拆掉 `Vector.__div` →
  恰好 4 条 FAIL(其余 444 条既有测试在两次变异下都不受影响)。

**450/450 测试(基线 444)+ `luacheck bots game --formatter plain` 0 警告。**

诚实边界(已写进测试头注释):dumper 的 DAMAGE 事件**漏计**守卫/召唤物/小兵伤害
(帧 B 实测事件和 117,而 lich 那 4 秒真掉了 242 血),所以 fixture 的 `burst` 是
**下界**,偏向「友军能活」——这偏差的方向**不利于**本报告第 3 节 (iii) 的论点,
即结论是保守的。上表的存活时间取自死亡事件,是精确的。
