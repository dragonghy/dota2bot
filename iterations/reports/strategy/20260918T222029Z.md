## 二、缺陷

`bots/ability_item_usage_generic.lua` 的 `X.ConsiderItemDesire['item_smoke_of_deceit']`
(诡计之雾)问的是「**这附近有没有人会把这团雾拆掉**」。出厂写法:

```lua
local isThereEnemyNearby = false
local nInRangeAlly   = J.GetAllyList(bot, nRadius)              -- nRadius = 1200
local nInRangeEnemy  = J.GetNearbyHeroes(bot, nRadius, true, BOT_MODE_NONE)
local nInRangeTower  = bot:GetNearbyTowers(nRadius, true)

if (#nInRangeEnemy == 0) or (#nInRangeTower == 0) then
    for _, allyHero in pairs(nInRangeAlly) do
        ... if 那个**队友**的 1200 里有敌方英雄或敌方塔 then
            isThereEnemyNearby = true          -- 全函数唯一的写入点
    end
end

if not isThereEnemyNearby then ... return BOT_ACTION_DESIRE_HIGH ... end
```

**发问者自己的那两个读数被算了出来 —— 而且 `bEnemies` 旗标是对的 —— 然后被花在了
「要不要去扫队友」这道闸上**;函数里没有任何东西让它们够得到那个答案。
而扫描的主语**永远是队友**:`J.GetAllyList` 就是 `J.GetNearbyHeroes(bot, …, false, …)`,
它**从不返回自己**(`jmz_func.lua:9997` 逐字 *"bot:GetNearbyHeroes never returns self"*)。

⇒ **这团雾罩的那个单位(四行之下的 `hEffectTarget = bot`),正是这个谓词唯一看不见的单位。**
而且它有**三条互相独立的失效路**:

| | 形状 | 帧数(1039 活体主体帧) |
|---|---|---|
| (A) | 1200 里**同时**有敌方英雄和敌方塔 ⇒ 闸为假 ⇒ **那唯一的检查一次都没跑** | 32 |
| (B) | 1200 里**一个队友都没有** ⇒ 循环体永不执行,单人站在敌人旁边读作「干净」 | 153 |
| (C) | 队友扫了、队友自己干净,而那个离**我** 867u 的敌人离他们都 >1200 | 21 |

⭐ **(A) 是最刺眼的那一条**:出厂代码**恰恰因为两种破雾物都在场**才拒绝去跑那个检查。
本轮的真帧证人 `f_260819_122930_lich_rescue_doomed` 的 lina(dire, t=201.3)身上,
敌方 Ogre Magi 882u、敌方塔 860u,而她 305u 外的队友 Necrolyte **自己也读 e=1 tw=1**
—— **闸拒绝去跑的那次扫描,正是会抓到它的那次扫描。**(这一句在测试里是断言,不是散文。)

## 三、为什么这是「遗漏」不是「选择」,以及为什么它不是「已经有人读过了」

**判据用的是 0NEXT48 本轮买到的那一句**:读到两半不一样,先问**另一半有没有这一项**。
这里的另一半就是发问者本人,而它**一项都没有** —— 没有任何一种「谁会拆我的雾」的读法
会让五个队友的圈是决定性的、而施法者自己的圈无关紧要。⇒ **不需要域来证明它错**
(与 `pipetower`、`bbancient` 同判据);下面的域定价的是**它多久咬一次**,不是它错不错。

⭐⭐ **而这个调用点已经被逐个读过了,并且读对了。** `pipetower`(同一个文件、同一天、
往前两轮)的 helper 头逐字写着:*"the other eighteen GetNearbyTowers call sites in that
file -- those were read one by one and the ones passing `true` read the answer as DANGER,
which is the right way round."* 本块的**两处**塔调用都在那十八个里、都传 `true`,
**而那句话对它们是真的**:旗标朝向是对的。
📌 **那次审读定价的是一个读数的【朝向】。这个读数能不能够到答案,是另一个问题 ——
而「为第一个问题查过」的调用点,和「两个问题都查过」的调用点,读起来一模一样。**
这是 0NEXT45(已登记 ≠ 已处理)与 0NEXT47(解释契约的注释不是遵守契约的证据)的**第三种形态**,
也是最便宜的一种:要读的东西**就在上一轮自己写下的那段注释里**。

## 四、修法(一个杠杆)

`bots/FunLib/jmz_func.lua` 新 helper(紧接 `J.GetBackupTowerCount` 之后):

```lua
function J.IsSmokeBreakerNearSelf( tEnemyHeroes, tEnemyTowers )
	if not J.IsModeTurbo() then return false end
	if not J.IsSoakCandidate( 'smokeself' ) then return false end
	if tEnemyHeroes ~= nil and #tEnemyHeroes >= 1 then return true end
	if tEnemyTowers ~= nil and #tEnemyTowers >= 1 then return true end
	return false
end
```

调用点把 `local isThereEnemyNearby = false` 换成
`local isThereEnemyNearby = J.IsSmokeBreakerNearSelf( nInRangeEnemy, nInRangeTower )`
(并把这一行挪到三张表之后)。**disarmed 逐字就是出厂那个 `false`。**

- ⭐ **为什么传表而不是传 bot**:helper 里重新求一遍就意味着**第二对引擎调用 + 第二份半径**
  —— 两个要保持相等的东西,而那正是 `roamring`/`tormring` 付过的账。
  传调用点自己的表,让「同一个圈、同一个 getter、同一个旗标」**由构造为真,不靠审读**。
- **不碰**:1200 半径、闸里那个 `or`、队友扫描、上面 `DotaTime() < 0` 的早返回、
  下面 ROAM/GANK/ROSHAN 三支、任何别的 `ConsiderItemDesire`。
- ⛔ **不是合取**:helper 里只有一个 `IsSoakCandidate`,并且它**不被任何别的 gated helper 调用**
  (`pullcad`,GH #606/#576;`tests/test_gated_helper_nesting_census.lua`)。

**方向由构造定死**:armed 只能把出厂的 `false` 变成 `true`;这个旗标除了
`if not isThereEnemyNearby then` 之外没有第二个读者,而那个 `if` 里的每一支都是
「`return BOT_ACTION_DESIRE_HIGH` 去放雾」⇒ **armed 只能少放雾,永远不能多放一次**。
**批测读数若反向,不能读成「杠杆让 bot 放雾更多」。**

## 五、域与价值 —— 两件不同的事,分开写

**域(`tests/_smokeself_sweep.lua`,112 fixture / 1039 活体主体帧,ring = 出厂的 1200,零 arm)**:

```
enemy hero within 1200 of the caster   438
enemy tower within 1200 of the caster   63
caster has at least one (armed = true) 469
shipped flag true (the ally scan)      292
FLIP (shipped false, armed true)       206     over 84 of 112 fixtures
  (A) 32 | (B) 153 | (C) 21   ← 互斥且相加 = 206
  其中 TOWER-ONLY(圈里有塔、没有敌方英雄)19
```

⚠️ **和 `towerpow` 不同,这里谓词本身是完全可测的**:每一个输入都是几何 + 队伍归属,
.dem 两者都带 ⇒ **206 是「答案变了的帧数」,不是「机会数」**。
⛔ 它**不是**「局数变了」(道具持有与外层分支没有走);⛔ 它是**按主语计帧**不是情形。

### ⛔ 而价值的一半是不可测的,并且登记成「不可测」,不是登记成「零」也不是登记成「满」

真实道具**在敌方英雄或敌方塔 1025 内不能使用**;而引擎的 `IsFullyCastable()`
(`J.CanCastAbility` 在 desire 函数被调用**之前**就读它)有没有把这条限制算进去,
**在这个容器里回答不了**(不许 bot 侧调试,AGENTS.md)。于是按**最近破雾物的距离**切:

```
nearest > 1025    33    施法在引擎侧合法(无论 IsFullyCastable 怎么答),
                        而雾会被那个已经站在那里的敌人下一步就驱散
nearest <= 1025  173    引擎可能本来就拒绝施法;这一半的价值取决于那个没答的问题
```

⇒ **本杠杆只按那 33 帧主张**。⭐ 顺带:出厂的 1200 > 真实的 1025,是保守侧;
**「圈该不该改成 1025」是一个【选择】,是另一个杠杆,登记、不动。**

**还有一条成本,同样挂在那个没答的问题上、也没算进 33**:`X.ItemUsageThink` 按固定顺序
`{ 5, 4, 3, 2, 1, 0, 15, 16 }` 走格子,**在第一个 desire > 0 的道具上就 `return`** ⇒
一次本不该 HIGH 的雾 desire **会把那一帧里排在后面格子的每一件道具都挤掉**,不只是浪费它自己。
