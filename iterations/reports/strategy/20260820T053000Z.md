## 1. 第一个产出:又一条没人声明过的世界断言(结构不可寻址)

fixture loader 此前把 `GetTower(team, i)` 按**存活塔的位置**寻址 —— 对「循环 `i = 0..10` 再归约成最近/计数/还在不在」的读者是够用的,GH #37 那轮只需要这个 —— 而 `GetBarracks` 是 `nil`,`GetAncient` 给**两边队伍**都发同一个位于**地图原点**的 4500 血单位。

mock 把未覆盖的 ALL_CAPS 全局解析成哨兵整数,所以**只问一个具名槽位**的读者 —— `GetTower(team, TOWER_MID_1)` —— 在**每一个 fixture 里**都问的是 `slot <哨兵>`,拿到 nil。

`aba_defend.GetFurthestBuildingOnLaneHelper` 正是这样的读者(`Tower.Top1/2/3` → `GetBarracks` → 遗迹),而 `GetDefendDesireHelper` 紧接着就是

```lua
if not IsValidBuildingTarget(furthestBuilding) then return BotModeDesire.None end
```

⇒ **每个 fixture 里每条路的防守出价都只可能来自这一行之上的七个提前 return,`GetDefendDesireHelper` 的整个下半段结构上不可达**:`ShouldDefend`、`capBoost`/`baseFloor`、panic 地板、`recentlyHit` 衰减、`ConsiderPingedDefend`、tier/血量 remap 全在下面。白话:**「这支队伍在任何一条路上都没有建筑,而且两家遗迹叠在河道里」**。与 `HasModifier`、`WasRecentlyDamagedBy*`、`GetHeroLastSeenInfo` 三条同族。

**修复**(`tests/mock/replay_fixture.lua`,`tools/batch_test/replayscope/make_fixture.py`):

- 槽位**从几何推导**,不写死坐标,且在**全量建筑集**(含已阵亡)上推导 —— 否则掉一座塔会把幸存者悄悄重新编号:
  - 离本方遗迹最近的两座是基地塔(第三近的距离是它们的 ~3 倍,分界不接近);
  - `s = y - x` 分开三条路的走廊(`|s| < 1000` 中路,`s > 0` 上路,`s < 0` 下路)——本仓库 fixture 实测中路塔 `|s| ≤ 513`、最近的一座非中路塔 `|s| = 2160`,**4 倍余量**;
  - 同一条路里离本方遗迹最远的是一塔。
- 装真实的 `TOWER_*`(0..10)/ `BARRACKS_*`(0..5)整数;`GetTower` 对**已阵亡槽位仍返回 nil**(引擎语义);`GetAncient` 发**各队真实遗迹**。
- 建筑补 `OriginalGetHealth`/`OriginalGetMaxHealth`(`J.GetHP` 对己方单位读的是未被 hook 的取值器,此前拿到 nil 直接 `attempt to compare nil with number` 崩 —— 这个崩溃在接通遗迹之前不可达,所以从没人见过)。
- 建筑补**真实血量分数**(生成器新增 `hp` 字段):`aba_defend` 读它两次 —— 路况紧迫度乘子是它的 remap,「这座一/二塔已经保不住了」是它的阈值。没有该字段的老 fixture 逐字节不变。

## 3. 头号产出:gated `defclose`

### 3.1 缺陷

TS 源(`typescript/bots/FunLib/aba_defend.ts:310`):

```ts
for (let j = 1; j <= tPosList.length; j++) {
    if (p === tPosList[j]) { ... }
}
return bestPos ?? tPosList[0];
```

TS 数组 0-based,这个循环读索引 `1..length` —— **跳过 `[0]`,多读一格 `[length]`(undefined)**。tstl 忠实译成 Lua 的 `tPosList[j + 1]`(索引 `2..#+1`)。而 `bestPos or tPosList[1]` 的兜底返回的**就是那个被跳过的第一项**。

五个调用点(全在 `aba_defend`):

| 调用 | 意图 | 实际 |
|---|---|---|
| `{4,5}`(`ShouldDefend` nNearby==1/==2) | 4/5 号里离塔近的来守 | **只可能答 5,且不看距离**;没有存活 5 号时答 4,同样不看距离 |
| `{2,3}`(`ShouldDefend` 兜底) | 2/3 号里近的 | 只可能答 3;兜底 2 |
| `{2,3,4,5}`(`ShouldDefend` 挨打闸门) | 挨打时只有最近的还能守 | **永远不可能答 2** |
| `{4,5}`(遗迹告急挑辅助) | 最近的辅助回家 | 同第一行 |

第三行的连带后果:挨打闸门里 **1 号根本不在列表**、**2 号结构上不可能中选** ⇒ **只要队里还有一个存活的 3/4/5 号,挨过打的 1 号和 2 号就被禁止防守任何建筑**,与他们离塔多近无关。

六局 turbo 录像、**2883 个**「自家塔还站着 + 1600 内有敌方英雄」的建筑-帧,shipped 答案与真正最近者不同:

### 3.4 改动与可分离性

gated `defclose`(`J.IsSoakCandidate('defclose') and J.IsModeTurbo()`),`bots/FunLib/aba_defend.lua` + **TS 源同步**。armed 时扫描覆盖整张列表;shipped 路径逐字节不变。

**必须挑明:这不是单调的。** 它是**纠错不是旋钮** —— 相对 shipped **既可能增加也可能移除**一个防守者,不能像 `capmono` 那样用「纯 min」论证安全。

### 3.5 验收

`tests/test_defclose_defender_arbitration.lua` **11 例**:前提全断言(角色/血量/距离/塔血/塔 1600 内敌人数/主角 1600 内 0 敌人)、机制断言(拒绝是**角色算术不是距离**:5 号存活所以 `{4,5}` 兜底不可能触发,3 号存活所以 `{2,3}` 兜底答 3)、缺陷在**最终出价层**断言并**重建整场脚本竞价**、「守错塔」断言、对照帧逐位相同(lane desire 扫 0/0.30/0.50)、非 turbo 对照、id 隔离对照、两条源码级反向断言(兜底行 + 五个调用点计数,别人正经修掉时自曝过期)。

**局限,明写**:`GetDefendLaneDesire(lane)` 是引擎状态,`.dem` 不带(GH #27 同族)。出价断言**扫**这个值而不是假装知道它,并写明在哪些取值上竞价易手;lane desire = 0 时中路出价仍然动(0.100 → 0.250),但赢家不变。
