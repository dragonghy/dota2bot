## 1. 第一个产出:又一条没人声明过的世界断言(结构不可寻址)

fixture loader 此前把 `GetTower(team, i)` 按**存活塔的位置**寻址 —— 对「循环 `i = 0..10` 再归约成最近/计数/还在不在」的读者是够用的,GH #37 那轮只需要这个 —— 而 `GetBarracks` 是 `nil`,`GetAncient` 给**两边队伍**都发同一个位于**地图原点**的 4500 血单位。

⇒ **每个 fixture 里每条路的防守出价都只可能来自这一行之上的七个提前 return,`GetDefendDesireHelper` 的整个下半段结构上不可达**:`ShouldDefend`、`capBoost`/`baseFloor`、panic 地板、`recentlyHit` 衰减、`ConsiderPingedDefend`、tier/血量 remap 全在下面。白话:**「这支队伍在任何一条路上都没有建筑,而且两家遗迹叠在河道里」**。与 `HasModifier`、`WasRecentlyDamagedBy*`、`GetHeroLastSeenInfo` 三条同族。

**修复**(`tests/mock/replay_fixture.lua`,`tools/batch_test/replayscope/make_fixture.py`):

- 槽位**从几何推导**,不写死坐标,且在**全量建筑集**(含已阵亡)上推导 —— 否则掉一座塔会把幸存者悄悄重新编号:

## 3. 头号产出:gated `defclose`

### 3.1 缺陷

TS 源(`typescript/bots/FunLib/aba_defend.ts:310`):

```ts
for (let j = 1; j <= tPosList.length; j++) {
    if (p === tPosList[j]) { ... }
}
return bestPos ?? tPosList[0];
```

TS 数组 0-based,这个循环读索引 `1..length` —— **跳过 `[0]`,多读一格 `[length]`(undefined)**。tstl 忠实译成 Lua 的 `tPosList[j + 1]`(索引 `2..#+1`)。而 `bestPos or tPosList[1]` 的兜底返回的**就是那个被跳过的第一项**。

五个调用点(全在 `aba_defend`):

| 调用 | 意图 | 实际 |
|---|---|---|
| `{4,5}`(`ShouldDefend` nNearby==1/==2) | 4/5 号里离塔近的来守 | **只可能答 5,且不看距离**;没有存活 5 号时答 4,同样不看距离 |
| `{2,3}`(`ShouldDefend` 兜底) | 2/3 号里近的 | 只可能答 3;兜底 2 |
| `{2,3,4,5}`(`ShouldDefend` 挨打闸门) | 挨打时只有最近的还能守 | **永远不可能答 2** |
| `{4,5}`(遗迹告急挑辅助) | 最近的辅助回家 | 同第一行 |

第三行的连带后果:挨打闸门里 **1 号根本不在列表**、**2 号结构上不可能中选** ⇒ **只要队里还有一个存活的 3/4/5 号,挨过打的 1 号和 2 号就被禁止防守任何建筑**,与他们离塔多近无关。

### 3.6 本轮的自曝:第一版钉帧是错的,已重做

**总监的 GH #57 在本轮进行中落地**,结论是:英雄的位置来自**种子抽签**,不是 `team_slot % 5 + 1`(全语料吻合率 47.3%)。本组第一版的钉帧和第一版的域实测**都是按槽位算的**。

发现之后重做了两件事:

1. **fixture 现在可以带抽签角色。** loader 此前**根本没有抽签角色**,`aba_role.GetPosition` 落到 `RoleAssignment[team][i]` = 抽签**槽位**;游戏里 `X.ShufflePickOrder` 会把 `RoleAssignment` 和 `sSelectList` **一起**换,所以引擎看到的仍是抽签角色,而 loader 没有那次洗牌可重放,**必须被告知**。本轮六局实测:槽位标签与抽签真值只吻合 **23/60 = 38%**。修复:`make_fixture.py --roles <analysis.json>` 经 `tools/batch_test/soak/seed_draft.py` 由种子推出位置,英雄名 canon 化(`vengefulspirit`/`vengeful_spirit`),**匹配不全就报错拒绝出半张表**;loader 写 `bot.assignedRole`。没有该字段的 fixture 逐字节不变 ⇒ **没有历史结论因此翻面** —— 但**仓库里现存每一个 fixture 的角色都还是槽位派生的**,凡是在 fixture 里 fork 在 `GetPosition` 上的断言,只有 ~40% 的把握描述了它来自的那局。这条要进 backlog。

2. **钉帧和域实测重做。** 第一版钉的 `f_260820_043637_viper_defend_token`(已删)按槽位说 viper 是 4 号 —— **抽签真值是 2 号**,而 2 号在 `nNearby ∈ {1,2,3}` 时**本来就满足 `result`** ⇒ **那一帧根本没有缺陷**,armed/shipped 的差别是 fixture 标错角色的产物。在提交进 main 之前发现并重做;域实测用真值重算,**数字更大**(32.8/59.8/37.6,槽位标签算出来是 35.5/47.4/20.3)。

缺陷本身不依赖角色数据 —— 它是源码级的 off-by-one,读代码就能证明 —— 但**「哪一帧上它咬人」完全依赖角色数据**,所以这次重做是必需的,不是洁癖。
