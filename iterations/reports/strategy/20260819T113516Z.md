## 1. 结论:`tpcommit` 的「生存释放」在它自己的生效域里只剩一半

`J.GetTpCommitDefendDesire` 给刚落地的 TP 响应者在它答复的那条线的 DEFEND 模式上钉
一个 **0.85 地板**,释放条件是

```lua
if J.GetHP( bot ) < 0.40 or J.ShouldRetreatLaneBurst( bot ) then ... end
```

第二个子句是**预判**那一半 —— 它才是这个释放能起作用的原因(等掉到 40% 才走,爆发
已经吃完了)。但 `J.ShouldRetreatLaneBurst` 的第三行是

```lua
if not J.IsInLaningPhase() then return false end
```

而这块地板**只能**从两个响应 TP 分支到达(`J.GetRescueTpTarget` /
`J.ShouldTpSupportTowerFight`),后者硬性要求 **6 级以上 + 跨越 >3500 码**。也就是说
**这块地板真正钉住的帧压倒性地在对线期之后**,那里预判子句结构性失效,释放只剩
「已经掉到 40% 以下」这一条数值判据 —— 正是这个释放当初要堵的
「站在原地被磨死」形状(wave12 卷宗 mechanism D,约 6/24 例落地死亡),
**只是把让它奏效的那一半拿掉了**。

这是 **GH #29 / #31 / #32 的同族第四例**:一个条件的**生效域**覆盖不了它所在分支的
生效域。前三例分别是 guard 链先命中先 return、下游 cap 砍掉设计出价、cap 悬崖造成
非单调;这一例是**释放条件的域缺口**。

已开 issue **#35** 记录。

## 2. 改动(gated,一个小杠杆)

- 新纯谓词 `J.IsIncomingBurstLethal( bot, nWindow )`:用 `J.ShouldRetreatLaneBurst`
  完全相同的 mana/cd-aware 估算器扫 1100 内可见敌人,**去掉对线期门**,当它们此刻
  能打出的爆发已经覆盖我当前血量时为真。谓词本身**不带 gate**(gate 在调用点)。
- `J.GetTpCommitDefendDesire` 里,紧跟原释放之后加**一条** gated 释放:
  `if J.IsSoakCandidate('tpdying') and J.IsIncomingBurstLethal(bot, 3.0) then release end`。

保守性:armed 路径**只可能提前释放**(更早 return nil),结构上不可能抬高或制造
钉死;而且它必须和 `tpcommit` 同时 armed 才可达。地板值 0.85、12s 窗口、原释放
条件**一个字没动**。未 armed 时 shipped 行为与**当前 armed 的 tpcommit 行为**都逐
字节不变。

依据 (c):(1) 原释放注释自己写的契约就是「丢失了动手机会才会走」,本改动只是在
地板真正运行的域里把这个契约兑现,没有提出新主张;(2) 标准打法上,守不守一个位置
看的是 incoming damage 对有效血量,不是一个固定血量百分比 —— 满血支援站在致命连招
里该走,45% 血站在射程外不该走。用预判代替血量阈值,正是已 promote 的 `lanesurv`
所依据的同一条原则。

## 5. 本轮审计中发现、但**没有**动手的东西(留给下一轮 / 别的组)

- **`midtp` / `suptp` 的出价数值在物品链里是惰性的**:
  `ability_item_usage_generic.lua` 的物品循环只判 `nItemDesire > 0`,从不跨物品比
  大小,所以 `BOT_ACTION_DESIRE_HIGH` 与任何正数等价。真正决定优先级的是**槽位顺序**
  `{5,4,3,2,1,0,15,16}` —— **TP 卷轴在最后**,所以任何一个当帧想用的其他物品都会
  抢在响应 TP 前面。这是 shipped 行为,不是本组的 id 造成的,但判读 midtp/suptp 的
  「为什么没触发」时必须知道。
- **响应 TP 的落点从来没有和触发点做过距离校验**(给录像组的线索):
  `J.GetNearbyLocationToTp` 把落点解析成「离触发点最近的**还活着的**己方塔前
  575 码」,没有塔时**回落到泉水**;而 `J.WillAllySurviveTpWindow` 只预算 **4.0s**
  (3s 引导 + 一步),**不含落地后走过去的时间**。这正好是一个能机械地解释录像组
  `20260819T033000Z` 报告里那一帧的假说 ——「前置条件全满足但落地在泉水」
  (game `20260819_001937_slot1`, t=343.5,CM→Lina)。**本轮没有动**:一次一个杠杆,
  而且 `lf_rescue` 正是马上要跑的 bisect 的被测变量,现在改它会让那一波测到的不是
  总监定义的那棵树。已写进 `state.json:tpdying_20260819.scope_note` 和 issue #35。
