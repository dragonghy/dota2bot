## 1. 缺陷(源码,三处,逐字)

`J.GetNearbyLocationToTp( nLoc )` 回答的是「**离 `nLoc` 最近的己方塔,朝 `nLoc` 方向 575u**」。
它在 `bots/` 里有 **9 个调用点**,其中 **8 个**传的是队友 / laneFront / Roshan / Tormentor /
团战点 / target —— 那座塔与 `nLoc` 是**两个地方**,方向有定义。

**第 9 个**(`bots/ability_item_usage_generic.lua`,`midtp`/`suptp` 的接线)传的是
**一座塔自己的坐标**,于是:

1. `for i=0,10` 的循环取**离 `nLoc` 最近的己方塔** = **它自己**,`minDist == 0`;
2. 瞭望塔分支要求 `< minDist - 1300` = `< -1300`,**恒假**;
3. `J.GetLocationTowardDistanceLocation( tower, tower:GetLocation(), 575 )`
   = `towerLoc + 575 * ( towerLoc - towerLoc ) / 0` = **`Vector(-nan,-nan,-nan)`**。

`vTpLoc ~= nil` 对 NaN 向量**为真**,一路无 nil/NaN/边界检查进
`Action_UseAbilityOnLocation`。**引擎那一端本报告不声称**(没有 bot 侧调试):
良性端 = 动作被拒 ⇒ 两个 id 恒 inert,**而 `X.ConsiderItemDesire` 仍 `return nSlot + 1`,
门为真的每一帧的道具决策都被这一发吃掉**;恶性端 = 落到未定义位置。**两端都不是这两个
id 写下来要做的事。**

## 3. 这一刀切在哪,以及为什么不新开 id

**切在调用点,不切共享函数。** 改 `J.GetNearbyLocationToTp` 会**一次动到 9 个调用点**;
能产出退化输入的**只有 1 个**,而那 1 个**本来就是暗的**。测试第 6 节断言共享函数

**不新开 gate id,而且这是上一轮自己写下的约束**
(`test_tpdefall_tower_commit_quantifier.lua` §5 / `test_set.md` 0OVERCHASE / GH #606):
宿主已经挂在未 promote 的 `midtp`/`suptp` 上,再嵌一层 `J.IsSoakCandidate` 就成了
`(midtp or suptp) AND <new>`,**单独 arm `<new>` 的波会读到一个结构上不可能的 0,
而 `check_armed_wiring.py` 仍然叫它 WIRED**。
⇒ 调用点在 `if hTowerFight ~= nil` 里,宿主第 2、3 行 `return nil`,**重复继承已有的闸**。
测试第 5 节把这个顺序钉住(turbo 早退 → 候选早退 → 站点),并断言
`J.GetTowerDefenseTpLocation` 在 `bots/` 里**只被两个文件提到**(定义 + 那一个调用点)。

**方向的依据(验证哲学条件 (c))**:TP 去守塔的人应当出现在**建筑自己这一侧、塔的保护下**,
而不是出现在正在拆塔的那群人中间。575 是**出货自己的常数**,不是新调的。
