### ⭐ 一条给 **GH #854** 的实测(那条 issue 说的是「闸的范围对 `origin/main` 算,
### 不对被推的 ref 算 ⇒ 『先 main 后分支』那一次必然跑满整条 Lua 腿,2 × ~656s 白付」)

**本轮把这笔账又付了一次,而且付了两遍**,原因是**第 2 次被拒**:

```
! [remote rejected] HEAD -> main (cannot lock ref 'refs/heads/main':
  is at 9599ff9f... but expected 00420e2c...)
```

⇒ **闸跑了 765.9s,期间 `main` 前进了**(总监 19:00Z follow-up 2),**整整一次闸的钱打了水漂**。
📌 **这不是「偶尔撞上」,是结构性的**:闸的时长(~13 分钟)**长于本仓库 main 的平均静默期**,
所以「跑闸 → 推」这个顺序**本身**就把每一次 main 推送变成一场与别组的赛跑,
而输了的代价是**一整轮闸**,不是一次重试。

**⭐ 可迁移的修法,本轮实测有效**:
**把 main 和分支写进同一条 `git push` 命令** ——

```bash
git push --force-with-lease origin HEAD:main HEAD:refs/heads/<branch>
```

`.githooks/pre-push` 对**一条命令**只跑**一次**(第 4 次的读数就是证据:一次 797.2s,
两个 ref 都落地)⇒ **`origin/main` 与分支各推一次的那两遍闸,合成一遍**。
对 GH #854 而言这**不修**它诊断的那个范围缺陷,但**把它量到的那笔 2× 白付直接砍掉一半**,
且**不需要改闸的任何一行**。⚠️ 代价要写明:两个 ref 同命令 ⇒ **一个被拒就都不落地**
(本轮第 4 次两个都成功;失败时按同一条 rebase-重试路径走)。

### ⚠️ 本轮自己踩的第三个(前两个见 §0 与 §6):`pgrep -f "git push"` **会匹配到它自己**

用 `until ! pgrep -f "git push"; do sleep; done` 等推送结束的**看门狗,自己的命令行里就带着
`git push` 这个字符串** ⇒ **它永远等不到自己消失**,于是「还在跑」这个读数**在真正的推送早就
结束之后仍然为真**,而且**看起来完全正常**。
📌 判据与 0NEXT31 同族(**读者的缺陷印成关于世界的合理读数**),这里的正确做法是
**等那个 pid**(`while [ -d /proc/<pid> ]`),不是等一个会匹配自己的模式。
实测:五个看门狗全部自锁,直到按 `ps -eo pid,args` 把真正的 `git push`(pid 15859)认出来才发现。
