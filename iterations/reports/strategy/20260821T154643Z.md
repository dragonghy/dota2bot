## 1. 机制:惰性戳 + 一帧寿命的 VM = 恒真守卫

`bots/mode_farm_generic.lua:123-126`(逐字):

```lua
J.Utils['GameStates']['defendPings'] =
    J.Utils['GameStates']['defendPings'] or { pingedTime = GameTime() }
if GameTime() - J.Utils['GameStates']['defendPings'].pingedTime <= 5.0 then
    return BOT_MODE_DESIRE_NONE
end
```

游戏里没问题:表在开局几秒内被填一次,此后 `GameTime() - pingedTime` 一直变大,
直到真有人 ping 防守。**fixture 里,VM 被造出来、被问一个问题、被扔掉** ——
填表那一行和读表那一行相隔几微秒,**读的是同一次时钟**。差值**恰好是 0**。守卫触发。
每一帧、每一个 fixture。

**两个互相独立的原因,而且修掉显眼的那个什么都不会变**:

1. mock 的 `GameTime()` 是常数 0(`tests/mock/bot_api.lua:232`),而 loader 把
   `DotaTime()` 接到了真实帧时间(`tests/mock/replay_fixture.lua:488`)⇒
   **fixture 世界跑着两个时钟,差整整一局**;
2. 戳是**用它稍后要比的那个时钟**初始化的。

**原因 (2) 单独就够**。谁要是把 loader 的 `GameTime()` 修诚实(所有人第一反应的那个修法),
守卫**照样每帧触发**,因为初始化跟着一起走。这条已经写成**变异探针**断言在文件里
(`[MECHANISM] repairing the clock does NOT open the guard`),不是论证。

**四个已发布站点共用这个键,其中三个挡在出价前面**:

| 站点 | 后果 |
|---|---|
| `mode_farm_generic:123` | `return BOT_MODE_DESIRE_NONE` |
| `mode_side_shop_generic:50` | `return BOT_MODE_DESIRE_NONE` |
| `FunLib/aba_push:222` | `return BotModeDesire.None`(**三条推塔 mode 的出价都从这里来**) |
| `FunLib/aba_defend:881` | 只挡「喊人来防守」的 ping,**防守出价不受影响** |

第四个仍然列出来,因为它是这个共享键的**写者**:谁先跑谁盖戳,之后所有人读到的都是 0 差。

## 4. 交给 GH #84 §5:`535` 的两半分开量了

`535` 的门是 `bot:GetLevel() >= 15`,(甲) 判 TEETH:farm 的 **runMode 应战块**
(敌人进我攻击距离 + 900 内两个队友 → `Action_AttackUnit`)是活的 Turbo 情境,
挂在一个 Turbo 没人够得着的成熟度代理上。本轮把它拆成两半各量一次:

* **情境这一半是活的,而且不是猜的** —— **872 个存活英雄帧里 3 帧**满足内层 `if` 的
  **每一个子句**(等级 4 / 11 / 11,敌人在 **55–167u**,900 内 2–3 个队友)。
  这 3 帧上,`GetLevel() >= 15` 是**唯一**挡在一个刷钱的 bot 和 `Action_AttackUnit` 之间的东西。
  三帧逐个钉住:`f_260819_142047`(chaos_knight lvl4,venomancer@158,两队友)、
  `f_260819_222559`(dragon_knight lvl11,lich@167,三队友)、
  同帧(juggernaut lvl11,lich@55,三队友)。
* **外层这一半从不同时成立** —— `runMode` 只在 `X.ShouldRun(bot) ~= 0` 时被置位,
  全语料 **940 帧里 5 帧**,**与那 3 帧的交集为空**(两个方向都验过)。

⇒ **(乙) 的形状(gated + 真实帧 + 断言最终动作)在本语料上没有帧可站**,和 `285` 一样。

**但和 `285` 不一样的地方,这次要说清楚**:`285` 卡在 **dumper 缺口**(mode 不在 `.dem`,
再买也没有);`535` 卡在 **语料缺口**。`X.ShouldRun` 是**当帧的纯函数**,
一份含有该共现的录像就能定它。⇒ **语料请求是活的**(见 §6),不像 #84 那次是撤回。

**顺带钉住两条结构事实**:

1. **`ShouldRun` 的一条腿在触发帧上永远够不到这个块**:`enemyFountainDistance < 1000`
   那条(return 2)与块自己的 `J.GetDistanceFromEnemyFountain(bot) > 2200`
   **读同一个 helper、同一帧、区间不交**。只能靠尾巴(下条),而那要 2 秒走 1200 码 ≈ 600 移速。
2. **fixture 只看得见 runMode 段的第一帧**。`GetDesireHelper` 在 `ShouldRun` 触发那一瞬置位,
   然后**不再重问**地保持 `shouldRunTime` 秒(1.33–3.33,**返回值当时长用**);
   fixture 每个 VM 都从 `runTime = 0` 开始 ⇒ 只观察得到段的**开口**,看不到尾巴,而尾巴是大头。
   **这是第三种 harness 盲区**,与第十二条(dump 有、loader 丢)和第十三条(dump 从来没有)都不同:
   这里状态**可重建,但只在开口处**。⇒ **「940 帧里 5 帧」不能读成游戏内频率。**

## 5. 本轮不做什么

  (GH #61 lane-front 的定案),是**口径决定,归总监** —— 已开 `[harness]` **GH #91**。
  本组建议照 #61 办:**每个测试自己声明**,并给 `rf` 加一个有名字的声明助手,
  这样「我假设最近没人 ping 防守」在用例里是看得见的一行,而不是 loader 里的一条静默默认。
- **不给 `GetRoshanDesire` 打桩**(同上,口径)。
