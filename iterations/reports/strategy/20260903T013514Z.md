## 2. 候选 2(`AllyPIDs` 模块级缓存):活着,而且它的形状比 issue 写的更准

`local AllyPIDs = nil`(`bots/FunLib/jmz_func.lua:11541`),
`if AllyPIDs == nil then AllyPIDs = GetTeamPlayers(GetTeam()) end`(`:11592`)。
若一个 Lua VM 服务两队,**先调用的那一队把名单冻给了两队**,另一队的**未 armed** 扫描
就拿着错误的数值去喂 `GetTeamMember`。

**⭐ 主判据(可复用,超出本主题):这个缺陷只可能打坏对照,打不坏被测的那个 fix。**

(`if bSlotDust then nSlot = i end`,`:11600`)⇒ **armed 腿对这个缓存泄漏免疫**。
所以「结构性零对照」塌掉不等于 `slotdust` 这个 id 有问题,**它等于这一轮没有对照**。
这一条现在被 `tests/test_slotdust_reachability_fit.py` §4 钉住(闸的那一行还在源码里)。

## 3. ⭐⭐ 为什么这件事不是「再跑一次就知道」——本轮真正买到的那一格

`slotdust_arbitration.py` 的排他列**由 `reachable_unarmed` 定义**:

```python
        if reachable_unarmed(team, slot):
            out[leg]["reachable_slot"] += 1
            continue                      # ← B2/B3/B4 在这里就没人问了
```

于是**能区分三个假设的那一个数——「来自够得到的槽位、且熬过全部三条排除的扔尘有多少」——
从来没有被任何一次运行、在任何一份语料上算出来过**。它不是一个小数字,也不是一个噪声大的
数字;它**不存在**。**一个模型只能被它自己没有定义的读数纠正。**

这与本组 8-31 起的那条老判据同族(「一个只能证伪的读数必须在选杠杆之前跑」,GH #400),
但**上一次错的是没跑,这一次是跑了、跑得很干净、而那个读数在结构上答不了这个问题**。
两次的症状都是**一个自洽的、带分母的、看起来完成了的表**。

## 4. 落地:REACHABILITY FIT(`tools/batch_test/behavioral/slotdust_arbitration.py`)

对**每一条**扔尘跑同一套 B2/B3/B4,按队伍槽位登记 `幸存/总数`,并按一条规则出裁定:

> **基线腿上,有幸存者的槽位必须是够得到的** ⇒ {有幸存者的槽位} ⊆ 任何存活假设。

- 三条排除的判定被提到 `blocked` 一个变量里,**下面的级联逐字不动、只是读它** ⇒
  **九个既有列的值一个都不动**(§5 是这一句的证据,不是这一句的重复)。
- 新列 `fit_casts_s1..5` / `fit_survive_s1..5`,按 layer×leg 聚合;
  `team_of(layer, leg)` 把 (层, 腿) 映回队伍(ab 层按定义是 radiant armed)。
- 报告新增 REACHABILITY FIT 一节 + 三个假设各自的 `REFUTED / not refuted` 行。
- **LIMIT 12 写进模块 docstring**:**这个检验只能证伪**。一个把所有槽位都算作够得到的
  假设在这里不可证伪;没被证伪 ≠ 被证实;某槽位零幸存也可能只是**没人从那个槽位扔过尘**
  (读旁边的 `fit_casts`)。**若每个基线槽位都有幸存者,那这份读数说的是 B2/B3/B4,
  不是可达性。**

**计量登记(铁律 4)**:两层读数都打印,满足 (i-a)。**(i-b) 不适用而且要说清为什么**:
这里的读数是一个**支持集合**不是一个量级——一条幸存者证伪得和九条一样硬——而且每队的基线腿
**只住在一个层里**(dire baseline 只在 ab,radiant baseline 只在 ba),**没有并池那一步**,
侧偏项无处可藏。
