## 1. ⭐ 主判据(可复用,超出本主题):**一个不被计数的 skip 不是 limit,是一个旁边摆着分母的谎**

发现真命中之后先去查有没有现成工具 —— **有**,而且比手写的好:
`tools/agent/call_arity_census.py`,带 allowlist、自检、一整节 LIMITS。
**但它 `--all` 跑全树读作 `OVER (0)`,而我手写的那个在全树上找到了一个 OVER。**

差别在解析器。它按**声明里字面写的点名**建表;`bots/` 下有 **24 个转译自 TypeScript 的模块**、
**256 个导出**,一律声明成 `function ____exports.Foo(...)`,而每个引用方写的是

```lua
local Utils = require(GetScriptDirectory()..'/FunLib/utils')
Utils.Foo(...)
```

两个名字**从不相等** ⇒ 调用在 `if name not in decls: continue` 处掉出去。
**那条 continue 不增加任何计数器。** 工具有两个具名的 skip 桶
(`ambiguous_skipped`、`vararg_skipped`),和**一个静默的**,而静默那个**有 665 个调用宽**。

于是分母行**一直很健康**(files 275 / declarations 1700 / dotted_calls 28511),
**披露行结构上披露不了这个洞**,而 `tests/test_call_arity_census.py` 从 2026-08-25 起断言的

> `ok("the OVER half is still empty", ...)`

**对那个解析器为真,对这棵树为假**。这棵树**唯一**的 OVER 成员就住在这样一个调用点上,
在那句断言一路绿灯的整段时间里**没被看过一眼**。

⇒ 与 #431 / #437 / #445 同族;四次的症状逐字相同:**一个偏小的、自洽的、带分母的读数**。
**这一次的新意在于:错的不是查询词也不是解析器本身,而是"跳过"与"没找到"共用了一条静默分支。**

## 2. ⭐⭐ 第二条主判据:**「被使用」和「被读」不是一回事**

唯一的 OVER:`hero_selection.lua:1040`

```lua
tLaneAssignList[team] = CaptainMode.CMLaneAssignment(Role.RoleAssignment, userSwitchedRole)
```

而 `captain_mode.lua:380` 是 `function ____exports.CMLaneAssignment(roleAssign)` —— **一个形参**。

`userSwitchedRole` 在整个文件里**只有三处**:`local ... = false`(:755)、
`= true`(:805,人类在聊天框打 `!pick`)、以及这里。Lua 丢掉它
⇒ **这个 flag 是只写的,它背后那个功能从来没被实现过**。

**luacheck 抓不到,而且抓不到是对的**:它**被"使用"了** —— 作为实参出现。
**一个实参走到一个不收它的形参表,对 linter 是使用,对程序是丢弃。**

判 **COSMETIC 不判 TEETH**,两条都是结构性的:分支是 `GAMEMODE_CM / REVERSE_CM`,
**本仓优化 Turbo(gamemode 23),永远进不去**;且 OVER 的多余实参被 Lua 丢掉,
**进得去也不改行为**。行里钉了"什么会让这条判决作废":`CMLaneAssignment` 长出第二个形参。

### (a) GH #451,英雄组,**活的**
`hero_tinker.lua` 的 **8 处** `J.Utils.GetItem('item_x')`。声明是 `GetItem(bot, itemName)`,
函数体去调 `bot:GetItemInSlot(i)` ⇒ 物品**名字**成了接收者。lua5.1 实测:

```
$ lua5.1 -e 'local s="item_x"; print(pcall(function() return s:GetItemInSlot(0) end))'
false   attempt to call method 'GetItemInSlot' (a nil value)
```

`CanDoCombo2()` 只要跳刀 + Laser + WarpFlare 好了就走到第一处。
**引擎的错误处理器是坏的**(`error in error handling` 吞掉全部 Lua 错误文本)
⇒ **它一直在无声地炸**,这也是它活到今天的原因。

### (b) GH #452,本组的域,**活的** —— 一个恒假的闸 + 一个只写的集合
`mode_team_roam_generic.lua` :1771 / :1819 / :1823,`Utils.SetContains(itemName)`。
声明是 `SetContains(set, key) → not not set[key]`,单参 ⇒ `set` = 名字,`key` = nil。
lua5.1 实测:`("item_aegis")[nil]` 是**合法的读**(只有以 nil 为键**赋值**才报错),
取到 nil ⇒ **闸恒假**,`not SetContains(...)` **恒真**。

后果:`ignorePickupList` 在 :1821 被写入、**永远不被查询**;`tryPickCount >= 3`
把计数清零、加进忽略表,然后**径直落到 :1823 那个恒真的判断上再捡一次**
—— 对一个已经放弃的掉落物**三帧一轮地无限重试**。

⚠️ **同三行里还有第二个、独立的缺陷**:`AddToSet` 存的是物品**句柄**,三处读问的是
物品**名字** ⇒ **光把 set 补上仍然永远不命中**(实测同样 `false`)。
这是 `0SLOT` / `slotarb` 的**两套下标空间**族**第三次**出现。
⇒ **正确的修法是两处一起改,不是补一个实参。**

### (c) GH #452,本组的域,**潜伏的**
`mode_roam_generic.lua:1251` 一行上**两个各自都能抛错**的缺陷:少了 `bot`(枚举成了接收者);
以及 **`not` 比 `<=` 结合更紧** ⇒ 这一行是 `(not <boolean>) <= 2`,

但 `GeneralReactToStackedDebuff` 在 `bots/` 里**没有任何调用者** ⇒ **潜伏,不是今天的火**。
