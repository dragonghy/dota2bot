## 1. 缺陷

`bots/mode_outpost_generic.lua` 的 `GetDesireHelper`:

```lua
if not DidWeGetOutpost
then
    if botName == 'npc_dota_hero_invoker' then return BOT_ACTION_DESIRE_NONE end
    for _, unit in pairs(GetUnitList(UNIT_LIST_ALL)) do
        if unit:GetUnitName() == '#DOTA_OutpostName_North'
        or unit:GetUnitName() == '#DOTA_OutpostName_South'
        then table.insert(Outposts, unit) end
    end

    DidWeGetOutpost = true          -- ← 无条件
end
```

这个块是 `Outposts` 的**唯一写者**,`GetClosestOutpost` 是它的**唯一读者**
(源码计数已钉:1 声明 / 1 `table.insert` / 1 长度测试 / 7 处在 getter 里)。
`DidWeGetOutpost = true` **无条件**排在扫描之后 ⇒ **只要那一次扫描返回空表,`Outposts` 永远是空表**:
`GetClosestOutpost` 恒答 `nil`,`GetDesireHelper` 唯一的非 NONE 出口挂在 `ClosestOutpost ~= nil` 之后,
于是这个 mode 的出价**这一局剩下的时间恒为 NONE**,`Think`(以及它 `:117` 那条连续型命令)**永远到不了**。
**没有报错,没有重试,没有任何一条腿会举手。**

## 2. ⭐ 主判据(可复用,超出本主题)

> **一个闩必须记录它所把守的后置条件,不是那次尝试。**

`DidWeGetOutpost` 的名字问的是「我们**拿到**了吗」,代码答的是「我们**看过**了吗」。
凡是「只做一次」的标志位被写在**本该产出点什么的那个块的出口处**,
**空结果与满结果就无法区分**——而且这个区分是**永久性**的,
因为那个标志位**正是唯一还会再跑一次生产者的东西**。

**与三条同族明确区分**(四者都是「守卫/推理与它的消费点对不上」,**因**各不相同):

| | 缺陷的因 |
|---|---|
| GH #348(sniper) | **顺序**:判 `nil` 的前一行就索引了 |
| GH #368(`rotscope`) | **作用域**:守卫和被守卫者同名但不是同一个变量 |
| GH #370(`roamidle`) | **未汇报的副作用**:被调方下了命令却读起来像查询 |
| **本条(`outlatch`)** | **生产者、标志位、消费者三者各自都对** —— 错的是**标志位回答的问题和消费者问的不是同一个** |

## 3. ⭐⭐ 第二条互相独立的后果(登记,**本轮不修**)

`GetClosestOutpost` 的合取式里,`not Outposts[i]:IsNull()` ——
**它存在的全部理由就是「这个句柄可能已经没了」**——被排在**第四**位求值,
**在 `Outposts[i]:GetTeam()` 与 `GetUnitToUnitDistance(bot, Outposts[i])` 这两次
对它所守护的那个句柄的方法调用之后**。Lua 的 `and` 从左到右短路 ⇒ 守卫**晚了两步**。
这是 **GH #348 的形状在第二个文件里**,而它值多少钱**恰好由第 1 节决定**:
表只填一次、永不刷新,句柄陈旧化正是那个闩的直接后果。

**一次一个杠杆** ⇒ 本轮只修第 1 节。这一条由 `[source S6]` 钉住,
断言**缺陷仍在**——哪天它翻转,那个测试文件必须被重新推导,而不是悄悄通过。

## 7. ⚠️ 方法自伤(记下来,因为它**安静地通过了一轮**)

用 `function GetClosestOutpost%(%).-\nend` 抓函数体,**非贪婪会停在第一个嵌套 `end`**,
于是返回一个**被截断**的函数体,读数计数**少报一处**,却仍然**匹配上了一个看着合理的期望值**。
**一个返回得比它声称的少的扫描器,是靠「同意你」来失败的。**
已改为按**两侧邻居的 `function` 头**切片,并把这段推理写进文件本身。
与 GH #341/#345(工具从未求值它自称读的那条子句)、GH #370(源码扫描把自己的注释数了进去)同族。

**教训(可复用,比这次的具体号码更值钱)**:**「下一个 issue 号」是一次预测,不是一次读数。**
GH #290 要求的顺序(先 push 再发引用)让**代码引用 issue** 这个方向天然要预测号码;
预测在多流并发的 2h 触发格局下**随时可能被别的流取走**。
正确做法是**发完 issue 立刻回填并二次 push**(本轮做了),而不是相信预填值。
`claim_precheck.sh` **抓不到这一形** —— 它验证的是**路径 / `state.json` 键 / 章程节 / commit 哈希**,
`#NNN` 这种 issue 引用**不在它的解析面里**,所以它在预填错的树上照样打 `clean`。
**登记为工具面的一个洞,请总监裁要不要给 precheck 加一条 issue-号存在性/归属检查。**
