## 1. 起点是一条**没找到东西**的普查,如实记

先做的是 GH #162 那把尺子的**类型对偶**:`GetSpecialValueInt` 读一个**小数**的 KV 值会被截断
(`0.75 → 0`,任何倍率都会毁掉)。焦点五全部 `GetSpecialValueInt` 读数 × 该英雄整份 KV 的
同名 key,**一个真阳性都没有**:唯一命中(Axe `duration` 对上 `axe_berserkers_call` 的
`2.1 2.4 2.7 3.0`)是**假阳性** —— `abilityW` 是 `axe_battle_hunger`,它的 `duration` 是 `12.0`。

**这次假阳性正好指出了 #162 那把尺子自认的缺口**:它**不解析句柄→技能**,所以「key 在」什么都不证明。
于是把工作单元换成**把那个缺口关掉**:先解析句柄,再问它读的东西对不对。焦点五里 WK 是唯一
按字面名绑定的(`GetAbilityByName('skeleton_king_bone_guard')`),其余四个走 `sAbilityList[N]` /
`sTalentList[N]` —— **索引**。而**索引正是没人钉住的那个量**。

## 2. 发现

`aba_skill.X.GetTalentList` 走 `bot:GetAbilityInSlot(0..25)` 按槽位顺序收集 `IsTalent()`,
所以 `sTalentList[N]` = 「游戏给这个英雄的第 N 行天赋条目」(1 = t10 左 … 8 = t25 右)。
**具体是哪个天赋是 V 社说了算的**,树里没有任何东西钉住它。

`hero_lion.lua` 绑 `talent8 = sTalentList[8]`,**十五处**拿它决定 `lion_voodoo`(妖术)的事。
而两个源 join 出来的答案是:

```
lion  7  special_bonus_unique_lion_4   lion_voodoo/radius            = +250   <- 才是「妖术 AoE」
lion  8  special_bonus_unique_lion_2   lion_impale/AbilityCastRange  = +600   <- 代码绑的是这个
```

**不是休眠的错配**:本文件自己的 `tTalentTreeList['t25'] = {10, 0}` ⇒
`J.Skill.GetTalentBuild` 第 4 项 = **8** ⇒ **出货构筑训的正是让那十五处答 true 的那一半。**

**两条后果,只有第一条需要引擎:**

1. `X.SkillsComplement` 把 `ActionQueue_UseAbilityOnEntity` 换成 `ActionQueue_UseAbilityOnLocation`,
   而 `lion_voodoo` 的 `AbilityBehavior` 是 `DOTA_ABILITY_BEHAVIOR_UNIT_TARGET`,**整份 KV 里
   没有任何天赋 override 改过它** —— 对单位指向技能下地面指令。引擎拿它怎么办**离线断不了**
   (AGENTS.md:无 bot 侧调试)⇒ **登记为风险,不写成「实测 no-op」**。
2. `( J.CanCastOnTargetAdvanced( npcEnemy ) or talent8:IsTrained() )` 拿同一个假前提**绕过施法
   合法性检查**。**这一半不需要引擎就能判错**:妖术在两种天赋下都是单位指向。

与 GH #162 / #137 / #115 / #104 同族,区别在漂移住在哪:**不是 key 的名字,是行的位置**,
**任何 key 普查都看不见它**。

## 4. 改法:收紧型的门,方向由形状承担

```lua
function X.IsHexAoe()
	if talent8 == nil or not talent8:IsTrained() then return false end
	if J.IsModeTurbo() and J.IsSoakCandidate( 'lionhexaoe' ) then return false end
	return true
end
```

十五个调用点全部改走它。**出货读数先跑**,armed 路径**唯一能加的东西是 `return false`**
⇒ gate-off 等于出货是**构造出来的**,不是测出来的。这是 GH #154「放宽型的门写成
『出货判据先跑一遍』」的**对偶**,与 GH #165「armed 只准取 min」合起来是同一条:
**门的方向性由代码形状承担,不由常数承担。**

## 6. 槽位顺序没有只信一个源

树里**已经站着的**、由更早三轮从**另一个源**(dota2.com datafeed)写下的声明,与新快照**逐槽相符**:

| 出处 | 声明 | 快照(odota + 游戏 KV) |
|---|---|---|
| `hero_axe.lua:280` | 7 = `special_bonus_unique_axe_2`,+嘲讽 AoE | ✅ `axe_berserkers_call/radius +85` |
| `hero_zuus.lua` FACT 块 | 5 = `special_bonus_unique_zeus_2`(弧闪,不是大招) | ✅ `zuus_arc_lightning/arc_damage +60` |
| 同上 | 3 = 大招伤害天赋 | ✅ `special_bonus_unique_zeus_4` = `zuus_thundergods_wrath/damage +75` |
| GH #150 | 6 = `special_bonus_unique_wraith_king_facet_3` | ✅ `skeleton_king_bone_guard/min_skeleton_spawn +5` |
| 本文件 `X.GetAbilityRDamageBonus` | Lion 5 = 手指每杀伤害 | ✅ `lion_finger_of_death/damage_per_kill +20` |

六条全部写成断言 ⇒ **哪个源重排了都会当场红**,而不是被悄悄重锚。

**普查的判据是单向的**(与 key 普查、鞋子供给普查同纪律):`mods` **非空是证明**;
`mods` **为空什么都不证明**(通用行、facet 行住在 `npc_abilities.txt`,本普查不读)。
所以 §2 的结论是**通过 slot 7 是什么**得出的,不是通过 slot 8 少了什么。

## 10. 留给后来人

1. **一个天赋句柄的正确性有两个独立问题**:槽位指向谁、以及那个天赋的效果是不是代码假设的那种。
   **key 普查只能答第二个的一半**;槽位那一半以前没有任何工具。
2. **判「句柄绑对没有」最便宜的判别式是同一文件的散文怎么写的** —— 本例散文对、代码错,
   与 GH #134 那一族(散文比代码晚)方向相反,所以**两个方向都要看**,不能默认哪边新。
3. **「turbo 里这一行是死的」是关于构筑会不会点它的论断**,**不能**顺带豁免**读它的句柄**。
   `test_focus_talent_anchor.lua` 那句不钉 t20/t25 的理由本身没错,错在它的适用范围被默认放大了。
4. **收紧型和放宽型的门不要写进同一个谓词。** 结构性 gate-off 等价的前提是 armed 分支只能
   往一个方向动;混了方向就只剩「测出来的等价」,而那正是 GH #144 的 M7 逃逸的那个层级。
