## 1. 出发时的假设,以及它是怎么被自己的锚按住的

`X.ConsiderW`(WK 唯一的 Bone Guard 释放点)两条开火分支:

```
branch 1   ( nStack / maxStack >= 0.6  or  talent6:IsTrained() )
branch 2   ( nStack == maxStack        or  talent6:IsTrained() )
```

本轮出发时的假设是**这个 bypass 是缺陷**:一个天赋 handle 把释放规则**唯一的弹药检查**整个关掉,
拿到它的 WK 会空着弹匣烧 42 秒冷却 + 100 蓝。

**假设错了,而且是被 datafeed 一行按死的。** 索引 6 =
`special_bonus_unique_wraith_king_facet_3` = **"+5 Bone Guard Skeletons Spawned"**,
配 `skeleton_king_bone_guard.min_skeleton_spawn = **0**` ⇒ **学了天赋,空仓释放照样出 5 个骷髅**,
所以「不管存了多少都放」**正是对的规则**。这是一条**建在真实平地板之上的放宽析取**。

**⇒ Lever B 结案:NOT-A-DEFECT。** 钉住它的三条断言,全部**从代码/feed 读出来**而不是断言:

1. 记录下来的天赋名必须仍读作 `+N Bone Guard Skeletons Spawned` 这个**平量**形状,且
   `min_skeleton_spawn == 0`;两条并列成一个断言 —— 判词只在两者同时成立时才成立。
2. `talent6:IsTrained()` 在**活代码**里恰好出现 **2** 次,且**两次都是 `or` 的右操作数**。
   (方向是判词的一部分:`and` 或取反的形式能**减少**开火,那是另一个结论。)
3. **本文件自己的 build 在 t20 真的取索引 6** —— 把文件交给 `J.Skill.GetTalentBuild` 的那张表
   **捕获出来**,再喂给出货的 `GetTalentBuild`。`test_wk_fact_anchor.lua` §2 钉的是
   「t20 那一行驱动索引 {5,6}」,**没钉的是本文件取这一对里的哪一边** —— 取错边的话,
   `talent6` 就是一个出货 build 从不点的天赋,两条析取会因**第二个独立的理由**而死。

turbo 里它仍然是死的(GH #84:`level >= 20` 0/210,高水位 19)。**GH #108 把批测局时上限
10 → 25 分钟,是最可能让它活过来的那个改动** —— 这也是 §5 那条残留的触发条件。

## 2. 在证伪它的路上量到的东西:`X.ConsiderW` **整条在 fixture 里验不了**

函数第一道门:`or not bot:HasModifier( "modifier_skeleton_king_bone_guard" ) -> return 0`。

逐帧量(每个 fixture 一次 `dofile`,不是正则):

| 读数 | 值 |
|---|---|
| 语料里的 WK 帧 | **34** |
| 其中带 modifier 列表的 | **17** |
| 其中带某个 `modifier_skeleton_king_*` 兄弟的 | **17 / 17** |
| 带 `modifier_skeleton_king_bone_guard` 的 | **0** |
| 出货 `X.ConsiderW()` 在真实帧上返回 > 0 的 | **0 / 34** |

那 17 的分母是关键:**不是「这批语料没有 WK 的 modifier」** —— 17 帧全都带着天生的
`modifier_skeleton_king_vampiric_spirit_aura`(elapsed 400–720s,横跨整局)。

**名字没写错**,三条独立证据:

* `grep -rn bone_guard bots/` 在本英雄文件之外只命中 `FunLib/spell_list.lua` 一行权重,
  而那个文件**只有 `hero_morphling.lua` 在 require** ⇒ `X.ConsiderW` 是全仓**唯一**的施法者;
* 语料里 **4 帧**抓到这个技能**正在冷却中**(cd 40.2 / 32.5 / 27.1 / 3.5,对它恒定的 42s)
  ⇒ 那几局里引擎的 `HasModifier` **答了 true**;
* GH #77 那份 l1trade 的 ground truth 里记着 **WK 的骷髅**打出的伤害(110 点)。

⇒ 缺的是**管线**:`make_fixture.py` 的 `modifiers` 从战斗日志的 `MODIFIER_ADD`/`REMOVE`
**成对重建**,这一个没有对。

**⭐ 一字段反事实(把「是这道门在沉默」从读源码变成量出来的)**:只授予 `HasModifier` 这一个字段、
别的什么都不改 —— **20/34 帧**的结果当场改变:它们越过这道门,一路跑进 `X.IsNearLaneFront`,
撞上 loader 对 `GetLaneFrontLocation` 的**声明式拒答**(GH #61)。剩下 14 帧停在语料**答得出**的
地方(技能没学 / 在冷却 / 4 级地板)。**20 就是这个盲区的大小。**

## 3. 还有两条,让释放**算术**在离线世界里本身就没有意义

即便语料带上那个 modifier,两个阈值的**操作数**在 fixture 里也都是空的:

* `abilityW:GetSpecialValueInt('max_skeleton_charges')` 离线读 **0**(mock 的 `Get*` 默认)
  ⇒ 比值是 `0/0`(NaN,`>= 0.6` 为 **false**),等式是 `0 == 0`(**true**)
  ⇒ **branch 2 的弹药检查白送**;
* loader **没有实现 `GetModifierByName`** ⇒ 走 `Get*` 默认 **0** ⇒ `GetModifierStackCount(0)`
  读的是该英雄 modifier 列表(**按名排序**)的**第一行** —— 实测是
  `modifier_skeleton_king_reincarnation_scepter`。honest 的答案应该是 **-1**,那样
  `modIdx > -1` 这个守卫才开始工作。

两条都写成断言上了棘轮。**第二条不归本组**:实现成 `-1`/真实索引是一行改动,但它会**改变**
现有 fixture 上任何读 stack 的分支 ⇒ 建议 harness 侧单开、单独验(已写进 GH #150 §3)。

## 4. 为什么值得钉住(本轮最该被别的组拿走的一条)

这是一个**装了子弹的 `axeblink` 陷阱**:下一个想改 Bone Guard 的人,在 fixture 上量域,读到 0,
会得出「域是空的」—— 而他量到的是**工具**。已在 `X.ConsiderW` 正上方写死一段:
**Bone Guard 的域只能用批测请求量,不能用 fixture 扫。**

**一般化的写法**(比 §Y.2 低一层、桌面可查):`HasModifier` 型的门,其可测性取决于那个 modifier
**在战斗日志里有没有 ADD/REMOVE 对**;没有对的 modifier,fixture 世界恒 false,**门下游的一切
结构性不可达**。判别式是现成的:同一英雄身上**别的** modifier 出现在语料里 ⇒ 分母存在 ⇒
这一个的 0 是**关于这一个 modifier 的事实**;整个英雄一个 modifier 都没有 ⇒ 什么都不能说。

## 8. 留给后来人的两条

1. **先问「这个门读的那个 modifier,在语料里有没有分母」。** 34 帧里 0 次听起来像空域,
   但决定它是不是证据的是**同一英雄身上别的 modifier 出现了多少次**(这里 17/17)。
   分母不存在时,那个 0 什么都不是。
2. **一个「怀疑某个 bypass 是缺陷」的结论,先把它绕过的东西的 datafeed 数值读完。**
   本轮的原假设在写代码之前就死了,死于一行 `dname`:`+5 ... Skeletons Spawned` 是**平量**,
   于是「空仓也放」从荒谬变成正确。**拿「它绕过了一个检查」当缺陷证据是不够的**,
   要看它绕过之后那个动作还剩多少价值。
