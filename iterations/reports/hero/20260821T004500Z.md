```
t=342.0  hp   3/363 (0.8%)  mp 170  hero lvl 5  reincarnation lvl 0  cd 3.2
t=342.5  hp   1     (0.3%)  mp 184  hero lvl 6  reincarnation lvl 1  cd 2.4  <- 刚点出大招

t=344.7  DEATH(大招未触发)
```

它确实满足门的每一条前提(hero lvl 6 / 已学 / `cd <= 1.0` / mana 187 ∈ [160,220) / 2 友 2 敌
在 1200 内),**所以它在域内**;但它不是这个门要抓的东西:

1. **1 点血。** 这一刻「要不要撤退」已经不是决策,0.2 秒后就死了;
2. **大招真实上仍在冷却(0.4s)。** 门自己的 `> 1.0` 容差把它读成 ready,但技能不会触发
   —— **这次死亡根本不能归因于蓝量**,armed 也一样死。

⇒ 域**在语义上是空的**,唯一成员是误报。

## 6. 成因(结构性,代码里可指):正确的留蓝**已经在花蓝那一侧**

`bots/BotLib/hero_skeleton_king.lua:490`:

```lua
function X.ShouldSaveMana( nAbility )
	if nLV >= 6 and nAbility ~= nil and abilityR ~= nil
	and abilityR:GetCooldownTimeRemaining() <= 3.0
	and ( bot:GetMana() - nAbility:GetManaCost() < abilityR:GetManaCost() )
	then return true end
	return false
end
```

它**用的就是正确的 `GetManaCost()`**,并且**看住了 WK 全部两个花蓝技能**
(`ConsiderQ` Hellfire Blast 在 :225、`ConsiderW` Bone Guard 在 :442,两处都是
`or X.ShouldSaveMana(...)` 直接 return NONE)。

**⇒ WK 在大招就绪时结构上花不进 [160,220)。** 唯一入口是外部掉蓝(Mana Drain / 虚灵 / Nyx)
或冷却刚走完的一瞬,9 局零发生。数据对上:2119 个就绪帧的 mana **p1 = 234**、**p5 = 260**、
中位 **363**,`< 220` 的只有那 1 帧。

> **一句话:读的那一侧写错了数字,花的那一侧写对了,于是错的数字观测不到。**

反向侧 `gated_extends` = **0 帧**,而 9 局里 **5 局大招吃到 2 级** —— 不是够不到,是蓝从不掉到
160 以下。

## 7. 顺带更正一条已进裁定的事实

#73 的裁定把 lever(a) 的复活条件写成「turbo 局能稳定到 hero level 12+」,依据是 Lion 那轮的
9/11/11。**那是「Lion / 辅助位」的事实,不是「turbo」的事实**:同一批波次里 WK 的 hero level
上限是 **10/11/11/12/12/12/12/13/14**,5 局吃到大招 2 级。⇒ 那句复活条件应改写为
「**在辅助位的经验曲线上**够不到 12」。

## 8. 顺带一条量测事实(给全队,未单开 issue)

第一版扫描报出 **34** 个分歧帧,其中 **33 个是尸体** —— dumper 对死亡英雄**继续输出快照,
状态冻结在死亡瞬间**(那局 WK 带着 187 蓝躺到复活)。任何按帧计数的检测器都会把
**一次死亡放大成几十帧的域**。工具里已加 `hp > 0` 过滤并注释钉住;与 #43 的**赛后**冻结同族,
但这一个发生在**局中**,过滤条件不同,建议各组自查窗口型检测器。
