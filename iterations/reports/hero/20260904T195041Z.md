## 3. 第二步(逐个消费者):**残量不是一个数,是三个互不相交的理由**

`-92` 让我照第二撮的做法「看那个 0 落在比较式哪一边」。**在这一撮上这个问题问不出来**,
因为五个键**根本没有比较式** —— 它们连读它的那一步都不存在。分三类:

| 理由 | 键 | 句柄 | 证据 |
|---|---|---|---|
| **API 里没有 getter** | `AbilityModifierSupportValue`、`AbilityChargeRestoreTime` | 359 | `docs/BOT_API_REFERENCE.md` 全文 0 次 `GetModifierSupportValue` / `GetChargeRestoreTime` |
| **有 getter,焦点五一个消费者都没有** | `AbilityChannelTime`、`AbilityDuration`、`AbilityCharges` | 187 | `GetChannelTime` 5 处(tinker×2、monkey_king、ringmaster、dawnbreaker);`GetDuration` 4 处(windrunner、shadow_demon×2、jakiro);**全部非焦点**。`GetCurrentCharges` 14 处里 13 处是物品句柄,唯一的技能句柄是 techies 的 `ProximityMines`(非焦点),与 `hero_sniper.lua:244` 那句「`GetCurrentCharges()` is item-only」一致 |
| **两半齐全** | `AbilityDamage` | 29 | `GetAbilityDamage` 在 `bots/` 有 58 处;焦点文件里 `hero_lion.lua:583/798/985`、`hero_zuus.lua:888/981` |

**这一格比缺陷本身值钱**:前两撮之后剩下的「还没上规格的键」看上去是一条**待办队列**
(一个数,做完就少一个)。它不是。**六个里五个发不了**,而且发不了的理由**分三种、
互相不能推广**。一个按「把残量清零」推进的轮次会**接五个没人读的 reader**去关一个计数 ——
和 GH #471 记的「接线是纯粹的无效改动**加**一份新的闸债」是同一个形状,只是发生在 mock 里。

## 4. 第三步(发):只发 `AbilityDamage`,而**它一位读数都不动**

**唯一两半齐全的那个键,交集是空的**:快照里**声明**该键的焦点技能只有
`axe_berserkers_call`,值是 `0 0 0 0`;而焦点文件里**调用**该 getter 的五处
(`hero_lion.lua` 的 `X.GetImpaleKillDamage`:583 / `X.ConsiderW`:798 / `X.ConsiderE`:985,
`hero_zuus.lua` 的 `X.ConsiderW`:888 / `X.GetBoltKillHealthCap`:981)调在
**一个都不声明该键**的技能上。两条路都到 0。

⇒ **这次落地是可证明的 no-op**(gate-off/gate-on 无关:这是测试仪器,不带 gate)。

**那为什么还发?因为它换的是「理由」,而这个理由是承重的。**
`lionqdmg` 与 `zusboltcap` 两根活杠杆的**全部立案句**都是「出货的那次读是硬 0」。
在此之前,任何 fixture 驱动的读数拿到的 0 来自 `tests/mock/bot_api.lua` 的通用 `^Get`
默认值 —— **对的答案,错的来源**,正是 `evidence-discipline` 第四条点名的形状
(`tests/test_lion_q_kill_damage.lua:335`/`:511` 两处 `GetAbilityDamage() == 0` 断言
本轮之前就是这么绿的)。现在这个 0 是 loader 自己读 KV 读出来的,**和引擎同源**。

**第二个独立见证**:`tests/mock/ability_damage.lua`(由
`tools/agent/ability_damage_census.py` 从**全部 128 个出货英雄**的 KV 生成,输入与
`special_value_shapes.lua` 不同)的 `NONZERO` 表里 **16 个英雄,焦点五一个都不在**。
两份来源不同的普查对「这个读数是 0」给出同一个答案。

### `zusboltdom` 的处置(`-92` 要求登记该键的那天一起写清楚)

`zusboltdom` 按 `X.GetBoltKillHealthCap` **上限的值**开关,所以**让那个值变成非 0 的改动
会把它变成 no-op —— 那是设计不是回归**。**本次落地不会**:上限仍是 0,因为
`zuus_lightning_bolt` **真的没有** `AbilityDamage` 顶层字段,**引擎在那里也答 0**。
⇒ `zusboltdom` 在 fixture 世界与实战里**都未被触碰**,不需要重裁、不需要重新入集。
真正会触发那条处置的是 **GH #175 / `zusboltcap` 自己域内的 KV 修复**,不是本次。
`§9c` 是那道门:**任何一个焦点英雄拿到非 0 的 `AbilityDamage` 的那天它就红**,
消息里点名 `lionqdmg` / `zusboltcap` / `zusboltdom` 三个必须重读的 id。
