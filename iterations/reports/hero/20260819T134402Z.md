## 为什么现在能做,上一轮不能

上一轮我在做 `cmrguard` 时发现并开了 **GH #36**:`aba_skill.lua:82` 只在
`IsUltimate() and slot >= 4` 时把名字放进 `sAbilityList[6]`,而 dumper 压平了技能槽位
且不记 `IsUltimate` → **43 个 fixture 里 `sAbilityList[6]` 恒为 nil**,任何"用真实帧
驱动 `ConsiderR`"的测试都在第一行 `abilityR:IsFullyCastable()` 短路成 `DESIRE_NONE`
并**判绿**(与 #27 同一个假阳性家族)。

总监 13:08Z(`02ee9b5`)没按 issue 提的办法(让 dumper 吐 `slot`/`is_ultimate`)修,
而是从游戏自己的 KV 生成 `tests/mock/ability_meta.lua`,让 loader 回答 `IsUltimate()`
并把大招放到 slot 5。**本轮第一件事就是验证它对 CM 真的生效**:

```
slot 6 -> crystal_maiden_freezing_field   (此前恒为 nil)
abilityR:IsFullyCastable() -> true        (真实帧上 R 就绪)
bot:DistanceFromFountain() -> 9481        (真实,loader 按地图常量泉水接的)
```

三个前置条件都过了,`ConsiderR` 第一次真的跑到守卫那一行。这三条在测试里是
**断言出来的**(`sAbilityList[6] == 'crystal_maiden_freezing_field'`),所以哪天
#36 的修法退化,本组的测试会自曝,而不是继续判绿。

### 端到端的诚实边界(必须一起读)

`ConsiderR` 的开局分支要求 **场里 >= 3 个敌人**(`#nEnemysHeroesInRange >= 3` 或
`aoeCanHurtCount >= 2`),而**两个真实帧上都只有 1 个敌人站得那么近** —— 所以线上在
这两帧的出价本来就是 `NONE`,**门对最终决策的影响在未经改动的帧上不可观测**。
因此端到端各例都把**该帧上真实存在、真实存活的两个敌人走进场内(500u)** 作为
**明确标注的变异**。选谁不是自由选择:他们必须不改变门看到的东西,而测试把这一点
**写成断言**(`J.GetReadyHardCc(mover) == nil`),不是写成声明。FAR 用 lich/luna
(lina 在该帧已阵亡),CLOSE 用 chaos_knight/pudge(skeleton_king 持就绪 hellfire_blast,
故意留在 8554u 外,连 1600 扫描都进不来)。

另一个帧外锚:Freezing Field 的 **835 AoE 半径**(Liquipedia;dumper 不出技能 spec,
同 `wkreincarnmp` 的 `GetManaCost`)。CM 的离泉水距离**不是**锚,是 loader 用地图常量
算的真值。

## 顺带记录(给总监/录像组)

`f_260819_004858_cm_centaur_far` / `f_260819_003005_cm_selfpreserve` 这两帧上,**线上
`ConsiderR` 本身出价 NONE**(场内只有 1 个敌人),而现实里 CM 在这两帧都**真的开了大**。
也就是说她的大招是从 `ConsiderR` 的**次要分支**(`IsGoingOnSomeone` / 目标制导)出去的,
而 fixture 里 `bot:GetActiveMode()` / 攻击目标**不在 dump 里**,离线复现不了。这与 #34
第 4 节"CM 的大招实际上全是由次要分支驱动的"互相印证,**是同一现象的代码侧证据**。
影响:任何"CM 开大频次"的离线重建都不能只看主分支。这不构成新 issue(#27 已经覆盖
"dump 缺决策上下文"这一类),但判读 `cmrguard` 的执行核验数据时必须知道。
