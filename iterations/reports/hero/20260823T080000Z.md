## 3. 机制:issue 的首要嫌疑是对的,但可以钉得更死

issue 写「少数几局能越过去说明队列不是**严格**阻塞」。实际上采购层
**结构上无法**补齐差的那一根 —— 差的是一个取在过滤器错误一侧的计数:

1. `Item.GetBasicItems`(`aba_item.lua:1239`)展开 `item_magic_wand` 时丢掉每一个
   已持有的组件,但**连续重复的第二个**会被 `sLastRepeatItem`(:1261,注释写着
   「能修复"两个"系列重复的问题」)救回来 ⇒ 身上是 `magic_stick + 1 树枝` 时,
   存活清单是 `{ item_branches, item_recipe_magic_wand }`。**这一步是对的**,
   它确实还想要一根。
2. `item_purchase_generic.lua:1250` 的 `_buildRequiredCounts` 数的是**这份已经
   过滤过的**清单 ⇒ `required['item_branches'] = 1`。
3. `_stillNeeds`(:137)拿它跟 `_countOwnedEverywhere`(:82,扫 0–14 全部格子)比:
   `have(1) < required(1)` 为假 ⇒ `_popIfNoLongerNeeded` 当已满足弹掉。

**分子来自过滤后的世界,分母来自过滤前的世界;只有持有量为 0 时两边才自洽。**
于是唯一被买的是 recipe(唯一一件他一个都没有的组件)—— **与 §3 观察到的 40/40
背包逐位对上**,也解释了为什么 40 局的「最大同时树枝数」直方图是 `{1: 40}`。

**这条通用缺陷已单开 GH #139**:它不是 WK 专属,任何「配方要 2 件同款、买单先给
了 1 件」的组合都走同一条路。**非树枝的同款重复组件(gauntlets / circlet /
slippers / null_talisman …)没有普查过** —— 明写在 #139 里,不假装扫过。
那 4/40 走到 phase_boots/bracer 的局大概率是 `rebuildCount < 3` 的
`GetReducedPurchaseList` 旁路,**没有追**,也写进了测试头。

> **报告「逃逸」的变异,必须先证明它真的施加上了。** M8(「把剥注释那一步拆掉」)
> 第一次跑报 **0 红 = 逃逸**;实际是那条 `sed` 的 Lua 模式转义没匹配上,

**3** 根树枝。**会读散文的解析器就会报告散文。** 剥注释现在是共用函数
`strip_comments`,并有专门的自测钉住它(拆掉它,两条断言红)。

## 9. 核验 —— 以及一个**不是本轮造成、但本轮抓到**的进程内排序红

容器需先 `apt-get install lua5.1` + `luarocks install luacheck`,均已装。

- `luacheck bots game --formatter plain` → **exit 0,0 警告** ✅
- `tests/test_wk_magic_wand_branches.lua` → **10/10 绿**,12 次变异 12 抓 ✅
- **逐文件**跑「所有引用 `skeleton_king` / `life_stealer` / `item_branches` 的
  测试文件」→ **全绿** ✅
- `lua5.1 tests/run_tests.lua`(整套,进程内)→ **在本容器里跑不完**,这正是
  **GH #124** 登记的现象。两次尝试:第一次 2400s 上限内推进到 ~694/1451 例被我
  中止(与并行扫描抢 CPU);腾出 CPU 后仍卡在慢用例上。**失败明细只在跑完时才打印**
  ⇒ 一个字都拿不到。

**但那一次跑出了一个 `F`,我把它定位出来了。** 方法(可复用):`run_tests.lua`
按文件名排序、每个文件内按用例名排序、逐点输出,所以**点的序号唯一确定用例**。
`F` 在第 **507** 个点;把全部文件按同样规则枚举并计数(注意 `test_itemdesire_
world_assertion.lua` 排在 `test_l*` **之前**、有 **25** 个用例,漏掉它会把答案
整体错位 25 —— 我第一次就错在这里)⇒

> **507 = `tests/test_lf_rescue_final_action.lua ::
> [nineteenth world assertion] the mock ids are not stable across loads`**

**它不是本组的文件,也不可能是本轮改动造成的** —— 这是结构性的,不是推测:
① `run_tests.lua` 是**按文件顺序逐个加载并跑完再进下一个**,而本轮新增的
`test_wk_magic_wand_branches.lua` 按字典序排在 `test_lf_*` **之后**,第 507 例跑
的时候它**还没有被加载**,影响不到它;② 本轮在 `bots/` 里的其余改动只是**两个
物品字符串**,而这条断言读的是 `ATTRIBUTE_STRENGTH` 在 mock 里拿到几个不同 id
(GH #133 那条第十九世界断言的同一个文件),**从不读任何买单**。

**它的形状**(源码 :552):断言 `ATTRIBUTE_STRENGTH` 在整份语料里取到 **>=2 个
不同 id** —— 也就是断言 mock 的 id **不稳定**。逐文件单跑该文件 **12/12 全绿**;
只有在整套进程内才红。**这是 08-23T04:00Z 那轮立的「靠同进程副作用」规矩的镜像**:
那两个是**逐文件红、进程内绿**,这个是**逐文件绿、进程内红**。

**诚实边界,这条很重要**:我**没有**证明它是既存红。我只证明了它**不可能由本轮
改动造成**(上面 ①②)。最朴素的复现尝试(先 `api.install({})` 预热 mock 再跑该
用例)**没有复现**,所以触发它的是更早某个文件的更具体的副作用,**具体是哪个没查**
—— 那是 harness 组的活,已带着定位方法和 507 这个序号留言到 **GH #133**。

**结论**:本轮以「luacheck 0 警告 + 逐文件绿」交付,与 08-23T04:00Z 那轮
(GH #124 之后本组已走逐文件)口径一致,并把整套进程内的这一个红**指名交出去**,
不静默吞掉。
