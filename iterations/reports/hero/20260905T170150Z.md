## 1. 事实

`bots/BotLib/hero_skeleton_king.lua` `X.ConsiderW` 的第一条分支(注释写着「辅助进攻」):

```lua
local nEnemysHerosInView = J.GetNearbyHeroes(bot, 1600, true, BOT_MODE_NONE )
local npcTarget = J.GetProperTarget( bot )

if J.IsValidHero( npcTarget )
    and #nEnemysHerosInView == 1          -- ← 本轮改的就是这一项
    and J.IsInRange( npcTarget, bot, 650 )
    and ( nStack / maxStack >= 0.6 or talent6:IsTrained() )
then
    return BOT_ACTION_DESIRE_HIGH
end
```

`nEnemysHerosInView` 是 **1600 内、WK 真正看得见的**敌方英雄(`J.GetNearbyHeroes` 包的是引擎的
`bot:GetNearbyHeroes`,引擎按视野过滤)。`== 1` 因此**恰好**是「我跟一个敌人单挑」——
**团战全被排除**。

**为什么这个形状对这个技能是错的**(条件 (c),全部由仓内 KV 快照支撑,不由口味):

| 项 | 值 | 来源 | 与敌人数量的关系 |
|---|---|---|---|
| behavior | `DOTA_ABILITY_BEHAVIOR_NO_TARGET` | `tests/mock/ability_behavior.lua` | 不选目标、不移动 WK |
| 冷却 | **定长 42**(不随等级) | `tests/mock/special_value_shapes.lua` | 无关 |
| 蓝耗 | `70 80 90 100` | 同上 | 无关 |
| 前摇 | `0.1` | 同上 | 无关 |
| 骷髅存活 | **40s** | 同上 | 无关 |
| 对**英雄**额外伤害 | **+25** | `skeleton_bonus_hero_damage` | **随敌人数增大** |
| 骷髅伤害 | `34 39 43 49` | `skeleton_damage_tooltip` | — |

**代价一项都不是敌人数量的函数**,而**收益是**:一次释放的骷髅活 40 秒、对英雄多打 25,
接进一场 3v3 买到的**面向英雄的攻击秒数**严格多于接进一场 1v1。
把一个**定长冷却的召唤资源**扣着不放过它本来就是为之攒的那场团战,是被支配的打法 ——
这也是 GH #525 对 Axe 那个**无目标** Berserker's Call 的同一读法,
但**机制不同**(那根是魔免前提,这根是**数量前提**),文件不同,英雄不同。

## 2. 改动(gated,turbo-only,未 armed)

新 `X.IsBoneGuardEnemyCountOk( nEnemies )`:armed 时 `nEnemies >= 1`,否则逐字复现出厂的
`nEnemies == 1`;调用点改为 `and X.IsBoneGuardEnemyCountOk( #nEnemysHerosInView )`。
gate 是 `J.IsModeTurbo() and J.IsSoakCandidate( 'wkbonefight' )`,**standalone**
(不与任何别的 id 合取 —— `pullcad` 陷阱;§6 有一条棘轮盯着它)。

**⭐ 方向由构造保证,不由数据保证**(`cullthresh` 那一轮的教训,本轮第一次在**另一个英雄**上复用):
`n == 1` 蕴含 `n >= 1`,对**每一个整数 n** 成立 ⇒ armed 的释放集是 shipped 的**严格超集**。
arming 只能**增加**释放,**永远不能删掉一次**。所以将来的负读数可以归因给
「Bone Guard 放多了不好」,**永远不能**归因给「这根杠杆吃掉了一次释放」。
§3 因此**扫整条数量阶梯**(n = 0..10)而不是断言某一个值 —— 单值断言正是当初放跑
`cullthresh` 第一版错守卫的那种测试。

## 3. ⭐⭐ 本轮最值钱的一格:**能验的那一半和整条分支不是同一半,而这一次能验的那一半正好是改动的那一项**

`X.ConsiderW` **整条分支在 fixture 上驱动不了**,而且这**不是本轮的发现** ——
是本组自己 2026-08-23 写下、2026-08-28 复核过的判词,就写在 `X.ConsiderW` 头上(GH #274):
`modifier_skeleton_king_bone_guard` 在语料里 **一个 WK 帧都没有**,因为 `make_fixture.py`
从战斗日志的 ADD/REMOVE 对重建 modifier,而这个 modifier 没有这样的对。
第二条独立堵点是 `J.GetProperTarget`,在**每一个** fixture 帧上结构性为 nil(GH #474)。

**但改动的那一项不受这两条堵点影响**:`#J.GetNearbyHeroes(bot, 1600, true, ...)`
在真实帧上算得出来。于是 §2 用**真实 helper** 吃**真实帧上的真实计数**:

**13 个 WK 主体 fixture 的可见敌人直方图:0 → 4 帧 / 1 → 2 帧 / 2 → 7 帧。**

- 出厂判据放行 **2/13**;armed 放行 **9/13**。
- 更贴分支形状的切法(**分支还要求 650 内有目标**,而 `GetProperTarget` 为 nil,
  所以用**几何代理**:650 内有敌方英雄):这样的帧有 **7 个**,
  出厂判据在其中放行 **1 个**,**丢掉 6 个**。

**⚠️ 计数是视野受限的**(引擎按视野过滤)⇒ §2 是「多敌人情形出现频率」的**下界**,
误差方向**不利于**本改动而不是有利,这是想要的方向。

**⚠️ 因此这个文件的措辞是:分支 = 源码级覆盖,改动的那一项 = 真实帧覆盖。**
它**不是**「fixture 验证过的分支」。§5 把两条堵点**各写成一条断言**,
**修好那天它红并点名说「这是好消息不是失败,去重写这个文件」** —— 同 `-99` 的处置。

## 6. ⚠️ 本轮自己踩的 / 登记的边界

- 变异台第一版的一行 `echo` 里带了反引号里的 `` `== 1` ``,被 shell 当命令替换执行,
  打出 `==: command not found`。**不影响任何变异的施加或计分**(变异本身走 `sub()` 的
  字面量替换),但它是一行会误导读者的输出,已改成引号。
- **本轮没有买到会翻转的帧,而这个 0 是 fixture 库按构造答不了的**,理由见 §3 的两条堵点。
  不要把 §2 的 9/13 读成「armed 会在 9 帧上放技能」—— 它读的是**数量项**,
  分支的其余三项(modifier / 目标 / 充能)在语料里**答不出来**。
- **充能项 `nStack / maxStack >= 0.6` 本轮不动**。dumper 不记 modifier 充能层数
  (同 GH #27 家族),`nStack` 在语料里恒 0;这一项要动得先有 (a) 证据。
- 归因边界:本 id **只管数量项**,不与 `wkbuild` / `wkrosh` / `wkqdmg` 合取,
  负读数可以干净地归给它。
