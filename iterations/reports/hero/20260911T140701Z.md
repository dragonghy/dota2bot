## 1. 主发现:那条红断言分不清「两条腿选了不同目标」和「有没有目标」

### 1.1 现场

```
FAIL[4]: 6. no decision flips: the archive cannot separate the two legs
      tests/test_wk_q_castrange_meter_domain.lua:509: a frame separated
      {meter zero, fed shipped, fed armed}: tests/frames/f_260909_215040_wk_blast_lion_480.lua,
      tests/frames/f_260909_215040_wk_blast_sb_1052.lua, tests/frames/f_260909_215040_wk_blast_sb_661.lua.
      That is the frame GH #390 asked for -- write it up rather than letting this assertion carry it.
```

三帧逐帧摊开,**三个世界的读数逐位相同**:

| 帧 | z(meter zero) | f(fed, shipped) | a(fed, armed) |
|---|---|---|---|
| `wk_blast_lion_480` | last=1286 desire=0.75 → lion | last=1286 desire=0.75 → lion | last=1286 desire=0.75 → lion |
| `wk_blast_sb_1052` | last=1286 desire=0.75 → slardar | 同 | 同 |
| `wk_blast_sb_661` | last=1286 desire=0.75 → spirit_breaker | 同 | 同 |

行号、desire、目标**名字**全都一样,那 `flips` 是怎么非空的?触发它的是合取式里的最后一项
`f.target ~= a.target` —— 比的是**两个 table 的身份**。

### 1.2 判别子:同一条腿、同样的参数,跑两次

```
ONE LOAD,  same leg twice: t1==t2 -> true    (d 0.75/0.75)
TWO LOADS, same leg twice: t1==t2 -> FALSE   (t1=table: 0x55990229ada0  t2=table: 0x55990239e0b0)
                                              names: npc_dota_hero_lion / npc_dota_hero_lion
```

`drive()` 每条腿各做一次 `rf.load`,**每次 load 自己造一套 unit handle**。于是
`f.target ~= a.target` 在**任何**返回了目标的帧上恒为真,只在两条腿都返回 `nil` 时为假。

⇒ **它量的是「这一帧有没有目标」,从来不是「两条腿选的目标一样不一样」。**
那三帧正是 27 个 body 帧里 ConsiderQ 返回非 nil 目标的**全部三帧**(都在 desire 0.75 的团战支路上,
`wkqdmg` 这个杠杆**够不到**的行);另外 24 帧「一致」只是因为 `nil == nil`。

### 1.3 ⭐ 为什么这不只是一个假阳性

要命的是**这个检测器在两个方向上都不可信**。假如杠杆**真的**换了目标,这一行会打出**一模一样的红**,
而且下一个人会照着它写 write-up —— 错在昂贵的那个方向上(把 harness 的产物当成 `wkqdmg` 的 (a) 证据
发到 issue 上,然后据此推进一个 promote)。⇒ 修法不是「改成按名字比」,而是**先立控制组**:

**改动**:`drive_legs(path)` —— 一次 load,在**同一个世界**里依次跑 zero / shipped / armed / **再跑一次
shipped**。最后那次是控制组,它必须和第一次 shipped **逐位相同**;控制组的断言**排在 flip 断言之前**。
控制组一红,底下那个 flip 读数一个字都不作数。

**本轮读数**:`ctrl_breaks = 0`,`flips = 0`。⇒ **归档分不开两条腿,一帧都分不开。**

### 1.4 ⭐ 买到的纪律:一个文件可以在 header 里声明观测量,却没有量它的仪器

这个文件的 §4 自己写着 **「The observable is TARGET IDENTITY, never cast count.」** —— 那句话是对的,
是本轮能找到缺口的原因。但**从 2026-09-09 到今天,这个文件没有任何一件仪器能量目标身份**。
声明观测量和拥有该观测量的量具是两件事,而且前者会让人以为后者也有。
(同族:GH #616/#624 的「推的人的闸里没有任何 Lua 测试」——**声明了覆盖,没有执行体**。)
header 那句话**逐字保留**,旁边补了这一段。

## 2. 主发现之二:#390 recommendation 2 的答案 —— 支路不缺射程,缺的是 claim

#390 rec 2 原话是「改问一个分支到达的问题:`X.ConsiderQ` 的击杀确认分支到底产不产 Q 施法?」
本轮在归档上把它拆开量了。关键是 Lua 的**短路**:

```lua
if GetUnitToUnitDistance( bot, npcEnemy ) <= nCastRange + 80
    and J.CanKillTarget( npcEnemy, X.wk_GetBlastKillDamage( abilityQ ), nDamageType )
```

`wk_GetBlastKillDamage` **只在距离门已经通过时才被调用** ⇒ 数它的调用次数,就把「够不着」和
「打不死」这两种拒绝**分开**了。这正是 rec 2 要的那个拆分。

| 读数(两条腿,按 (帧,敌人) 对) | |
|---|---|
| 到达距离门 | **9** 个 body 帧(27 个 body 帧中) |
| **通过**距离门,算出 claim | **12** 对 |
| claim 通过,支路开火 | **0** 对,**两条腿都是 0** |

⇒ **支路是被到达的(12 次,不是 0 次),它停在 claim 上,不停在射程上。**
这与 §3「这个环十年来一直是 330 宽而不是 855」预测的方向相反,也是为什么 §3 那句
"understates reach" 说的是**环**,不是这道门。

⭐ **而且余量很窄**:归档里最紧的一对是 `f_260909_215040_wk_blast_sb_661` 的 spirit_breaker
**172 原始 hp vs 出货 claim 168.0 —— 差 4 点**(未计魔抗)。

⚠️ **这个 4 与 #390 的「最近一次差 63.6 ehp」不可比,两个不同总体**:#390 量的是 12 局里**真的发生过**
的 205 次施法,本轮量的是 51 个存活 WK 帧上支路**评估过的全部 (帧,敌人) 对**;而且一个是 ehp 一个是原始 hp。
**两者一致的只有那个 0,而只有那个 0 被写成结论。**

⭐ **归档里已知存在一个落进 band 的帧,它到不了这条支路**:`f_260820_181711_wk_l1trade_333`
(juggernaut 160 hp,出货 claim 168 会开火 / armed 120 不会)—— **Q 在该帧冷却 13.3s**,`ConsiderQ`
早在冷却档就 bail 了,在本轮的桶普查里它坐在 **COOLDOWN** 桶。⇒ **band 不是天方夜谭,是冷却/到达
把它挡在支路之外。** 这一条已写进 `hero-59` 的扫描指令,要求把「落进 band」和「当帧 Q 可用」分成两列,
**否则这两种 0 会混成一个**。

### 3.2 ⭐ M2 第一次是**假的变异,它只改到了散文**

第一版 M2 的正则是 `nDamage * 1.68` —— 树里命中的是**第 632 行的注释**,真正的出货公式在第 680 行
写作 `( 40 * ( hAbility:GetLevel() - 1 ) + 100 ) * 1.68`。于是它「存活」了,而**它根本没变异过代码**。
⇒ **一个存活的变异体,先问它改到代码了没有**(evidence-discipline 2 的前置);这是上一轮
「断言在数代码还是在数散文」那条纪律的**第二个实例,换到了变异台这一侧**。

### 3.3 ⭐ M2 改对之后,抓到的是**我自己这一轮新写的断言的排序缺陷**

M2 改对后,§9 确实红了,但红在**错的那一条**上:

```
9. ... : the kill claim was computed on 7 (frame, enemy) pairs on the shipped leg;
   it was 12 on 2026-09-11 ... so fewer means the branch stopped being reached
```

原因:claim 一旦通过,支路**当场 return** ⇒ 循环提前结束 ⇒ **开火的世界评估到的对数更少,不是更多**
(12 → 7)。我把「到达下界」写在了「开火为零」之前,于是**这个文件唯一存在的理由(抓到开火)
会把自己报成「支路不再被到达」** —— 方向相反的误诊,会把下一个读者支去 §5。
**已改成开火断言在前**,并在旁边写清了原因。与 §6「控制组在读数之前」**同一个形状**:
**能给发现起错名字的那条断言,必须排在能起对名字的那条后面。**
