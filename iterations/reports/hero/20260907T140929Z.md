## 1. 缺陷:`X.ShouldSaveMana` 判五件事,没有一件问「他会不会死」

`bots/BotLib/hero_skeleton_king.lua` `X.ShouldSaveMana`(**出货、无闸**):

```lua
nLV >= 6  and  nAbility ~= nil  and  abilityR ~= nil
and abilityR:GetCooldownTimeRemaining() <= 3.0
and ( bot:GetMana() - nAbility:GetManaCost() < abilityR:GetManaCost() )
```

英雄等级、两个非 nil 句柄、R 的冷却、一道减法。**没有一项是危险度。**

## 3. 改动:形状保证方向,不是算术保证方向

`X.ShouldSaveMana` 把出货五项合取式**绑定成 `bShipped`**,随后

```lua
if bShipped and X.IsReincarnationReserveIdle() then return false end
return bShipped
```

⇒ **armed 只能把答案由 true 变 false**。这是**形状**的性质,不是今天算术的性质。
新 helper:

```lua
function X.IsReincarnationReserveIdle()
	if not ( J.IsModeTurbo() and J.IsSoakCandidate( 'wksaveidle' ) ) then return false end
	if J.GetHP( bot ) < 0.95 then return false end
	return #J.GetNearbyHeroes( bot, 1600, true, BOT_MODE_NONE ) == 0
end
```

**1600 这个半径和整个调用是本文件自己的** —— `X.ConsiderW` 的 `nEnemysHerosInView`
逐字相同。没有新造一个没人量过的数。

### ⛔ 归因方向,预登记,不许合并

**WIDENING**:armed 之后 bot 放得**更多**。负读数**只能**读作「多放出来的那些不该放」,
**绝不能**读作「少了 N 次复活」—— 储备不产生复活,它只把蓝留着,而任何离线台都
无法给一次**没有发生的死亡**定价。跨语料的方向由 §3 用**同一个 `tally()` 调两次、
第二次两条腿对调**证明:必须读 0 的那条腿,在对调调用里必须报出**整个域(2)**,
所以那个 0 是被证明会数数的计数器产生的('staytower' 那轮 M14 的教训)。

## 4. 诚实边界(四条,写在源码头注与测试头注里)

1. **「1600u 内看不见敌人」不是「安全」。** 雾是真的;从 1700u 走进来的抓人这一项
   看不见。它买到的是「bot **看不到**囤蓝的理由」,与本文件其它敌人计数分支同一标准。
   hero-41 的第 (3) 列就是为这条边界设计的(命中后 8s 内是否死亡 / 敌人首次现身时刻)。
2. **2/33 是域不是频率。** fixture 语料是为别的调查切出来的一组瞬间。
3. **不碰同一函数里的 rank 盲区**(`nLV >= 6` 顶替「R 学过了」)。33 个计价帧里
   **level>=6 且 R rank 0 的帧数为 0**(本轮实测,复现了 census §6 的读数),
   就地没有证据可修。§7 断言本轮没有顺手把它关掉。
   ⚠️ **一处待判的矛盾,本轮只登记不判**:撤退位点的兄弟 id `wkreinctr` 在**它自己的
   语料**上量到「24 个出厂 TRUE 里 14 个坐在 ability level 0 上,其中 2 个在英雄
   等级 7」;而 census §1 把看起来符合这个形状的两帧**排除**了,理由是那两帧
   `rank 0` 是**缺席字段**。两处读数看起来矛盾,**很可能是同两帧的两种读法**。
   已挂进 hero-41 当一列(只要那个数,判读留下轮)。
4. **「储备被释放」≠「放了一发技能」。** census §5 量到出货 `X.ConsiderQ` 在 33 帧上
   无论储备开关都答 0;本文件 §6 在两个域帧上**重新推导**了这件事而不是引用它,
   所以这条边界不会悄悄过期。
