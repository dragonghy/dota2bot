## 1. 事实:今天焦点五的 t10/t15 各自在选什么

锚 = `https://www.dota2.com/datafeed/herodata?language=english&hero_id=<id>`,2026-08-22 读。
**只有 t10 / t15 在 turbo 可达**(GH #84 的等级普查:`level >= 20` 在 210 个英雄槽上 **0** 次,
高水位 19),所以下表只列这两档;t20/t25 记录在测试文件里但**不上棘轮**(钉死角只会制造噪音)。

`{0,10}` 取该档的**奇数**索引,`{10,0}` 取**偶数**索引(`aba_skill.lua:135`;测试是把这条
算术**从代码里读出来**的,不是断言的)。

**顺带澄清一条别人可能踩的坑**:`lion_to_hell_and_back` 在 feed 里标 `ability_is_innate: true`
—— 它**不是** facet 技能,Lion 永远有它,所以 lion 的 t15 选择**不是**在赌 facet。
同理 `zuus_cloud`(`ability_is_granted_by_scepter`)与 `zuus_lightning_hands`
(`ability_is_granted_by_shard`)都**不占初始技能槽**,Zeus 的 `sAbilityList` 索引
1/2/3/6 = arc / bolt / jump / 大招,**没有漂移**。#104 §1.3 记的「facet 门控天赋会让索引
整体前移」这个担忧,**机制本身仍可能成立,但它引用的证据不成立**:名字里带 `facet_`
不等于 facet 门控(WK 的 `..._facet_1` 改的是普通技能的普通数值,`required_facet` 为空)。
**而且 datafeed 对这五个英雄 `facets` 数组一律返回空** ⇒ 这个端点**根本回答不了** facet 问题
—— 所以正确的说法是「无证」,不是「已排除」。

## 2. 改动:Axe t10 `{0, 10}` → `{10, 0}`(纯数值,不 gate)

章程:**纯数值/构筑改动(出装顺序、天赋表)可以不 gate,但要写清理论依据**。依据全部是
「两个天赋各自的兑付条件」,不是口味:

- **[1](原选)只在 Culling Blade 拿到英雄人头之后兑付**,且只是把一个 buff 从 6s 拉到 9s。
  Culling 是 175 射程、70/75/80s cd 的处决技;buff 到账时,它本可以帮忙赢的那场架已经结束了。
- **[2](现选)只要场上有一个 Battle Hunger 在跳就兑付,每个 +8%**。Battle Hunger 是这个文件
  **买的第一点**(加点行 `{2,3,1,3,3,6,3,2,2,2,6,1,1,1,6}`),**10 级点满**,12 秒持续 /
  20-15-10-5 秒冷却,而 `X.ConsiderW` 有**四条**独立分支在放它(击杀 / 先手 / 团战最弱 /
  对线消耗)。所以它在大多数团战里都是亮着的。
- **它买的正是这个 Axe 缺的属性**:本组自己的实测(GH #56 / backlog #5)是他在 turbo 局
  **从来没有跳刀** —— 4 局 0 次、另外 4 局 0 帧 —— 所有的进场都是走过去的。

**诚实边界(和改动一起写进了 hero 文件)**:

1. [1] 是**团队** buff(+20/25/30 移速、+10/15/20 护甲、900 半径),本改动放弃了它 3 秒。
   主张是**兑付频率**,不是单次兑付谁更大。
2. **没有读任何语料**。上面数的是施放条件与本文件自己的加点顺序,**不是每局施放次数**。
3. **拿不到 pick-rate 佐证**:dotabuff 403 / liquipedia 429 / fandom 402,搜索结果是旧补丁。
   所以引用的数字全是 Valve 自己的 datafeed 字符串与数值,不是攻略里的散文。
4. 这是**未 gate 的改动 ⇒ 它现在就在稳定版里**(main 上所有 gate 关闭的默认行为),
   turbo 与普通模式**都**生效。理由是按 turbo 论证的(跳刀在 turbo 买不到);普通模式里
   Axe 会有跳刀,但 [1] 在那儿也不因此变强 —— 它的兑付条件不变。**请总监记一笔稳定版漂移。**

## 3. 顺带查出来的两处陈旧事实(都已就地写进 `hero_axe.lua`,行为不变)

**(甲) 那条 t15 注释不只是过期,它和自己的算术是反的。** 原文
`['t15'] = {0, 10}, -- +35 attack speed over +2 mana regen`。文件底下的 npc 块是 7.2x 的,
其中 `Ability12 = special_bonus_mp_regen_2`(索引 3)、`Ability13 = special_bonus_attack_speed_35`
(索引 4)。而 `{0,10}` **取奇数索引 = 3 = mp_regen_2** ⇒ **这一行选的正是注释说它拒绝的那个**。
所以这条注释是**删掉**而不是更新:两个名字今天都不存在,而**写它的人把编码方向搞反了**
—— 这就是本轮为什么把 `{0,10}/{10,0}` 的奇偶语义**驱动着**钉进测试(§1 第二例),
而不是在注释里再写一遍。t15 **本轮不动**(今天的这一对是 +8 Battle Hunger dps vs
+10 Call 护甲,值得单独一轮和它自己的证据)。

**(乙) `talent8` 的注释错了两层**,已更正:它写 `special_bonus_unique_axe: +Culling Blade
kill threshold`,而今天 `special_bonus_unique_axe` 是**索引 [3]**(+8 Battle Hunger dps),
索引 [8] 是 `special_bonus_unique_axe_5`(+Culling Blade **伤害**)。加进 `nKillDamage`
在新名字下仍然读得通(Culling 的「击杀阈值」早已并进它的纯伤害),但两个 handle
(`talent7`/`talent8`)**都是 t25** ⇒ 在 turbo 里都是死重量。

## 4. 登记但**没做**的一根杠杆(就地写成注释,附预注册域)

`X.ConsiderR` 的 `nKillDamage = 150 + 100 * nSkillLV` = **250/350/450**,而 Culling Blade
今天的伤害是 **275/375/475**(datafeed hero_id 2)⇒ **bot 低估自己的处决技 25 点纯伤害**,
于是在「目标血量落在估计值上方那 25 点带内」时**拒绝一发本来能杀的 Culling**。
正确的修法是从技能自己读(`abilityR:GetSpecialValueInt('damage')`),不是把今天的数再硬编码一遍。

**本轮不做,因为它是「增加一次施放」而不是「减少一次施放」**,本组对加动作类改动的门槛是
真实帧 + 量过的域,而本轮没买语料。**预注册域**已写进代码注释:Culling 就绪 + 目标在 175 内
+ 目标当前血落在 `(150 + 100*lv, 技能伤害]` 带内的帧,**数 episode 不数帧**。
