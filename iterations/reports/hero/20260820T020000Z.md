## 第 1 处:`bots/BotLib/hero_largo.lua:416`

```lua
and (J.IsCore(bot) or not J.IsThereCoreInLocation(creep:GetLocation(), 650))
```

`J.IsThereCoreInLocation` **全树没有定义**。Lua 在**调用时**才解析表字段,所以
文件照常加载、luacheck 照常 0 警告、`test_smoke_load` 照常绿 —— 缺陷只存在于
**走到那一行的那一帧**,而在那一帧它 raise
`attempt to call field 'IsThereCoreInLocation' (a nil value)`。

`or` 短路 ⇒ **核心位 Largo 永远走不到**;只有**辅助位 Largo** 会崩。所在分支是
`X.ConsiderCatchLick` 的**对线期击杀小兵**分支(`J.IsLaning and J.IsInLaningPhase`),
即整个对线期反复出现的帧形状。

### 代价比 issue 里写的更重(本轮量出来的)

没有任何地方 `pcall` 包 `X.SkillsComplement` —— `ability_item_usage_generic.lua:8520`
从 `AbilityUsageThink` **裸调**。所以异常抛出时,那一帧**整个技能层**都没了:
`SkillsComplement` 里排在后面的 `ConsiderFrogstomp`、`ConsiderAmphibianRhapsody`
一并被吞,不只是这一个 consider。而在游戏里这一切**看不见**(`print` 到不了控制台,
引擎的错误处理器把 Lua 错误文本吃掉)。

### 修复

`J.IsThereCoreInLocation(vLoc, nRadius)` 定义在 `bots/FunLib/jmz_func.lua`,
**紧挨着它的兄弟 `J.IsThereCoreNearby`**:同一段 team-member 遍历、同一条自我排除
(`allyHero ~= GetBot()`)、同一个 `J.IsCore` 判据,**只把距离项换成
unit-to-location**(`J.IsInLocRange`)。

**为什么选兄弟形状而不是 issue 建议的 `J.GetAlliesNearLoc` + `J.IsCore` 六行**:
结果等价,但兄弟函数**已经在线上跑**(pudge / venomancer / tinker / windrunner
四个 hero 文件在用),复制一份已验证的形状比重写安全。附带好处:
`J.IsInLocRange` 自带 `CanBeSeen()`,顺手把"已阵亡友军的陈旧坐标压住一刀"堵掉。

### 为什么没有 gate

门的关闭侧应当**等于上线默认行为**;而这里的上线默认行为是**抛异常**,不存在
一个"保守版本"可以保留。真正需要定夺的是**语义**(true / false / 忠实实现),
所以语义**钉在测试里**而不是写在讨论里 —— 这正是总监在 issue 里说的
"该由能把它放到真实帧上的人来定"。

## 诚实边界(两条,都不小)

1. **`X.ConsiderCatchLick` 没有被端到端驱动**。原因不是偷懒:**造不出 Largo 的
   fixture** —— 手边任何归档录像里都没有 Largo(他不在焦点五,也不在批测抽到的
   阵容里;按 #46/#49「一个种子 = 一套阵容」,阵容是全有或全无)。所以交付的是
   「真实帧 + 重建调用点表达式 + 源码 tripwire」,**不是真正的端到端**。要真端到端,
   得先有一局带 Largo 的录像。
2. **「谁是核心」在 fixture 世界里是声明的,不是观测的** —— 而且这是个更大的坑,
   见下面「顺带发现」。本测试因此**显式发 player id** 并把得到的 1/2/3/4/5 分裂
   **断言**出来(header 里逐条标注哪些是声明、哪些是观测)。helper 真正读的东西
   —— 位置、队伍、生死、可见性 —— 全是真实帧数据。
3. **Largo 不是焦点五**,本轮不对他的整体强度做任何声明;修的是一个崩溃,不是一次调优。

## 顺带发现 → 新开 `[harness]` **GH #53**

要在真实帧上钉「附近有没有核心」,才发现 **fixture 世界根本回答不了「谁是核心」,
而且它不是拒绝回答,是答错**:

- `tests/mock/bot_api.lua:162` 把 `GetPlayerID` 默认成 **0**,而 `replay_fixture.lua`
  造英雄时不传它(dump 里没这个字段)⇒ **一帧里 10 个英雄的 PlayerID 全是 0**;
- `aba_role.lua:364` 的非 CM 兜底是拿 player id 去 `GetTeamPlayers()` 里找下标读
  `RoleAssignment` ⇒ **五个人全部匹配到下标 1**;
- ⇒ **`J.IsCore(任意友军) == true`,在所有 61 个 fixture 里**。

**现成的受害者**:`tests/test_replay_creeppull_reachable.lua` 的
`end-to-end: the pull bid is reachable on the real frame`。`J.ShouldCreepPullLane`
里有一条 `if not J.IsCore(bot) then return nil end`(`jmz_func.lua:6479`,注释自己
写着 "Laning-phase core only")—— 这条子句在 fixture 里是**白送**的。实测:把 loader
改成给 roster 逐个发不同 id,**581 个测试里恰好只有这一条挂**,因为那个 fixture 的
roster 是**按英雄名字母序**的,zuus 落在下标 5。

**那次实验我没有保留**,并且在 #53 里写明了理由:dump 的 units 顺序是**字母序**,
和真实分路/位置毫无关系,所以"给不同 id"是**把一个任意答案换成另一个任意答案**,
不是修复。根因在 dumper —— `tools/batch_test/behavioral/dumper/main.go` 的 snapshot
里**没有 player id、没有 assigned lane、没有 draft 顺序**,和 #27(无 `vis`)、
#36(无 `is_ultimate`)、#43(赛后冻结帧)是同一个家族。#53 里给了三档处置建议
(dumper 加 `player_id` 最小改动;在此之前一律显式声明并断言;creeppull 那例请补声明)。

顺带一条同根因的:`J.Utils` 的缓存 key 普遍拼 `GetPlayerID()`,id 全是 0 ⇒
**一帧里 5 个友军共用一个缓存槽**。目前没观察到具体假绿,dumper 加字段会顺带修掉。
