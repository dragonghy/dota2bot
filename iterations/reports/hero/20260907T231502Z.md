## 2. ⭐ 找到的缺陷:一个出口在出货腿上**不可达**,而且是闭式的

`bots/BotLib/hero_lion.lua` `X.ConsiderR` 有十个开火点。其中两个隔三十行,
**读同一个列表** `nInBonusEnemyList`(`J.GetNearbyHeroes` at `nCastRange + 400`):

```
击杀 循环   for e in nInBonusEnemyList:
               J.IsValidHero(e) and X.CanCastAbilityROnTarget(e)
               and J.WillMagicKillTarget(bot, e, nDamage, nCastPoint + 0.25)
               -> return HIGH, e

团战 出口   npcWeakestEnemy := argmin GetHealth over
               { e in nInBonusEnemyList : J.IsValid(e) and X.CanCastAbilityROnTarget(e) }
            if npcWeakestEnemy ~= nil
               and J.WillMagicKillTarget(bot, npcWeakestEnemy, nDamage, nCastPoint + 0.25)
               -> return HIGH, npcWeakestEnemy
```

**同一个列表、同一个 `nDamage`、同一个延迟、同一个 helper。**
走到第二句意味着第一个循环什么都没找到,即该列表**没有任何元素**满足那个合取;
而 `npcWeakestEnemy` 正是该列表里一个**已经通过 `X.CanCastAbilityROnTarget`** 的元素
⇒ 它的 `WillMagicKillTarget` **由构造为假**。

两个选择器只差一个谓词,`J.IsValidHero` vs `J.IsValid`,而在这条列表上、
在 `X.CanCastAbilityROnTarget` 通过之后,**两者同答**:

- `J.IsValidHero(e)` = `not IsNull and CanBeSeen and IsAlive and not IsInvulnerable and IsHero`(`bots/FunLib/utils.lua:547`)
- `J.IsValid(e)` = `e ~= nil and not IsNull and CanBeSeen and IsAlive and not IsBuilding`(`bots/FunLib/jmz_func.lua:3295`)

`X.CanCastAbilityROnTarget` → `J.CanCastOnNonMagicImmune` 已经要了 `CanBeSeen` 与
`not IsInvulnerable`;`J.GetNearbyHeroes` 给的是英雄 ⇒ `IsHero` 真、`IsBuilding` 假。
两边都退化为 `not IsNull and IsAlive`。

**⇒ 出货的「团战」出口开不了火。**

## 3. 落地的 gated 修复(`lionultcash`,turbo-only,**未 armed**)

新 `X.lion_ShouldCashUltAtWeakest( hBot, hTarget, nCastRange, nBotHP, bShippedLethal )`。

**方向由构造保证 —— WIDENING,严格超集,目标不变**:
出货答案由调用点先算并**作为实参传入**,helper **第一句**就
`if bShippedLethal then return true end`,armed 只在它答 false 之后可达;
`npcWeakestEnemy` 在调用**之前**就选好,helper 不重选。
每一条 armed 的退出都 `return bShippedLethal`,**函数体里没有一个裸 `return false`**
(§5 的断言钉着;那是这个方向上的禁止字面量)。

armed 三条合取,各自带理由:

| 合取 | 理由 |
|---|---|
| `nBotHP < 0.4` | 块自己那一半。纯 `IsInTeamFight` 满血那一半**故意不开**:满血团战里把 100s+ 冷却的大招丢给一个砍不死的目标不是明显对的 |
| 2 秒内被英雄伤害 | 他是在**被杀**,不是只是血少。这也是 `J.IsDyingUnderAttack` 用的判别式,但**在这里写开** —— 那个 helper 自己 gated 在 `ultcash` 上,合取两个 id 就是 **pullcad 陷阱** |
| 目标在 `nCastRange` 内 | `npcWeakestEnemy` 取自 `nCastRange + 400` 的列表。少了这一条,armed 会下一个**要走过去**的施法单,把「死前兑现大招」变成一次 dive —— 那正是 backlog `-120` 在 CM 那边点的同族问题,**本杠杆不把它带进来** |

⚠️ **`nHP` 是传进来的、不是重算的**,这不是整洁:`J.GetHP( bot )` 对**自己队**的单位
读 `OriginalGetHealth()/OriginalGetMaxHealth()`(`jmz_func.lua:4079`),
与块自己的 `nHP = bot:GetHealth()/bot:GetMaxHealth()`(`:410`)**不是同一个数**;
重算会让两处的 `0.4` 互相打架。§5 有一条断言禁止 helper 体里出现 `J.GetHP(`。

## 4. ⭐⭐ 验证:不可达性是**驱动**出来的,不是读出来的

真实帧 `tests/fixtures/f_222428_lion_lich_burst.lua`(Lion subject,两个敌方英雄
**真的在射程内**:lich 701 血 @676.4u、axe 629 血 @740.9u,`nCastRange` 900,最弱是 axe)。
走**真的 `X.SkillsComplement`** 派发,用 `rf.record_actions` 录动作。

关键手法:**穷举的是「致命性谕示」,不是任何一方的血量。**
`J.WillMagicKillTarget` 被换成一个对**至多一个指名单位**答 true 的谕示,
在该帧名单上跑遍所有取值 —— 于是这不是一次取样,是**整个致命性立方体**。

| 致命的是谁 | 闸关(出货) | 闸开(armed) |
|---|---|---|
| 谁都不致命 | **一发不放** | **finger → axe** ← 杠杆 |
| lich | finger → lich(击杀) | finger → lich(**逐位相同**) |
| axe | finger → axe(击杀) | finger → axe(**逐位相同**) |

三点三中:闸关逐字等于出货;armed 只在出货拒绝的**那一个**点上不同;
两腿都开火时**目标相同**。
第一列同时就是不可达性的证明 —— **不存在**一种致命性取值让出货的「团战」出口开火。
