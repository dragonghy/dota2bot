## 1. 三处陈旧事实

锚:`https://www.dota2.com/datafeed/herodata?language=english&hero_id=42`,2026-08-22 读。
不是从 Liquipedia 的散文里抄的,是结构化字段。

### 1.1 索引 2 是 Bone Guard,不是「吸血光环」

| sAbilityList | 真名 | 关键数 |
|---|---|---|
| 1 | `skeleton_king_hellfire_blast` | 525 射程 / 95-110-125-140 蓝 / 14-12-10-8 cd / **落地 80-100-120-140 + 2s dot 20-40-60-80** / 停 1.0-1.6s |
| 2 | `skeleton_king_bone_guard` | **主动、无目标**。70-80-90-100 蓝 / **恒 42s cd** / 2-4-6-8 层上限 |
| 3 | `skeleton_king_mortal_strike` | 被动暴击 / 骷髅 |
| 6 | `skeleton_king_reincarnation` | 220-110-0 蓝 / 180-150-120 cd |

吸血是 `skeleton_king_vampiric_spirit`,datafeed 标 **`ability_is_innate: true`**
⇒ `J.Skill.GetAbilityList` 跳过 innate ⇒ **它一个技能点都不要**。
`skeleton_king_vampiric_aura` 这个名字**已经不在他的技能集里**。

### 1.2 `abilityW` 的种子名不在他的技能集里

```lua
local abilityW = bot:GetAbilityByName('skeleton_king_spectral_blade')   -- 旧
```

datafeed 的五个技能里没有它;全仓库 `grep` 只命中这一行本身。⇒ 每次加载解析成 nil,
**整条 W 路径靠 `X.SkillsComplement` 里那行兜底重取**
(`if not abilityW or abilityW:IsHidden() then abilityW = bot:GetAbilityByName('skeleton_king_bone_guard') end`)。

**没崩,也没有行为差异 —— 而这正是可以动它的理由**:因为兜底在,把种子换成真名时
`abilityW` 在**每一个读取点**上都还是同一个 handle ⇒ **可证的空操作**。兜底那一行**保留**,
并写成一条测试(删掉它就红),因为删了之后种子就变成了加载顺序风险。

> 唯一的假设:`GetAbilityByName` 对本单位没有的技能返回 nil。**结论不依赖它** ——
> 就算它返回别的东西,兜底那行也把结果压成同一个 handle;依赖这条假设的只有
> 「旧代码为什么没崩」这句**解释**。

### 1.3 npc / 天赋块整块是 7.2x 的

旧块写着 `special_bonus_attack_speed_20` / `..._strength_15` / `..._unique_wraith_king_7/6/1/8`。
今天是另外八个名字、另一个顺序(见 GH #104 §1.3)。WK 的 `tTalentTreeList` 于是解析成
t10→[2] / t15→[4] / t20→[6] / t25→[7],而**只有 t10 和 t15 在 turbo 里拿得到**。

**一条独立旁证**(用来核对「datafeed 按槽顺序列天赋」这个假设):旧块的
`Ability17 = ..._unique_wraith_king_4` 与今天的索引 [8] **逐字对上**;另一条是
`talent6` 恰好被 `X.ConsiderW`(Bone Guard 的 consider 函数)读,而索引 [6] 正是
Bone Guard 天赋。两条都是「如果顺序假设错了,这个巧合不会成立」型的核对。

## 3. `talent6:IsTrained()` 是一个 20 级测试

`X.ConsiderW` 两条释放分支都把它当**析取旁路**:

```lua
and ( nStack / maxStack >= 0.6 or talent6:IsTrained() )   -- 分支 1
if ( nStack == maxStack or talent6:IsTrained() )          -- 分支 2
```

证明链**全在仓库自己的代码里**:`talent6 = sTalentList[6]`,而 `aba_skill.lua:135` 的
`J.Skill.GetTalentBuild` 把 t10 驱动到索引 {1,2}、t15→{3,4}、**t20→{5,6}**、t25→{7,8}。
这条**不依赖**「哪个名字在哪个索引」,只依赖索引本身。配 GH #84 的等级普查
(`level >= 20` 在 210 个英雄槽上 **0** 次、高水位 19)⇒ **turbo 内恒假**。

**它有牙齿吗?有,只在 20 级有。** 同一帧(0/8 层、在兵线前、蓝够、Q 不可施法):
`IsTrained` 假 ⇒ `ConsiderW()` 返回 0;真 ⇒ 返回 `HIGH`。所以 turbo 里分支 2 的条件
**严格就是满层**,分支 1 严格就是 `>= 60%` 层。

这是 GH #84 §4.2 的**下一层**:§4.2 记的是 `tTalentTreeList` 的 t20/t25 两行是一张**表**里的
死重量;这里是**一个 t20 handle 被读进了出货中的决策函数**。

## 6. 跨组、只登记不动:facet 门控天赋会整体移位索引

天赋是**按索引**选的(`tTalentTreeList` → `GetTalentBuild` → `sTalentList[n]`),而 WK 的
索引 [2] 与 [6] 是 **facet 门控**天赋(`..._facet_1` / `..._facet_3`)。
`J.Skill.GetTalentList` 只把 `IsTalent()` 为真的槽 `table.insert` 进去 ⇒ 若某个 facet 没被选中
导致那个槽不是天赋,**它之后的所有索引整体前移**,而**全英雄池**的 `tTalentTreeList` 都按
索引选人。

**离线不可证伪**(mock 的天赋槽是空的,`sTalentList` 恒为空表),所以本轮只登记、不主张。
建议单开一条给总监/协同组。

## 7. 方法上的一条:第一稿的档位测试被一个变异走过去了

第一稿这么写档位断言:构造 all-`{0,10}` 与 all-`{10,0}` 两份配置,按**返回列表的位置**
认档位(`ipairs({10,15,20,25})`),然后断言索引 5/6 落在 20。

**M6(把 `GetTalentBuild` 的第三个 pick 重新指到别的档位键)从它旁边走了过去** ——
因为那个断言检验的是**我自己的排序假设**,不是代码里的接线:第三个 pick 读哪个键,
按位置认档位的写法根本看不见。

改法:**每次只翻一档的那一行,看返回的哪几个索引变了**,把「哪一档驱动哪些索引」
从代码里读出来再断言。改完 M6 与新加的 M12 都抓。

**同一节里还有第二件事,而且是普查棘轮抓的我自己**:`live_lines()` 一开始只剥
「以 `--` 开头的行」,**剥不掉 `--[[ ]]` 块**(npc dump 就是这样一个块,块内的行不以 `--` 开头)。
本轮我给那个块补了一句话、里面出现了 `talent6` 三个字 ⇒ 普查当场把 `skeleton_king` 数成
**3 处 STRUCTURAL**(记录是 2)而变红。**这不是误报,是判据的真实缺口** —— 已改成先 `gsub`
掉长注释再逐行剥。留一条给后来人:**任何「扫源码数活代码」的判据都要显式处理块注释**,
否则你在文件里写的每一句解释都会被自己的普查当成代码。

> **「断言一个映射」和「把映射从代码里读出来」是两件事。** 与 §AD 旁那条
> (「一对结局相反的帧只能钉住它们不同的那一维」)同族:一个只在**你没写进断言的那一维**上
> 变的变异,是检验断言写对没写对的唯一办法。建议收进判读纪律节。
